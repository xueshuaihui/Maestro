## 一、背景与问题

### 1.1 现状与问题

I1.6 之后，三种内建模板、角色/技能/工作流资产、CLI 命令集都已经能跑，但「实例管理器」还差最后一层：**它记得住过程，却接不住中断**。

- **daemon 一崩，实例就被判「已中断」**。我在跑编码闭环的回流复测：开发第二轮已完成、测试正在复测，机器重启或进程被强杀；再执行 `orch status`，只看到「已中断 ｜ 停在节点 执行中 / 会话 执行中」。之前已经完成的节点、已经确认的轮次、已经投出去的交接包，全部停在原地，没有人把它们接起来。继续跑只能新建实例，从第 1 轮重新开始。
- **重启后，已经做完的节点会被重做**。因为没有任何一份「最近一次确认过的位置」被单独记住，新核心只能按最保守的办法处理：要么整条链判中断，要么重新派发。用户看到的是模型把同一份研究、同一份测试又做了一遍，时间与额度都白花。
- **轮次会归零**。回流第二轮被杀掉，重启后即使能继续，也常常从「第 1 轮」重新计数；轮次上限本来是用来「超过就升级人工」的安全阀，一旦归零，安全阀就失效了。
- **ACP 恢复方言没有被区分**。DSH 内置 acp app 只广告 `session/resume`（**不回放**），第三方 `dsh-acp-server` 广告 `loadSession: true`（`session/load`，**回放/追加**）。今天适配器里的 `resumeOrCreate` 永远走「新建会话」这一条路：宿主明明能把会话接回来，用户看到的却是「会话已创建 sess-新号」，模型从零开始，已完成的上下文消失。
- **「会话进程死了」与「会话只是慢」被当成同一件事**。两者在界面上都表现为「会话 执行中 · 已运行 Nm · 无新事件」。进程死了应该重建会话并在当前轮重试；只是慢则不该重建，应该等节点超时或让用户决定。今天没有这两种不同的提示，也没有两种不同的处置。
- **人工节点等我一晚上，重启后没有人继续等我**。基线要求 `human` 节点在恢复后保持 `running`（等待人工）；今天 daemon 重启会把整个实例判中断，人工节点上的待办随之消失。
- **交接包投出去但对方没接，重启后一直「已投递」**。基线要求 `delivered` 未 `accepted` 的交接包恢复为 `pending` 并重投；今天没有这条恢复规则，连接线就一直停在「已投递」，既不重投也不告警。
- **每个任务都新会话，角色记不住上一轮**。规划要求角色可配置「任务内复用会话」或「每任务新会话」，现在只有「每任务新会话」一种行为，用户想复用没有开关，想确认当前用的是哪一种也没有地方看。
- **「检查点」只存在于文档里**。数据布局写了 `state/` 含检查点，但今天没有任何一份可恢复的检查点；写失败了也不会告诉用户，崩溃后更无法判断「最后一次确认到哪」。

**不解决会怎样**：I1.9 的三层日志与健康度要回答「这个实例为什么失败」，没有恢复记录就只能看到「已中断」；I1.10a 的角色流程图要展示「重启后仍在运行」的实例，没有恢复能力就只能展示一片中断；I1.11 的人工干预队列要接住「会话崩溃」「运行慢」「交接重投」三类待办，没有区分就全部混成一条。再往后每加一个宿主、每加一种失败，都要重新猜一次「上次到底做到哪」。

### 1.3 范围

**范围内**

1. **实例管理器完整：状态机**。把基线 9 态完整落到实例管理器：`blocked` / `ready` / `assigned` / `running` / `review` / `done` / `failed` / `escalated` / `cancelled`；9 个位置全部对用户可见（`blocked` / `ready` 同显「待执行」，`assigned` 显「已分配」），全部经 `orchestrator.transit()` 校验。代码侧 `NODE_STATES` 维持 **7 项**（`pending` / `running` / `review` / `done` / `failed` / `cancelled` / `escalated`），9 态由「7 项 + 精确位置投影」承载，映射见附录 D-2；看板仍是基线的 7 列（`index.md:166`），不新增列。
2. **实例管理器完整：轮次计数**。轮次随节点持久化，恢复时从检查点/实例记录恢复，**绝不重置**；`orch instance graph` 的节点行继续显示 `第 N 轮`。
3. **实例管理器完整：检查点**。新增一份可恢复的检查点，记录「最后一次确认到哪」；说明何时写、写什么、恢复怎么用、写失败用户看到什么（见 §2.2）。
4. **ACP 会话恢复方言**：`session/resume`（不回放）、`session/load`（回放/追加）、`resumeOrCreate` 回退链 `resume → load → new`；每次回退可见。
5. **崩溃恢复**：daemon 重启后从检查点恢复并继续推进；已完成节点不重放；轮次不重置；`suspended` 保持挂起；`escalated` / `failed` 不自动重跑；显式 `core stop` 仍按「已中断」处理。
6. **角色实例恢复**：`busy` 且会话不可恢复时降级为 `available`，并重新调度其服务节点；会话可恢复时保持 `busy`；角色实例仍是派生视图。
7. **连接线聚合恢复**：`delivered` 未 `accepted` 的交接包恢复为 `pending` 并重投；`accepted` / `consumed` / `rejected` / `expired` 不改；连接线聚合按既有优先级重算。
8. **特殊节点恢复**：`human` 节点保持 `running`（等待人工），不重派、不跳过；`escalate` 保持 `escalated`；`failed` 保持 `failed`；`suspended` 内全部保持。
9. **会话失败区分**：ACP 会话进程崩溃（重建会话、当前轮重试、失败则升级）与会话运行慢（不重建、提示、按节点超时处理）给出两类不同提示与不同处置。
10. **会话复用策略**：角色可配置 `reuse`（任务内复用空闲会话）或 `fresh`（每任务新会话）；默认 `fresh`，与今天的行为一致；配置可见、恢复时可判断。
11. **用户可见输出**：`orch status` / `orch instance status` / `orch instance log` / `orch instance graph` / `orch role show` / `orch handoff list` 上新增的恢复、检查点、崩溃、运行慢、复用文案，全部进附录 A。
12. **兼容与纯净**：非恢复路径的既有输出逐字不变；零新增运行时依赖；`src/core` / `src/daemon` 的 31 词禁词扫描 exit 0；不新增 CLI 命令。

#### 补充契约（C-01 ~ C-18）

| 编号 | 契约 |
|---|---|
| **C-01** | 节点精确位置只在 `pending` / `running` 上使用 `phase`；其余状态 `phase` 必须缺省。`blocked` / `ready` 都显示「待执行」，`assigned` 显示「已分配」，`running` 显示「执行中」；不带 `phase` 的旧节点按 `state` 直接显示 |
| **C-02** | `transit()` 收到 `phase` 时必须在写盘前校验：`blocked→ready`、`ready→assigned`、`assigned→running`、`running→assigned`、`assigned→cancelled`、`assigned→escalated`；其余组合拒绝并落一条 `rejected / illegal_transition` 事件。无 `phase` 的调用完全走既有 7 项状态表 |

| **C-04** | 检查点不含提示词全文、模型输出、凭据、完整对话历史；只含恢复所需的进度、会话标识、交接标识、锁定图快照与引用 |

| **C-06** | 恢复后必须写一条「恢复摘要」事件与对应检查点；摘要含检查点时间、跳过的已完成节点数、恢复后的轮次。重复启动不得重复写第二份摘要 |

| **C-10** | 恢复失败（无可用方言、宿主不可达、锁定图缺失）时，实例按 `interrupted` 落盘，并写一条可见原因；不得静默假装仍在运行 |
| **C-11** | 角色实例与连接线聚合仍是派生视图，不写 `state.json`；恢复后由核心按节点/会话/交接包重新计算。角色 `busy` 且其全部会话不可恢复 → `available`；连接线按交接包优先级重算。角色「不可用」（`unavailable`）只由「会话崩溃且重建失败 / 宿主不可达」产生，恢复后按派生规则回到「可用」或「服务中」（见 C-18） |

| **C-13** | 崩溃重建每次派发最多一次；重建成功后重发当前轮提示；再次崩溃直接升级人工，不进入无限重建。重建不增加轮次 |
| **C-14** | 运行慢不重建会话；节点声明了 `timeout` 时才在超时后按 `failed_reason: timeout` 处理（该字段语义见基线 `index.md:164`，当前代码尚无写入，**本迭代新增落盘**）；未声明时只提示并继续等待。慢阈值默认 10 分钟，测试可用 `MAESTRO_TEST_SLOW_MS` 缩短 |
| **C-15** | 会话复用 `reuse` 只在同一实例、同一角色、同一宿主、**会话状态为 `idle`**、且未被其他节点占用时复用（角色状态 ∈ {`available`, `cooldown`} 只用于筛选候选角色，不当作会话态）；`fresh` 每次新建。跨实例、跨宿主不复用 |
| **C-16** | I1.7 未合入前，恢复不得读取 worktree、不得推断产物隔离目录；`artifactRefs` 原样保留。I1.7 合入后，本迭代全部 AC 必须重跑，并由 I1.7 的产物语义复核恢复规则 |

### 2.2 实例管理器完整：状态机、轮次与检查点

- **使用角色**：运行长任务的编排者、负责值守的同学。
- **使用场景**：一条编码闭环跑到第二轮回流，daemon 因机器重启或强杀而消失；或者我主动 `orch core stop` 后想确认实例到底停在哪。
- **用户操作**：正常情况下我不需要做任何事；重启后我执行 `orch status`、`orch status --instance <实例>`、`orch instance log <实例>` 或 `orch instance graph <实例>` 查看。
- **预期效果**：
  - **状态机（9 个位置）**：节点仍在原来的位置。已完成的节点显示「已完成」；正在等待重新派发的节点显示「已分配」，并有一行说明「等待重新分配会话」；正在执行的节点显示「执行中」；等待校验的节点显示「待校验」；人工节点显示「执行中 · 等待人工」。重启前就处于「已分配」的节点仍是「已分配」并会被重新派发；重启前处于「待执行」的节点仍是「待执行」，依赖关系不变。
  - **轮次**：`orch instance graph` 的节点行仍显示 `第 2 轮`；`orch status --instance` 的恢复行显示 `轮次 2/3`。轮次不会因为重启回到 1。
  - **检查点何时写**：每一件「已经确认的进展」完成后立即写——节点被分配、节点开始执行、节点产出核对通过、节点状态改变、轮次 +1、交接包状态改变、实例暂停/恢复/挂起/完成。用户不需要手动保存。
  - **检查点写什么（用户语言）**：哪几个节点已经做完、每个节点走到第几轮、当前会话是谁、哪些交接还没落地、实例是挂着还是暂停、这次运行用的是哪张图。它不保存对话全文、模型输出或凭据。
  - **恢复时怎么用**：重启后先看实例记录；检查点用来补「这次运行用的是哪张图」和「上次确认到哪」。恢复摘要会告诉我「从 10:30:00 的检查点恢复，跳过 1 个已完成节点，轮次 2/3」。已完成的节点不会重跑。
  - **写失败时看到什么**：如果检查点写不进去，`orch run` 会打印一行 `检查点写入失败：<原因>；本次进展已保存，崩溃恢复可能回退到上一个检查点`，当前运行继续。之后若真的崩溃，重启时如果没有可用检查点，会提示「按实例记录恢复（可能重跑当前轮）」。
- **异常情况**：
  - 实例记录本身读不出来：维持既有的「状态不可读，已备份」，不自动重建、不静默清零。
  - 没有检查点且模板也认不出来：实例显示「已中断」，并提示「旧实例无检查点：已中断（如需继续请新建实例）」。
  - 恢复过程失败（宿主不可达、锁定图缺失）：实例显示「已中断」，日志里有一行 `恢复失败：<原因>；实例已中断（可执行 orch instance log 查看详情）`。
- **边界说明**：显式 `orch core stop` 仍然把实例标记为「已中断」，重启后不会自动恢复；已挂起的实例保持挂起，不按恢复规则重派；已取消 / 已完成 / 失败的实例不恢复。

### 2.3 ACP 恢复方言：resume、load、new

- **使用角色**：使用 DSH 或第三方 ACP 宿主的同学。
- **使用场景**：daemon 重启后，某个会话其实还能接回来；或者宿主只支持「新建」。
- **用户操作**：我不需要选择方言；恢复时自动判断。恢复后我用 `orch instance log` 看它用了哪一种。
- **预期效果**：
  - **`session/resume`（不回放）**：宿主广告支持 `resume` 时优先走它。日志出现 `恢复：会话 sess-003 · session/resume（不回放）`。它表示会话接回来了，但宿主不会把上一轮对话重新放一遍；如果会话最后是在执行中，就等它继续；如果已经空闲，只重发当前轮一次。
  - **`session/load`（回放/追加）**：宿主广告支持 `load` 时走它。日志出现 `恢复：会话 sess-003 · session/load（回放）`。它表示宿主会把历史回放/追加回来；我不会再投递一遍已完成的历史。
  - **`session/new`（新建）**：宿主两种都不支持，或角色策略是 `fresh` 时走它。日志出现 `恢复：会话 sess-005 · session/new（新建）`；只重发当前轮，已完成节点不动。
  - **回退链**：`resume` 失败 → 尝试 `load`（如果宿主广告）→ 仍失败 → `new`。每一次回退都有一行可见说明，例如 `恢复：session/resume 失败，回退 session/load（回放）`。绝不静默降级。
- **异常情况**：
  - 三种方言都失败：节点显示「已分配」，角色从「服务中」降为「可用」，未接受的交接包从「已投递」变「待投递」；实例不假装还在运行。
  - 方言成功但会话没有后续事件：按 §2.8 的「运行慢」提示，不重复重建。
- **边界说明**：已完成节点永不重发；`load` 不会导致我手动重发历史；`resume` 不会假设宿主记得上一轮；`stopReason` 不用来判断恢复成功或失败。

### 2.4 崩溃恢复：daemon 重启后接着跑

- **使用角色**：机器重启、daemon 被强杀后的同学。
- **使用场景**：编码闭环回流复测：开发第二轮已完成、测试复测执行中时 daemon 被强杀；我重新执行 `orch status`。
- **用户操作**：重启 daemon（多数情况下执行任意 `orch` 命令会自动拉起），然后看 `orch status` 与 `orch instance log`。
- **预期效果**：
  - 实例仍显示「运行中」，不是「已中断」。
  - `orch status --instance` 多一行：`恢复：检查点 10:30:00 · 跳过 1 个已完成节点 · 轮次 2/3`。
  - `orch instance log` 里能看到跳过哪些已完成节点、当前会话用的是哪种方言、哪些角色/交接包被降级。
  - 后续推进继续；已完成的节点没有新的派发记录。
- **异常情况**：
  - 恢复失败：实例变「已中断」，日志有 `恢复失败：<原因>；实例已中断（可执行 orch instance log 查看详情）`。
  - 没有检查点但实例记录完整、模板是内建的三张图之一：按实例记录恢复，日志提示「按实例记录恢复（可能重跑当前轮）」。
  - 重复重启：第二次启动不再重复推进，也不重复写恢复摘要。
- **边界说明**：已挂起的实例不自动恢复；显式 `core stop` 产生的「已中断」不自动恢复；旧格式实例不自动恢复；恢复不改变已取消 / 已完成 / 失败 的终态。

### 2.5 角色实例恢复：从「服务中」到「可用」

- **使用角色**：看角色状态、判断还能不能接新任务的编排者。
- **使用场景**：daemon 重启后，某个角色的会话接不回来。
- **用户操作**：执行 `orch role show <角色> --instance <实例>`，或看 `orch instance log`。
- **预期效果**：
  - 角色原本是「服务中」，会话不可恢复：显示 `可用 · 活跃会话 0/1 · 服务节点 —`，日志出现 `恢复：角色 开发 · 服务中 → 可用（会话不可恢复）`。
  - 该角色服务的节点会被重新调度；重新派发后角色回到「服务中」。
  - 会话可恢复：角色保持「服务中」，活跃会话数不变。
  - 原本是「可用」「冷却中」「未参与」的角色不受影响。
  - 会话崩溃且重建失败、或宿主不可达时，角色显示「不可用」；会话接回或重建成功后，恢复按派生规则回到「可用」，重新派发后回到「服务中」。
- **异常情况**：如果角色在恢复后既没有可用会话、也没有可调度节点，保持「可用」，不显示「服务中」。
- **边界说明**：角色实例是派生视图，不单独持久化；不新增「恢复中」这一角色状态；`retired` 仍只在实例结束时出现。

### 2.6 连接线聚合恢复：已投递未接受，改回待投递并重投

- **使用角色**：看交接进度、等对方接手的同学。
- **使用场景**：daemon 重启时，某张交接包已经投出去，但目标会话还没接受。
- **用户操作**：执行 `orch handoff list --instance <实例>`、`orch instance graph <实例>` 或 `orch instance log`。
- **预期效果**：
  - 交接包行显示「待投递」；实例状态块的交接包行显示 `待投递 · 重试 n/2`；日志出现 `恢复：连接线 测试→开发（回流） 已投递 → 待投递（重投）`。
  - 「已构造」但还没投递的交接包，恢复后继续投递：日志出现 `恢复：交接包 HO-002 已构造 → 继续投递`；不重新构造、不换包号、不把重试次数清零。
  - 随后自动重投；重投成功后回到「已投递」，目标首个事件后变「已接受」。
  - `orch instance graph` 在恢复实例顶部多一行连接线聚合，例如 `连接线：测试→开发（回流） 待投递（重投中）`。
- **异常情况**：重投连续失败仍按既有规则进入 `待投递` 计数，最终 `已过期` 并升级人工；用户看到的是「已过期」而不是永远「已投递」。
- **边界说明**：已接受的交接包不重投；已完成 / 已拒绝 / 已过期的交接包不改；连接线聚合不单独持久化，按交接包状态重算。

### 2.7 特殊节点恢复：人工节点继续等我

- **使用角色**：需要在人工节点上点「通过 / 驳回」的同学。
- **使用场景**：实例停在人工节点等我一晚上；daemon 重启。
- **用户操作**：重启后执行 `orch instance status` / `orch instance graph` / `orch instance log`。
- **预期效果**：
  - 人工节点仍显示「执行中 · 等待人工」，不会被判中断、不会被跳过、不会自动重派给角色。
  - 日志出现 `恢复：人工节点 T-004 保持等待人工（不重派）`。
  - 升级节点保持「已升级」；失败节点保持「失败」；挂起实例里的所有节点保持原状。
- **异常情况**：人工节点如果同时缺少人工任务记录，仍保持「执行中 · 等待人工」，并在日志里点名节点；不自动生成新的升级。
- **边界说明**：`subworkflow` 在恢复中作为不透明节点保留状态，不展开内部节点；子工作流内部的恢复留后续迭代。

### 2.8 会话失败区分：进程崩溃 vs 运行慢

- **使用角色**：看到「会话 执行中 · 已运行 Nm · 无新事件」的同学。
- **使用场景**：一次派发后，会话进程退出；或者会话进程还活着但一直没有新事件。
- **用户操作**：看 `orch run` 的滚动输出和 `orch instance log`。
- **预期效果**：
  - **会话进程崩溃**：出现 `会话进程已退出：正在重建会话（节点 T-003 · 轮次 2/3）`；重建成功出现 `会话已重建 sess-005（节点 T-003 · 轮次 2/3）`；节点继续当前轮，轮次不增加。重建失败出现 `会话重建失败：已升级人工（节点 T-003 · 轮次 2/3）`，实例挂起等人工。
  - **会话运行慢**：出现 `会话无进展：判定为运行慢，不重建会话（节点 T-003 · 已等待 10m）`；会话进程不重建，节点继续等待。如果节点声明了超时，超时后出现 `节点 T-003 超时：按运行慢处理，已升级人工（节点 T-003 · 轮次 2/3）`；没有声明超时则继续等待，不擅自失败。
- **异常情况**：同一次派发最多重建一次；重建后的会话再次崩溃，直接升级人工，不再重建。运行慢不会触发重建；崩溃不会只提示不处理。
- **边界说明**：`stopReason` 不参与判定；运行慢的「无新事件」提示沿用既有会话行，不新增心跳帧；两类提示不会同时出现在同一次处置里。会话升级人工时，会话指示器沿用基线既有的「已升级」（红色圆点），随节点「已升级」派生；本迭代不新增会话状态取值、不新增 CLI 输出。

### 2.9 会话复用策略：reuse 与 fresh

- **使用角色**：角色作者、想让同一个角色跨轮次保留上下文的同学。
- **使用场景**：编码闭环里开发角色第二轮修改；或者每次任务都想从干净会话开始。
- **用户操作**：在角色文件里写 `session_policy: reuse` 或 `session_policy: fresh`；用 `orch role show <角色>` 确认；用 `orch instance log` 看本次派发是复用还是新建。
- **预期效果**：
  - `reuse`：同一实例、同一角色、同一宿主，且有「空闲」的会话、该角色处于「可用」或「冷却中」时，下一轮/下一个节点复用它；日志出现 `会话 复用 sess-003（角色 developer）`。
  - `fresh`：每次派发新建会话；这是默认行为，既有三张内建图不受影响。
  - `orch role show` 在角色显式声明时多一行：`  会话复用：复用（reuse）` 或 `  会话复用：每任务新会话（fresh）`；未声明时不显示，保持既有输出。
- **异常情况**：`reuse` 但会话已崩溃 → 按 §2.8 重建或升级；`reuse` 但没有空闲会话 → 新建并继续。
- **边界说明**：不跨实例复用、不跨宿主复用、不复用正在服务其他节点的会话；不改变 `max_concurrent_sessions` 的派发拦截（仍未实现）。

### 2.10 功能之间的衔接

一次完整的用户旅程：

1. 我用编码闭环发起实例，跑到回流复测：开发第二轮已完成、测试正在复测（`T-001 开发 · 已完成 · 第 2 轮`、`T-002 测试 · 执行中 · 第 2 轮`）。
2. daemon 在这个时刻被强杀。我重新执行 `orch status`，daemon 自动拉起并恢复。
3. `orch status --instance` 多一行 `恢复：检查点 10:30:00 · 跳过 1 个已完成节点 · 轮次 2/3`；`orch instance log` 显示 `session/resume（不回放）` 或 `session/new（新建）`。
4. 已完成的开发节点没有新的派发记录；测试复测从原位置继续；上一轮「失败」的测试节点不会被当成「已完成」重跑。换到任务闭环（研究、撰写已完成，审核执行中）同理：两个已完成节点不重跑，审核继续。
5. 回流里的交接包重启后回到「待投递」并重投；若是「已构造」还没投递的包，恢复后直接继续投递；重投成功后回到「已投递」，目标首个事件后「已接受」。
6. 如果开发会话进程在中途退出，我看到「正在重建会话」；重建失败则「已升级人工」，实例挂起等我处理，角色显示「不可用」。如果只是慢，我看到「判定为运行慢，不重建会话」，节点继续等超时。
7. 如果恢复本身失败（宿主不可达、锁定图缺失），我看到实例「已中断」和一行原因；如果重投一直失败，交接包最终「已过期」并进入升级，不会永远停在「已投递」。
8. 如果实例停在人工节点，我重启后仍看到「执行中 · 等待人工」，不会被冲掉；如果角色会话接不回来，`orch role show` 显示「可用 · 活跃会话 0/1」，重新派发后回到「服务中」。
9. 整个过程里，已完成的节点没有重跑，轮次没有归零，连接线没有永远停在「已投递」。

### 2.11 用户可见的业务规则

| 编号 | 规则 |
|---|---|
| **BR-01** | 节点有 9 个精确位置：`blocked` / `ready` / `assigned` / `running` / `review` / `done` / `failed` / `escalated` / `cancelled`；用户看到 `blocked` / `ready` 都是「待执行」，`assigned` 是「已分配」，`running` 是「执行中」，其余不变 |
| **BR-02** | 任何节点位置变化都必须经过同一条状态迁移入口；不得由恢复、重投、复用等旁路直接改状态 |
| **BR-03** | 每一件可确认的进展完成后立即写检查点：节点分配、开始执行、产出核对通过、状态改变、轮次 +1、交接包状态改变、实例暂停/恢复/挂起/完成 |
| **BR-04** | 检查点记住：已完成节点、每个节点的轮次、当前会话、未落地的交接、实例是否挂起/暂停、本次运行使用的图；不记对话全文、模型输出与凭据 |
| **BR-05** | 恢复时实例记录优先；检查点补「锁定图」与「上次确认到哪」；两者不一致以实例记录为准并告警；实例记录不可读时维持既有「状态不可读」处理，不静默重建 |
| **BR-06** | 检查点写失败只提示、不停止推进；崩溃后允许回退到上一个检查点；提示文案见附录 A |
| **BR-07** | 轮次从检查点/实例记录恢复，绝不重置；重启后仍显示原来的 `第 N 轮` 与 `轮次 N/M` |
| **BR-08** | 恢复后不重放已完成节点；已完成的节点没有新的派发与提示 |
| **BR-09** | 只有 `running` / `created` 且有检查点（或可识别内建模板）的实例自动恢复；`suspended` 不恢复 |
| **BR-10** | 显式 `core stop` 产生的「已中断」不自动恢复；用户要重来只能新建实例 |
| **BR-11** | 旧实例无检查点且模板未知 → 保持「已中断」，提示新建实例，不猜测、不重写旧快照 |
| **BR-12** | 恢复失败 → 实例「已中断」并给出可见原因；不得静默假装仍在运行 |
| **BR-13** | 恢复是幂等的：重复启动不重复推进、不重复写恢复摘要 |
| **BR-14** | `review` 节点恢复只重新核对证据，不重放会话；核对通过则继续，不通过按既有失败/升级规则 |
| **BR-15** | `escalated` 节点恢复后保持「已升级」，不重派，不自动生成新升级 |
| **BR-16** | `failed`（`code-loop`）节点恢复后保持「失败」，不自动重跑，等待复测或升级 |
| **BR-17** | ACP 恢复方言顺序固定 `resume → load → new`；`fresh` 策略直接 `new` |
| **BR-18** | `session/resume` 不回放历史；调用方不得假设宿主记得上一轮，也不得重发已完成节点 |
| **BR-19** | `session/load` 回放/追加历史；调用方不得重复投递同一份已完成历史 |
| **BR-20** | `session/new` 是全新会话；只重发当前轮，已完成节点不动 |
| **BR-21** | 每一次方言回退都必须在日志里点名；不得静默降级 |
| **BR-22** | 三种方言都失败 → 节点「已分配」、角色「可用」、未接受交接「待投递」，按基线 §3.6 降级 |
| **BR-23** | DSH 内置 acp 只会 `resume`、不会 `load`；第三方 `dsh-acp-server` 会 `load`；适配器不得按宿主名分支 |
| **BR-24** | 角色 `busy` 且会话不可恢复 → `available`，并重新调度其服务节点 |
| **BR-25** | 角色 `busy` 且会话可恢复 → 保持 `busy`，活跃会话数不变 |
| **BR-26** | 角色 `available` / `cooldown` / `inactive` 不受恢复影响；不新增「恢复中」角色状态 |
| **BR-27** | 角色实例仍是派生视图，不写第二份真相；恢复后按会话重新计算 |
| **BR-28** | 交接包 `delivered` 未 `accepted` → 恢复为 `pending` 并重投 |
| **BR-29** | 已 `accepted` 的交接包不重投；保持「已接受」 |
| **BR-30** | `consumed` / `rejected` / `expired` 的交接包恢复后不改 |
| **BR-31** | 连接线聚合不单独持久化；恢复后按交接包优先级重算，并在恢复实例的图上可见 |
| **BR-32** | `human` 节点恢复后保持 `running`（等待人工），不重派、不跳过 |
| **BR-33** | `escalate` 节点恢复后保持 `escalated`，不重派 |
| **BR-34** | `failed` 节点恢复后保持 `failed`，不自动重跑 |
| **BR-35** | `suspended` 实例内所有节点保持原状，不按恢复规则重派、不重新核对 |
| **BR-36** | 会话进程崩溃与会话运行慢必须给两类不同提示，不得混用 |
| **BR-37** | 崩溃：每次派发最多重建一次，重建成功后重发当前轮；轮次不增加 |
| **BR-38** | 崩溃重建失败 → 升级人工，实例挂起等待处理 |
| **BR-39** | 运行慢：不重建会话，只提示；继续等待 |
| **BR-40** | 运行慢且节点声明了超时 → 超时后按 `failed_reason: timeout` 记为失败并升级人工（用户看到「已升级」）；未声明超时 → 继续等待，不擅自失败 |
| **BR-41** | 角色可配置 `reuse` / `fresh`；默认 `fresh`，与今天的行为一致 |
| **BR-42** | `reuse` 只复用同实例、同角色、同宿主、会话状态为 `idle` 的会话（角色处于「可用」或「冷却中」只用来判断候选角色）；`fresh` 每次新建 |
| **BR-43** | 会话复用不跨实例、不跨宿主；不复用正在服务其他节点的会话 |
| **BR-44** | 非恢复路径的既有输出逐字不变；恢复相关行只在发生恢复时追加 |
| **BR-45** | 零新增运行时依赖；`src/core` / `src/daemon` 的 31 词禁词扫描 exit 0 |
| **BR-46** | 不新增 CLI 命令；既有用法块保持 25 行，既有子命令参数不变 |
| **BR-47** | I1.7 未合入前不得依赖 worktree / 产物隔离；I1.7 合入后必须重跑本迭代全部 AC |
| **BR-48** | 真实宿主面验收必须在隔离 `DSH_HOME` + 复制凭据下进行；无法真实复现时判「阻塞」，不伪造成通过 |
| **BR-49** | 交接包「已构造」未投递时恢复后继续投递；不重新构造、不换包号、不重置重试次数 |
| **BR-50** | 会话崩溃且重建失败、或宿主不可达 → 角色显示「不可用」；恢复后接回或重建成功回到「可用」，重新派发后回到「服务中」 |
| **BR-51** | 交接包重投连续失败 → 最终「已过期」并升级人工，不会永远停在「已投递」 |
| **BR-52** | 同一次派发重建后再次崩溃 → 直接升级人工，不再重建 |
| **BR-53** | 恢复后原本「已分配」的节点保持「已分配」并重新派发；原本「待执行」的节点保持原位置，依赖关系不变 |
| **BR-54** | `subworkflow` 节点在恢复中保持不透明：不展开内部节点、不向内部派发 |

## 三、验收标准（用户视角）

### 3.1 功能验收标准（AC）

#### AC-01 九个节点位置在用户可见层对得上

- 场景类型：正常路径 ｜ 风险：P0 ｜ 引用：BR-01、BR-02
- **Given** 一个独立项目根、`NODE_ENV=test`；先用任务闭环跑到「研究、撰写已完成，审核待校验」（`MAESTRO_TEST_PAUSE=after_output:reviewer` 停住），再用 `MAESTRO_TEST_RECOVERY_HOLD=after_assign` 让恢复后的节点停在「已分配」
- **When** 我执行 `orch instance graph <实例>` 与 `orch status --instance <实例>`
- **Then** 已完成节点显示「已完成」；已分配节点显示「已分配」并带「等待重新分配会话」；执行中节点显示「执行中」；待校验节点显示「待校验」；`blocked` / `ready` 都显示「待执行」
- **机检：** `orch instance graph` 文本中 `T-xxx 开发 · 已分配` 出现 1 次；`orch status --instance` 的节点行含 `已分配`；`NODE_STATES` 仍是 **7 项**（回归断言），且 9 个位置投影齐全（新单测逐一覆盖）

#### AC-02 检查点随每一件进展推进

- 场景类型：夹具 ｜ 风险：P0 ｜ 引用：BR-03、BR-04
- **Given** 一个独立项目根，`NODE_ENV=test`，用编码闭环跑到测试节点产出核对通过
- **When** 我查看实例的检查点，再强杀 daemon 并重启
- **Then** 重启后的 `orch status --instance` 出现 `恢复：检查点 HH:MM:SS ...`，该时间不早于最后一次节点进展的日志时间
- **夹具：** `test/fixtures/recovery-driver.mjs --scenario checkpoint-advance`；每次进展后读取 `instances/<id>/state/checkpoint.json`，断言 `checkpointId` 单调递增、`rev` 与实例记录一致

#### AC-03 检查点内容足以恢复「做到哪」

- 场景类型：夹具 ｜ 风险：P0 ｜ 引用：BR-04、BR-05
- **Given** 编码闭环跑到回流复测：开发第二轮「已完成」、测试「执行中」（轮次 2/3），daemon 被强杀
- **When** 我重启并执行 `orch instance log`
- **Then** 日志显示跳过 1 个已完成节点、轮次 2/3；开发与测试的位置、轮次与崩溃前一致，测试从原位置继续复测
- **夹具：** 读取检查点，断言含 `instanceId` / `rev` / `checkpointId` / `graph` / `nodes` / `sessions` / `handoffs` / `paused` / `halted`；不含提示词全文、模型输出、凭据

#### AC-04 检查点写失败时用户看得到，运行不中断

- 场景类型：异常 ｜ 风险：P1 ｜ 引用：BR-06
- **Given** 一个独立项目根，`NODE_ENV=test`，注入 `MAESTRO_FAULT=checkpoint_write:fail`
- **When** 我发起编码闭环并跑到第一个节点完成
- **Then** `orch run` 输出出现 `检查点写入失败：<原因>；本次进展已保存，崩溃恢复可能回退到上一个检查点`，实例继续推进，最终退出码仍按原流程（完成 0 / 挂起 4 / 停止推进 5）
- **机检：** 日志中该提醒至少出现 1 次，且**每次运行最多 1 次**；`state.json` 仍有最新进展；不因检查点失败新增失败退出码

#### AC-05 检查点缺失但实例记录完整时按实例记录恢复

- 场景类型：异常 ｜ 风险：P1 ｜ 引用：BR-05、BR-09
- **Given** 一个独立项目根，编码闭环跑到第二轮，手动删除 `instances/<id>/state/checkpoint.json`，再强杀 daemon
- **When** 我重启并执行 `orch status --instance`
- **Then** 实例仍「运行中」，`orch instance log` 出现 `按实例记录恢复（可能重跑当前轮）`；已完成节点仍不重跑；模板是内建三图之一
- **夹具：** 删除检查点后重启；断言已完成节点 `session/prompt` 次数仍为 0，当前轮允许 1 次重发

#### AC-06 实例记录不可读时不从检查点静默重建

- 场景类型：异常 ｜ 风险：P0 ｜ 引用：BR-05、BR-12
- **Given** 一个独立项目根，实例记录被写成非法 JSON，检查点存在
- **When** 我执行 `orch status`
- **Then** 该实例显示「状态不可读」，并保留 `state.json.corrupt` 备份；不出现「运行中」，不自动用检查点覆盖原文件
- **机检：** `state.json` 原字节不变、`.corrupt` 存在；重启前后文件 `sha256` 相同；退出码按既有「状态不可读」口径

#### AC-07 重启后轮次不重置

- 场景类型：用户可见 ｜ 风险：P0 ｜ 引用：BR-07
- **Given** 编码闭环第二轮回流，开发节点轮次为 2/3，daemon 被强杀
- **When** 我重启并执行 `orch instance graph <实例>` 与 `orch status --instance <实例>`
- **Then** 开发节点行仍是 `第 2 轮`；`orch status --instance` 的恢复行是 `轮次 2/3`；不是 `第 1 轮` / `轮次 1/3`
- **机检：** `orch instance graph --format json` 的对应节点 `round === 2`；`maxRounds === 3`

#### AC-08 已完成节点不重放

- 场景类型：夹具 ｜ 风险：P0 ｜ 引用：BR-08
- **Given** 编码闭环回流复测：开发第二轮显示「已完成」（`round=2`），测试显示「执行中」（复测中）；daemon 在这个时刻被强杀
- **When** 我重启恢复并跑到实例结束
- **Then** 已完成开发节点没有新的派发；`orch instance log` 没有它的第二次派发记录；测试复测继续到结束；上一轮「失败」的测试节点没有被当成「已完成」重跑
- **夹具：** `test/fixtures/code-loop-driver.mjs --scenario retest-slow`（复测步 `delayMs=30000`），mock agent 的 `MAESTRO_MOCK_PROMPT_LOG` 中已完成开发节点的提示次数为 0；`node.dispatch` 事件中不含该节点。该场景实测中间态：`T-001 done round=2` / `T-002 running round=2`

#### AC-09 回流中途 kill daemon，重启后从检查点继续（规划验收句）

- 场景类型：用户可见 ｜ 风险：P0 ｜ 引用：BR-07、BR-08、BR-09、BR-12
- **Given** 一个独立项目根，编码闭环跑到回流复测（开发第二轮已完成、测试复测执行中），daemon 正在运行
- **When** 我用 `kill -9`（或 `taskkill //F //PID`）杀掉 `.orch/core.json` 里的 pid，再执行 `orch status`
- **Then** 实例显示「运行中」；`orch status --instance` 出现恢复行；已完成的开发节点没有重跑；测试继续复测；实例最终完成或按既有规则升级
- **夹具：** `test/fixtures/code-loop-driver.mjs --scenario retest-slow`；先等到 `T-001` 为 `done`、`T-002` 为 `running`（`round=2`），杀核心，再 `orch status` 拉起；断言恢复行、`skipped === 1`、已完成节点提示次数 0

#### AC-10 恢复摘要一行说清「从哪来、跳过多少、第几轮」

- 场景类型：用户可见 ｜ 风险：P1 ｜ 引用：BR-05、BR-09
- **Given** AC-09 的恢复完成
- **When** 我执行 `orch status --instance <实例>`
- **Then** 标准实例行之后多一行：`恢复：检查点 10:30:00 · 跳过 1 个已完成节点 · 轮次 2/3`（时间、数量、轮次按实际值）
- **机检：** 该行只出现 1 次；`orch instance graph --format text` 顶部也有同样的一行；非恢复实例不出现该行

#### AC-11 挂起实例重启后仍挂起

- 场景类型：边界 ｜ 风险：P0 ｜ 引用：BR-09、BR-35
- **Given** 一个实例因轮次超限已 `suspended`，节点 `running` / `review` 各一个
- **When** 我重启 daemon 并执行 `orch status --instance`
- **Then** 实例仍显示「已挂起」；节点仍显示原状态；没有恢复行、没有新的派发、没有重新核对
- **机检：** 重启前后 `orch instance graph --format json` 的 `state` 与节点状态逐项相同；`instance log` 没有新增 `node.dispatch` / `verification.*`

#### AC-12 升级节点重启后仍是已升级

- 场景类型：边界 ｜ 风险：P0 ｜ 引用：BR-15
- **Given** 编码闭环某节点已 `escalated`，实例 `suspended`
- **When** 我重启 daemon
- **Then** `orch status --instance` 仍显示「已升级」；没有重派；没有新的升级请求
- **机检：** `escalations` 数组中 `pending` 数量不变；`node.dispatch` 次数不变

#### AC-13 失败节点重启后不自动重跑

- 场景类型：边界 ｜ 风险：P0 ｜ 引用：BR-16
- **Given** 编码闭环测试节点判定失败（`failed_reason: verdict_fail`），实例等待复测
- **When** 我重启 daemon
- **Then** 节点仍显示「失败」；没有自动重跑；`orch status --instance` 仍给出既有下一步
- **机检：** 重启前后节点 `state === 'failed'`；`instance log` 没有新的 `node.dispatch`

#### AC-14 待校验节点恢复只重新核对，不重放会话

- 场景类型：夹具 ｜ 风险：P1 ｜ 引用：BR-14
- **Given** 一个任务闭环实例停在审核节点 `review`，证据文件存在；daemon 被强杀
- **When** 我重启 daemon
- **Then** 节点仍显示「待校验」，随后出现「重新核对」（`orch instance log` 行 `重新核对：{节点号} · 证据重新校验（不重放会话）`）并转为「已完成」；审核会话没有新的提示
- **夹具：** `task-loop` 场景 + `MAESTRO_TEST_PAUSE=after_output:reviewer`；mock prompt log 中审核节点恢复后提示次数为 0；`instance log` 含逐字短语 `重新核对：{节点号} · 证据重新校验（不重放会话）`（附录 A-3）

#### AC-15 旧实例无检查点且模板未知 → 已中断并提示新建

- 场景类型：边界 ｜ 风险：P1 ｜ 引用：BR-11
- **Given** 一个旧格式实例，没有检查点，模板名不在当前三张内建图里
- **When** 我重启 daemon
- **Then** 实例显示「已中断」；`orch instance log` 出现 `旧实例无检查点：已中断（如需继续请新建实例）`；不尝试恢复、不重写旧快照
- **机检：** 实例记录 `sha256` 不变；没有新增 `node.dispatch`；状态仍 `interrupted`

#### AC-16 显式 core stop 仍是已中断，不自动恢复

- 场景类型：回归 ｜ 风险：P0 ｜ 引用：BR-10
- **Given** 编码闭环运行中，我执行 `orch core stop`
- **When** 我再次执行 `orch status`
- **Then** 实例显示「已中断」；没有恢复行；没有自动继续
- **机检：** `core stop` 后状态 `interrupted`；再次 `status` 拉起核心后状态仍 `interrupted`；`instance log` 没有恢复摘要

#### AC-17 恢复失败时用户看到原因

- 场景类型：异常 ｜ 风险：P0 ｜ 引用：BR-12
- **Given** 一个实例有检查点，但恢复时宿主不可达（mock 进程无法拉起）
- **When** 我重启 daemon
- **Then** 实例显示「已中断」；`orch instance log` 出现 `恢复失败：<原因>；实例已中断（可执行 orch instance log 查看详情）`；不显示「运行中」
- **夹具：** `MAESTRO_MOCK_SPAWN_FAIL_ON_RECOVER=1`；断言状态 `interrupted` 且日志含 `恢复失败`

#### AC-18 恢复幂等：重复启动不重复推进

- 场景类型：夹具 ｜ 风险：P0 ｜ 引用：BR-13
- **Given** AC-09 的恢复已完成，实例在运行中
- **When** 我再强杀一次 daemon 并重启
- **Then** 已完成节点仍不重跑；恢复摘要不重复写第二份；节点派发次数只增加当前轮该有的次数
- **夹具：** 连续两次 `--kill-after`；统计 `recovery.summary` 事件数量为 1（同一实例同一代），已完成节点提示次数仍为 0

#### AC-19 resume 方言：广告 resume 时走不回放

### B.1 术语

| 术语 | 含义 | 易混对象 |
|---|---|---|
| 检查点 | 一份紧凑的「恢复信封」：锁定图、已完成节点、轮次、会话、未落地交接、挂起/暂停标记 | 不是第二份实例记录：实例记录仍是主真相 |
| 恢复 | daemon 重启后把 `running` / `created` 实例接回并继续推进 | 不是 `orch workflow resume`（那是用户对暂停实例的显式操作） |
| 恢复摘要 | 恢复时写的一条可见记录：检查点时间、跳过节点数、轮次 | 不是体检报告；不含完整事件回放 |
| 方言 | 宿主接回会话的方式：`session/resume`（不回放）、`session/load`（回放/追加）、`session/new`（新建） | 不是 transport：transport 是 stdio / HTTP+SSE |
| `resumeOrCreate` | 适配器的恢复入口：按 `resume → load → new` 回退 | 不是「先恢复再新建」的两次派发 |
| 已分配 | 节点已绑定会话但尚未开始执行；恢复后等待重新派发时出现 | 不是「待执行」：待执行还没有绑定会话 |
| 运行慢 | 会话进程仍存活，但超过慢阈值没有新事件 | 不是「崩溃」：崩溃是进程退出 |
| 崩溃重建 | 会话进程退出后，用同一角色策略重新建立会话并重试当前轮 | 不是「重跑节点」：轮次不增加，已完成节点不动 |
| 会话复用 | 同一实例、同一角色、同一宿主的空闲会话被下一次派发继续使用 | 不是「并发共享」：不复用正在服务其他节点的会话 |
| `session_policy` | 角色文件里的会话策略：`reuse` / `fresh` | 不是 `max_concurrent_sessions`：后者是并发上限，本迭代不拦截 |
| 锁定图 | 检查点里保存的一份运行时图快照，恢复按它继续 | 不是资产版本号：没有版本字段，只有图对象副本 |
| 角色实例恢复 | 按会话恢复结果重新计算角色状态（`busy` → `available` 等） | 不是持久化角色实例；角色实例仍是派生视图 |
| 连接线聚合恢复 | 按交接包状态重算连接线聚合，不单独持久化 | 不是交接包本身：交接包才是数据源 |

### D-2 节点九态 ↔ 7 项 + 位置投影（C-01 / C-02 的可执行版）

**9 态 ↔ 7 项映射**（`NODE_STATES` 实为 7 项，见 `src/core/state-machine.js`；本迭代不改这张表）：

| 基线 9 态 | 承载方式 | 用户可见词 |
|---|---|---|
| `blocked` | `state='pending'` + `phase='blocked'`（缺省同此） | 待执行 |
| `ready` | `state='pending'` + `phase='ready'` | 待执行 |
| `assigned` | `state='running'` + `phase='assigned'` | 已分配（+「等待重新分配会话」） |
| `running` | `state='running'` + `phase='running'`（缺省同此） | 执行中 |
| `review` | `state='review'` | 待校验 |
| `done` | `state='done'` | 已完成 |
| `failed` | `state='failed'` | 失败 |
| `escalated` | `state='escalated'` | 已升级 |
| `cancelled` | `state='cancelled'` | 已取消 |

9 个位置全部可达、全部经 `transit()` 的 `phase` 校验、全部有独立显示词（`blocked` / `ready` 共用「待执行」是基线原样，不算合并）。

```
state=pending   phase=blocked   -> 位置 blocked   显示 待执行
state=pending   phase=ready     -> 位置 ready     显示 待执行
state=pending   phase 缺省      -> 位置 blocked   显示 待执行（旧节点）
state=running   phase=assigned  -> 位置 assigned  显示 已分配
state=running   phase=running   -> 位置 running   显示 执行中
state=running   phase 缺省      -> 位置 running   显示 执行中（旧节点）
state=review                    -> 位置 review    显示 待校验
state=done                      -> 位置 done      显示 已完成
state=failed                    -> 位置 failed    显示 失败
state=escalated                 -> 位置 escalated 显示 已升级
state=cancelled                 -> 位置 cancelled 显示 已取消
```

`transit(instanceId,'node',to,{ phase, ... })` 的校验表：

```
blocked   -> ready
ready     -> assigned
assigned  -> running
running   -> assigned   （恢复时会话不可恢复）
assigned  -> cancelled
assigned  -> escalated
```

- 其余 `phase` 组合一律 `rejected / illegal_transition`，磁盘不动。
- `phase` 只允许在 `pending` / `running` 上出现；`review` / `done` / `failed` / `escalated` / `cancelled` 带 `phase` 视为非法。
- 位置变化与 `state` 变化必须在同一次 CAS 保存里完成；不得先写 `phase` 再写 `state`。
- 恢复不产生迁移：原本 `blocked` / `ready` / `assigned` 的节点直接保持原位置并重新入队，**不得为恢复新增自环迁移**（不写 `assigned→assigned` 之类的迁移边）。
- `snapshotOf()` 只读投影，不写回；`status.md` 仍按看板列词显示（`assigned` → 「执行中」），口径见 A-1 与 B-17；不改 `src/core/status-text.js` 的词表。

### D-4 ACP 方言（M-3 / C-07 ~ C-09）

能力归一化：

```
sessionCapabilities = initialize.agentCapabilities.sessionCapabilities
                   ?? initialize.sessionCapabilities ?? {}
canResume = Boolean(sessionCapabilities.resume)
canLoad   = Boolean(sessionCapabilities.load || initialize.loadSession === true)
```

方法：

```
resumeSession(sessionId, { cwd, mcpServers = [] })
  -> request('session/resume', { sessionId, cwd, mcpServers })

loadSession(sessionId, { cwd, mcpServers = [] })
  -> request('session/load', { sessionId, cwd, mcpServers })

resumeOrCreate({ cwd, sessionId, policy = 'fresh', capabilities })
  policy === 'fresh' -> newSession({cwd}) -> {restored:false, dialect:'new'}
  policy === 'reuse':
    1. canResume -> resumeSession；成功 {restored:true, dialect:'resume'}；失败记录 attempts
    2. canLoad   -> loadSession；成功 {restored:true, dialect:'load'}；失败记录 attempts
    3. newSession；成功 {restored:false, dialect:'new'}
    4. 全失败 -> {ok:false, code:'SESSION_RESTORE_FAILED', attempts}
```

调用方恢复后动作（C-09）：

```
最后会话状态 ∈ {thinking, tool_running} -> 只等待，不 prompt
最后会话状态 ∈ {idle, waiting_dependency} -> 重发当前轮 prompt 一次
已完成节点 -> 永不 prompt
```

- `resume` / `load` 的请求超时沿用 `requestTimeoutMs`；失败按 `attempts` 记录，不吞错误。
- 每次回退写一条 `recovery.dialect` 事件，`detail` 含 `from` / `to` / `reason`。
- `session/load` 成功后不得再次投递已完成历史；`session/resume` 成功后不得假设历史存在。
- 不按 `hostId` / 宿主名分支；只看能力广告。
- **会话升级指示器显示来源**：会话升级人工时显示的「已升级」（红色圆点）是基线 §3.2 会话 6 态中 `escalated` 的既有输出（`index.md:181`「已升级，等待人工 / 红色圆点」、`:192`「核心生成 escalation」），随节点「已升级」派生；本迭代沿用该既有显示，不新增会话状态取值、不新增 CLI 输出，也不在附录 A-3 登记（属既有输出，非本迭代新增/变更文案），避免验收方误判为新增文案。

### D-5 启动恢复（M-4 / C-05 ~ C-06、C-10 ~ C-11）

```
reconcileOnBoot(generation):
  for each readable v2 instance:
    skip terminal / suspended / CORE_IMMUTABLE
    skip coreGeneration === current
    if state ∈ {running, created}:
      checkpoint = loadCheckpoint(id)
      stateDoc   = load(id)
      if stateDoc not readable -> leave corrupt path; continue
      if checkpoint missing:
         if template ∈ builtin -> proceed with record + warn "按实例记录恢复（可能重跑当前轮）"
         else -> markInterrupted('core.gone') + event "旧实例无检查点..."
      else:
         recover(id, stateDoc, checkpoint)
```

`recover()` 顺序：

1. 选图：`checkpoint.graph` 优先；缺省用 `template` 解析内建图；两者都没有 → `markInterrupted('RECOVERY_NO_GRAPH')` + 可见原因。
2. 节点对账：`done` 跳过；`review` 重新核对；`running` 尝试会话（不可恢复 → `running -> assigned`）；原本 `assigned` 的保持 `phase='assigned'` 并直接重新调度（不新建迁移）；`pending` 保持原 `phase`（`blocked` / `ready` 都不动、依赖不变）；`human` / `escalate` / `failed` / `cancelled` 保持。
3. 会话对账：按 D-4 方言；不可恢复 → `running -> assigned`；角色 `busy` → `available`（派生），崩溃且重建失败 / 宿主不可达 → `unavailable`；交接 `delivered` 未 `accepted` → `pending`（`deliveryAttempts` 保留），交接 `created` → 继续投递（不重构造）。
4. 写恢复事件（摘要、方言、角色、连接线、人工节点），写检查点，置 `recoveredAt` / `coreGeneration`。
5. 从 `assigned` / `ready` 节点继续调度；已完成节点不进入派发队列。
6. 任一致命错误 → `interrupted` + `恢复失败` 事件；不假装运行。

- `interruptAll()`（`core stop`）不改；`core stop` 产生的 `interrupted` 不被 `reconcileOnBoot` 重新拉起。
- `core.ping` 的既有字段不改；启动日志新增 `CORE_BOOT_RECOVER`（`recovered` / `interrupted` 列表），不进入用户命令输出。

### D-6 角色实例与连接线恢复（C-11）

- 角色实例不落盘；恢复后按 `role_to_sessions` 重算：
  - 角色全部会话不可恢复 → `available`；有可恢复会话 → `busy`；会话崩溃且重建失败 / 宿主不可达 → `unavailable`；无会话且无服务节点 → `available` / `cooldown`（沿用 I1.5 派生规则）。`unavailable` 不是新增枚举，取 `labels.js` 既有词「不可用」。
  - 降级写一条 `recovery.role` 事件；`orch role show` 读派生视图。
- 连接线不落盘；恢复后按交接包优先级重算：`rejected > expired > pending > delivered > accepted > consumed > not_started`。
- 交接包 `delivered` 且 `acceptedAt` 为空 → `transit('handoff','pending')`，保留 `deliveryAttempts`，写 `pendingAt`，再走既有 `deliverWithRetry`。
- 交接包 `created`（已构造未投递）→ 不重新构造、不改 `handoffId`、不重置 `deliveryAttempts`，直接走 `deliverWithRetry` 并写 `恢复：交接包 {包号} 已构造 → 继续投递`。
- 重投 3 次仍失败 → 既有 `expired` + `escalateDeliveryFailure`，不新增重试次数、不新增原因码。
- `accepted` / `consumed` / `rejected` / `expired` 不进入重投。

### D-7 特殊节点恢复（C-11 的补充）

- `nodeType === 'human'`：保持 `state === 'running'`，不创建会话、不派发；写 `recovery.human` 事件；`orch instance graph` 行追加 ` · 等待人工`。
- `nodeType === 'escalate'`：保持 `escalated`，不新建升级。
- `failed`（`code-loop`）：保持 `failed`，不自动复测。
- `suspended`：所有节点保持原状态，不进入 D-5 的节点对账。
- `subworkflow`：作为不透明节点保持 `state` / `phase`；不展开内部节点、不向其派发。

### D-8 崩溃与运行慢（C-12 ~ C-14）

- **崩溃判据**：会话已建立后，transport `onExit` 或 `prompt` 返回 `DSH_SPAWN_FAILED` / `IPC_CLOSED`。`stopReason` 不参与。
- **崩溃处置**：
  1. 写 `session.crash` 事件 + 可见行。
  2. 按角色策略重建：`fresh` → `newSession`；`reuse` → `resumeOrCreate`（方言链）。
  3. 重建成功 → 重发当前轮 prompt 一次；轮次不变。
  4. 重建失败 → `escalated`（`reason: session_crash`），实例 `suspended`；角色按 C-18 显示「不可用」；不再重建。
- **运行慢判据**：会话 `thinking` / `tool_running`，进程存活，距 `lastEventAt` 超过 `SLOW_MS`（默认 10 分钟；`MAESTRO_TEST_SLOW_MS` 可缩短）；既有 `STALL_MS = 10s` 只用于显示「无新事件」，不用于失败判定。
- **运行慢处置**：写 `session.slow` 事件一次；不重建；若节点声明 `timeout`（秒）且已超过，则写 `failed_reason: timeout`（**本迭代新增的落盘字段**，语义见基线 `index.md:164`，当前代码尚无该字段）并升级人工（节点终态 `escalated`）；未声明则继续等待。
- **图注入口**：`MAESTRO_TEST_GRAPH=<绝对路径>` 只在 `NODE_ENV=test` 下替换内建图，用于给节点声明 `timeout`；生产路径不读，CLI 的 `--template` 仍只接受三张内建图。
- 同一派发崩溃重建最多 1 次；重建后再次崩溃直接升级（`MAESTRO_MOCK_CRASH=twice` 可复现），`session/new` 不再增加、轮次不变。

### D-13 会话复用（M-5 / C-15）

- 角色文件可选键 `session_policy`，取值 `reuse` / `fresh`，缺省 `fresh`；加入 `ROLE_OPTIONAL_KEYS`、`ROLE_KEY_ORDER`（放在 `max_concurrent_sessions` 之后）、`ROLE_ALIASES`（`sessionPolicy`）、`DERIVE_INHERIT_KEYS`、`EDITABLE_KEYS`；`PROTECTED_KEYS` 不含它。
- `checkRoleShape` 校验取值；非法值报 `ROLE_SESSION_POLICY_INVALID`，明细含原值，文案见 A-10；不改变既有必填键与既有原因码。
- `role show` 仅在源对象显式出现 `session_policy` 时输出 A-5 的行；未声明不输出。**加载器不得把缺省 `fresh` 注入角色对象用于渲染**；缺省值只在派发选择时生效。`role list` / `role validate` 不新增行。
- `role create --from` 继承该键；`role edit --set session_policy=reuse|fresh` 可改；`--unset session_policy` 回到缺省 `fresh`。
- 派发选择：
  - `fresh` → 每次 `newSession`，与今天一致。
  - `reuse` → 在同一实例、同一 `roleId`、同一 `hostId` 的会话中，找 **`state === 'idle'`** 且 `servingNodeId` 为空或等于当前节点的会话（角色 `status ∈ {available, cooldown}` 只用于判断该角色是否有候选资格）；找到则复用并写 `会话 复用 {id}（角色 {中文名}）`；否则新建。
  - 不复用跨实例、跨宿主、正在服务其他节点的会话；不改变 `max_concurrent_sessions` 的派发拦截（仍未实现）。
- 恢复时：`fresh` 直接 `new`；`reuse` 按 D-4 方言链；复用失败退回 `new` 并写回退行。
