## 一、背景与问题

### 1.1 现状与问题

我是这个工具的唯一使用者，也是唯一编排者。现在要把一件事交给 DSH 做，流程是这样的：开一个终端、`cd` 到工作目录、敲 `dsh`、等它想、看它输出、自己判断有没有做完、自己去翻产物落在哪。

一件事还能忍。一旦有两件事要同时推进，就开始失控：

- **不知道哪个会话在干活**。两个终端窗口，一个在跑、一个卡在等确认，我从标题栏看不出来。
- **任务之间靠手工搬上下文**。上一个任务写出来的东西，我得自己复制路径、描述要求，再贴给下一个。
- **关掉终端就等于失忆**。重启之后刚才跑到哪一步、产物在哪、哪一步失败了，全靠回忆。
- **失败只有一句话**。`error` 或者干脆没输出，我得自己去猜是宿主挂了、会话没了、还是任务本身错了。

阶段零已经证明这条路技术上是通的：真实 DSH 上单轮 72ms 完成、5 个会话并发 149ms 且零串台、ACP 事件足以推断"目标已接受"（63ms）和"正在执行"。**这些时延是在包内确定性 mock LLM 上测的，只说明链路快，不代表真实模型的推理时延。** 但阶段零是**脚本级验证**——跑完就散，没有东西在持续记录状态，也没有东西替我做"东西交给谁了、对方接没接、做完没有"的判断。

**不解决会怎样**：后面每一个工作流（编码闭环 I1.2、非编码闭环 I1.3）都建立在"核心能可靠驱动会话、并且知道现在是什么状态"之上。这一步不稳，后面加角色只是把手工拼装变成更复杂的手工拼装。

### 1.2 目标与成功衡量

| # | 指标 | 目标值 | 怎么量 |
|---|---|---|---|
| 1 | 从敲下命令到看见"执行中"（热启动） | ≤ 5 秒；冷启动 ≤ 30 秒，单独记录 | 命令输出时间戳，10 次取最大 |
| 2 | 跑完一个单节点任务的人工介入 | 1 条命令发起、0 次手工操作 DSH 终端、0 次手工复制路径 | 人工计数 |
| 3 | 节点 / 会话 / 交接包三层状态与真实执行的一致率 | 抽查 20 次，状态变化 1 秒内反映，错标 0 次 | 对照 ACP 事件原始记录核对 |
| 4 | 连续 10 次任务 + 1 次强杀重开 | 三层状态 + 事件记录 4 项 100% 可查，重复执行 0 次 | 逐条核对状态记录 |

### 1.3 范围

**范围内（本次让用户获得的新能力）**

1. **最小命令集（4 个命令）**：`run` 发起、`status` 查状态与事件、`cancel` 取消、`core stop` 停核心。这是验收的唯一操作面；完整命令集与输出格式在 I1.4（见下方"关于最小命令集"）。
2. **常驻核心进程 + 本地通信**：核心作为独立进程运行，命令通过本地 socket 下指令、取状态。关掉命令窗口不影响正在跑的任务。
3. **ACP 适配器（stdio，只接 DSH）**：`initialize`、`session/new`、`session/prompt`、`subscribeEvents`，外加会话生命周期的 `session/cancel`、`closeSession`。transport 留出扩展位，本迭代只实现 stdio。
4. **会话状态归一化**：6 个会话状态全部有定义与映射；本迭代可观测 5 个（其中"等待审批"仅夹具可产生），`已升级` 只有定义、不显示。
5. **实例状态机（最小）+ 节点状态最小集**：实例 `已创建 / 运行中 / 已完成 / 失败 / 已取消 / 已中断`；节点 `待执行 / 执行中 / 待校验 / 已完成 / 失败 / 已取消`。三者都给出迁移表与非法迁移拒绝，见 2.2 / 2.4 / 2.5。
6. **交接包状态机**：7 个状态全部有定义、非法迁移被拒绝；本迭代可观测 5 个（`created / delivered / accepted / consumed / rejected`），`pending / expired` 只有定义。
7. **持久化基础**：每个实例一份状态快照 `state.json`（原子写）+ 一份追加式事件记录 `events.jsonl`。**不含**链式哈希、执行日志摘要、追踪 span（I1.9 / I1.12）。
8. **核心事件总线 + 确定性测试夹具**：状态变化统一从总线发出并落盘；夹具是可切换"请示审批 / 直接拒绝 / 延迟开始 / 忙 / 发噪声 / 报错"的 mock ACP agent，**不是产品功能**，只服务验收与回归。

## 二、具体功能细节（用户视角）

### 2.1 功能总览

| 功能点 | 谁在用 | 解决什么问题 | 本次交付程度 |
|---|---|---|---|
| **A 发起单节点任务** | 编排者 | 不用再手工开终端敲 DSH、盯输出 | 一条命令跑通单角色单节点；实例、节点、会话都由核心自动建，不写工作流 |
| **B 看会话在做什么** | 编排者 | 不知道会话是在想、在调工具、还是在等审批 | 6 个状态有定义与映射，5 个可观测（1 个仅夹具），命令输出与事件记录可见 |
| **C 看节点走到哪** | 编排者 | 分不清"会话说完成了"和"这件事真的做完了" | 节点 6 个状态，由核心裁决推进；与会话状态分开显示 |
| **D 看交接包走到哪** | 编排者 | 分不清"交出去了""对方接了""做完了" | 7 个状态有定义，5 个可观测；非法迁移被拒绝 |
| **E 出错时看得懂** | 编排者 | 失败只有一句 `error`，得自己猜 | 开始前 / 开始后两组失败，各条提示可区分，宿主原文不吞不改 |
| **F 关掉再打开还在** | 编排者 | 重启后一切归零，靠回忆 | 状态快照 + 事件记录落盘可查；明确标"上次中断"，不自动重跑 |

> 编号说明：本迭代有 6 个功能点，故用 2.2~2.7；模板中的「功能之间的衔接」与「业务规则」顺延为 2.8、2.9。

### 2.2 A 发起单节点任务：用户能做什么，看到什么

- **使用角色**：编排者（当前就是我自己）
- **使用场景**：手上有一个边界清楚的小任务，例如"写一段 200 字的产品说明并保存到 `out/intro.md`"，想交给一个角色在 DSH 上跑完
- **用户操作**：在终端执行一条命令。不需要写工作流文件，不需要手工开 DSH 终端。核心没在跑时会自动拉起
  ```
  orch run --cwd ./demo --task "写一段 200 字的产品说明，保存到 out/intro.md"
  ```
  要对已经存在的实例再发一次（例如上次中断了），用同一个实例号：
  ```
  orch run --cwd ./demo --instance INST-001 --task "…"
  ```
- **预期效果**：命令输出依次出现——
  1. `实例 INST-001 · 运行中`
  2. `会话已创建 sess-xxxx`
  3. `任务已投递`
  4. `会话 执行中 · 已运行 3s`
  5. `会话 等待下游 · 产出已提交`
  6. `节点 已完成 · 耗时 1m12s`

  命令退出后，随时用 `orch status` 能查到这次的实例、节点、会话、交接包与事件记录
- **异常情况**：
  - DSH 起不来 → `无法启动 DSH：<原因>`，**不进入**"执行中"，不留半截会话
  - 工作目录不可写 → `工作目录不可写：<路径>`，命令以失败退出，不创建会话
  - 同一实例同一节点已有一次执行在跑 → `该节点正在执行，本次未发起`，**不新建第二个会话**
  - 核心进程起不来 → `核心进程启动失败：<原因>`，命令以失败退出
- **边界说明**：一次只跑一个节点。多节点并行、节点间依赖、条件分支都不在本迭代。**每次发起都新建一个会话，不复用**（阶段零已定：阶段一默认 `fresh`）

**实例状态（本迭代能走到 5 个，`已中断` 由重启时判定）**

| 实例行显示 | 含义 | 能从这里走到 |
|---|---|---|
| `已创建` | 实例已登记，还没开始 | `运行中`、`已取消` |
| `运行中` | 正在推进 | `已完成`、`失败`、`已取消`、`已中断` |
| `已完成` | 节点到达"已完成" | 终态 |
| `失败` | 节点到达"失败" | 终态（重跑是 I1.2） |
| `已取消` | 我取消了 | 终态 |
| `已中断` | 核心进程在运行中消失，重启后判定 | 终态（恢复执行是 I1.8） |

> 不在上表的迁移一律拒绝，并在事件记录里留一条"拒绝的迁移"。实例状态显示在 `orch status` 的第一行。

### 2.3 B 看会话在做什么：用户能做什么，看到什么

- **使用角色**：编排者
- **使用场景**：任务跑起来了，我想知道它此刻是在思考、在调工具、还是卡在等审批
- **用户操作**：盯着 `orch run` 的输出（实时刷新），或在另一个窗口执行 `orch status --instance INST-001`
- **预期效果**：会话那一行在 6 个值之间切换，每个都带人话说明——

  | 我看到（会话行） | 意味着 | 本迭代能否观测 |
  |---|---|---|
  | `空闲` | 会话已建好，还没接到任务 | 能（仅夹具可停在此时刻） |
  | `执行中 · 已运行 3m` | 正在推理或输出 | 能 |
  | `执行中 · 调用工具（写文件）` | 正在调工具，显示工具名 | 能 |
  | `等待审批：git_push` | 停在一个需要我点头的动作上 | 能（仅夹具；真实 DSH 当前不发起审批） |
  | `等待下游` | 已产出，等核心核对或等下游接收 | 能 |
  | `已升级` | 核心判定需要我介入 | **不能**：只有定义，不显示，触发在 I1.2 |

- **异常情况**：宿主长时间没有任何新动静 → 仍显示 `执行中`，并附 `已运行 8m · 无新事件`。**不擅自判定失败**（阶段零实测：取消要 4.3 秒才生效，贸然判定会把还在跑的当成挂了）
- **边界说明**：会话状态只更新"这个会话在干什么"的指示，**不改变节点走到哪一步**。取消或关闭后该会话退出"执行中"，回到 `空闲`。`已升级` 本迭代只有定义，既不显示也不产生

### 2.4 C 看节点走到哪：用户能做什么，看到什么

- **使用角色**：编排者
- **使用场景**：会话说它跑完了，我想确认这件事是不是真的做完了。会话的"结束"只是它自己不说话了，不等于产物真的存在
- **用户操作**：`orch status --instance INST-001`，或看 `orch run` 的收尾输出
- **预期效果**：节点那一行按核心裁决推进，与会话行分开显示——

  | 我看到（节点行） | 意味着 | 对应基线的节点状态 |
  |---|---|---|
  | `待执行` | 任务已登记，还没交给会话 | `blocked` + `ready`（合并显示） |
  | `执行中` | 会话正在为这个节点干活 | `assigned` + `running`（合并显示） |
  | `待校验` | 会话说它做完了，核心正在核对产出 | `review` |
  | `已完成` | 核心核对通过，这件事算做完 | `done` |
  | `失败` | 没做成，附原因 | `failed` |
  | `已取消` | 我主动终止了它 | `cancelled` |
  | （不显示） | 需要人工介入 | `escalated`，本迭代只有定义，I1.2 才产生 |

  典型的一次推进会看到：`节点 执行中` + `会话 执行中` → `节点 待校验` + `会话 等待下游` → `节点 已完成` + `会话 空闲`

- **异常情况**：会话结束时声称做完了，但核心核对产出失败（任务声明了产出路径，而文件不存在或为空）→ 节点显示 `失败`，附 `核对失败：未找到声明的产出 out/intro.md`
- **边界说明**：本迭代的"核对"只做**最小检查**——任务若声明了产出路径，检查文件存在且非空；若任务没声明产出路径，只核对会话是否正常结束，并在事件记录里注明"未声明产出，跳过存在性检查"。完整证据模型与审核角色在 I1.3，交接包 schema 校验在 I1.4，产物指纹校验在 I1.12。**会话说完成不算完成**，必须核心核对通过才推到"已完成"

**节点状态迁移（不在表内的一律拒绝）**

| 从 | 可到 | 触发 |
|---|---|---|
| `待执行` | `执行中`、`已取消` | 会话开始执行 / 我取消 |
| `执行中` | `待校验`、`失败`、`已取消` | 会话提交产出 / 宿主报错 / 我取消 |
| `待校验` | `已完成`、`失败` | 核对通过 / 核对未通过 |
| `已完成` / `失败` / `已取消` | —（终态） | — |

### 2.5 D 看交接包走到哪：用户能做什么，看到什么

- **使用角色**：编排者
- **使用场景**：我想分清三件事——"东西交出去了吗""对方接了吗""对方做完了吗"
- **用户操作**：`orch status --instance INST-001`，或 `orch status --instance INST-001 --events`
- **预期效果**：一个交接包按顺序显示，每步带时间戳——

  ```
  交接包 HO-001  已构造   10:30:02
  交接包 HO-001  已投递   10:30:02
  交接包 HO-001  已接受   10:30:05
  交接包 HO-001  已完成   10:31:14
  ```

  单节点场景下，交接包由核心构造并投给**同一个节点的会话**（本迭代不存在跨角色传递）

- **异常情况**：
  - 目标明确拒绝（会话返回拒绝，或审批被拒）→ `已拒绝`，并附原因
  - 我取消了任务 → `已拒绝`，原因写 `已撤回`。**不能**与"目标拒绝"混成同一条
  - 投递后长时间没有任何"对方开始干活"的迹象 → 仍显示 `已投递`，附 `等待目标响应 · 已等待 2m`。**不自动判过期、不判失败**（阶段零实测：把还在执行的任务判过期，会误杀）
  - 宿主不在线导致根本没投出去 → 本迭代**不产生**该情形（会话建不起来就是 2.2 的"无法启动 DSH"）
- **边界说明**：本迭代只做状态与判定，不做自动重投、不做升级生成（I1.4 / I1.2）。`待投递` 与 `已过期` 只有定义与拒绝非法迁移，不会真实发生

**交接包状态与迁移（不在表内的一律拒绝）**

| 状态 | 含义 | 本迭代可观测 | 可到 |
|---|---|---|---|
| `已构造` | 交接包已构造，未投递 | 能 | `已投递` |
| `已投递` | 已投到目标会话，等对方开始 | 能 | `已接受`、`已拒绝` |
| `已接受` | 对方开始处理 | 能 | `已完成`、`已拒绝` |
| `已完成` | 目标节点产出提交并被核心核对通过 | 能 | —（终态） |
| `已拒绝` | 对方拒绝 / 审批被拒 / 我撤回 | 能 | —（终态） |
| `待投递` | 宿主不在线，投递未确认 | **不能**（重投在 I1.4） | `已投递`、`已过期` |
| `已过期` | 连续重投失败后判超时 | **不能**（I1.4） | —（终态） |

### 2.6 E 出错时看得懂：用户能做什么，看到什么

- **使用角色**：编排者
- **使用场景**：任务没跑成，我需要知道该怪谁、下一步做什么
- **用户操作**：看失败提示
- **预期效果**：分两组，一眼能认出是"还没开始"还是"跑起来之后坏的"——

  **开始前就失败（任务根本没跑）**

  | 我看到的提示 | 真实含义 | 我该做什么 |
  |---|---|---|
  | `无法启动 DSH：<原因>` | 宿主起不来 | 查 DSH 安装与路径 |
  | `工作目录不可写：<路径>` | 目标目录没权限 | 换目录或改权限 |
  | `核心进程启动失败：<原因>` | 核心没起来 | 查核心进程与端口占用 |
  | `该节点正在执行，本次未发起` | 这个节点已经有一次执行在跑 | 等它结束，或先取消 |

  **跑起来之后失败（任务已开始）**

  | 我看到的提示 | 真实含义 | 我该做什么 |
  |---|---|---|
  | `会话已失效，需要重新创建` | 会话被关了或根本不存在 | 重跑，会新建会话 |
  | `审批被拒绝，任务中止于 <步骤>` | 一个动作没有被放行 | 检查审批策略 |
  | `执行失败：<宿主原文>` | DSH 报错了 | 看原文 |
  | `核对失败：<具体原因>` | 会话结束了，但产出对不上（例如 `未找到声明的产出 out/intro.md`） | 看产出路径与内容 |
  | `未知错误：<宿主原文>` | 宿主返回了没见过的错误 | 看原文，别猜 |

- **异常情况**：宿主返回没见过的错误 → 原文透出，前缀 `未知错误：`，**不吞掉、不改写、不截断**
- **边界说明**：不做自动重试、不做降级链（I1.4 / I1.8）。"会话已失效"与"该节点正在执行"是**两条不同提示**，不能因为宿主返回同一个错误码就合并

### 2.7 F 关掉再打开还在：用户能做什么，看到什么

- **使用角色**：编排者
- **使用场景**：任务跑到一半，我关了终端，或者核心进程被杀了，或者机器重启了
- **用户操作**：重新执行 `orch status`（不带参数会列出所有实例），或 `orch status --instance INST-001 --events`
- **预期效果**：能看到这次的实例、节点、会话、交接包状态，以及顺着时间戳可读的完整事件记录；未完成的实例明确标 `已中断`，并说明停在节点/会话的哪一步
- **异常情况**：状态快照损坏 → 提示 `状态不可读，已备份为 state.json.corrupt`，**不静默清空**，不假装"没有这个实例"；若事件记录仍可读，照样能看历史
- **边界说明**：不自动恢复执行、不重新接回原会话。恢复能力在 I1.8。**"不自动重跑"是硬要求**——偷偷重跑比不恢复更糟

### 2.8 功能之间的衔接：走完一遍是什么样

我把这六个功能串起来跑一遍，体感是这样的：

1. 敲一条命令。几秒内（热启动目标 ≤5 秒）屏幕上出现 `实例 INST-001 · 运行中`、`会话已创建 sess-7f3a`、`任务已投递`。
2. `会话 执行中 · 已运行 1s`。我可以去干别的，回来瞄一眼。
3. 半分钟后变成 `会话 执行中 · 调用工具（写文件）`。我知道它在落盘，而不是在原地空转。
4. `会话 等待下游`，同时 `节点 待校验`。这时我去看交接包：`已投递 10:30:02 → 已接受 10:30:05`——"已接受"出现了，但节点还停在"待校验"，没到"已完成"。
5. 核心核对产出通过，`节点 已完成 · 耗时 1m12s`，交接包 `已完成 10:31:14`。事件记录里能顺着时间戳把每一步重放一遍。
6. 如果我中途关了终端，任务照跑；下次 `orch status` 会看到它在继续。如果核心进程被杀了，下次打开会看到 `实例 已中断`，不会自己重跑。
7. 如果哪一步失败，我在第 4 步就能看到是 `执行失败：<原文>`（宿主报的错）还是 `核对失败：未找到声明的产出 …`（做完了但东西对不上），而不是等到最后只有一句 `error`。

整个过程我**没有打开过 DSH 自己的终端**，也没有手工复制过任何路径。

### 2.9 用户可见的业务规则

| 编号 | 规则 | 用户怎么感知 |
|---|---|---|
| **BR-01** | 同一个实例的同一个节点，同一时刻只能有一次执行 | 重复发起时看到"该节点正在执行，本次未发起"，而不是两个会话各跑一遍 |
| **BR-02** | "已接受"不等于"已完成" | 交接包显示 `已接受` 之后，节点仍是"待校验"或"执行中"，直到核心核对通过 |
| **BR-03** | 会话状态只影响指示，不改变节点走到哪一步 | 会话显示 `等待审批` 时，节点仍是"执行中"，不会跳到"已完成" |
| **BR-04** | 任务没真正开始时，状态不会自己跳到"执行中" | 会话建好后我什么都不做，十分钟后它还是"空闲" |
| **BR-05** | 会话刚建好、还没接到任务时是"空闲" | 创建后立刻显示 `空闲`，不显示 `执行中` |
| **BR-06** | 取消或关闭后不残留，且交接包记为"已撤回" | 会话回到 `空闲`、节点 `已取消`、交接包 `已拒绝（已撤回）`，三者都不停在中间态 |
| **BR-07** | 连续跑两个任务，第二个的状态只反映第二个任务的进展 | 第二个任务的"执行中"不会因为第一个的收尾消息提前亮起 |
| **BR-08** | 目标一直没开始干活，不会被判成过期或失败，只显示等多久了 | 看到 `已投递 · 等待目标响应 2m`，而不是 `已过期` 或 `失败` |
| **BR-09** | 会话说做完了不算做完，核心核对通过才算 | 事件记录里能看到节点先到"待校验"，核对通过才到"已完成" |
| **BR-10** | 每次状态变化都可追溯 | 事件记录里每条都有：哪个对象（实例/节点/会话/交接包）、什么时间、从什么状态到什么状态 |
| **BR-11** | 中断后重开不自动重跑 | 看到 `已中断`，且不会自己又跑一遍 |
| **BR-12** | 失败时保留宿主原文与出错步骤 | 看到 `执行失败：<原文>` 或 `核对失败：<原因>`，能看到停在哪一步 |
| **BR-13** | 不同原因的失败给不同提示，不合并成一句"失败" | 开始前 4 条、开始后 5 条，各是各的提示 |
| **BR-14** | 状态会说明它在干什么 | 调工具时能看出是哪个工具，等审批时能看出等的是哪个动作 |
| **BR-15** | 只有对方真正开始处理任务，才算"已接受" | 宿主发来的命令刷新、用量统计这类消息再多，交接包也停在"已投递" |
| **BR-16** | 状态记录损坏时保留原文件，不静默清空 | 看到"状态不可读"并被告知备份在哪，历史不会凭空消失 |

```gherkin
Then 我看到"执行失败："加上宿主原文
And 我能看到停在哪一步
And 节点显示"失败"，交接包不显示"已完成"
```

#### AC-22 没见过的错误原样透出

#### AC-24 目标迟迟不开始，也不判过期

### 3.2 非功能验收标准

| 编号 | 我作为用户能感知的约束 | 目标 |
|---|---|---|
| NFR-01 | 发出任务后多久看到"执行中" | 热启动 5 秒内；冷启动 30 秒内，且冷启动耗时单独记录 |
| NFR-02 | 状态变化多久反映到我能看到的地方 | 1 秒内 |
| NFR-03 | 连续跑 10 个任务，我会不会看到状态错乱或记录缺失 | 0 次错乱、0 条缺失 |
| NFR-04 | 重启后能不能查全上次的状态 | 实例 / 节点 / 会话 / 交接包 / 事件记录 5 项都能查到 |

| NFR-08 | 我取消之后，多久看不到"执行中" | 5 秒内 |

### 3.3 验收前置条件

**环境准备**

- 本机已安装 DSH 并能启动
- 有一个可用的模型来源：真实凭据，或包内确定性 mock LLM。**用 mock 时只能验证链路与状态，不代表真实推理质量，验收记录必须写明用的哪种**
- 有一个单节点任务样例，写明任务描述与预期产出路径
- `.orch/` 可写，且当前没有残留的旧实例干扰
- **产出落盘能力的验收门（开工前）**：阶段零在真实 DSH 上报过 `unknown tool "bash"` / `UNKNOWN_TOOL`，当时据此记为「落盘未验证」。根因已查明：**Windows 上没有 `bash` 工具**（profile 里 `tool-bash` 以平台条件禁用，由 `pwsh` 顶替），文件写入工具是 `write`——是探针用错了工具名，不是宿主不能落盘（证据与复现命令见 `iteration-0/report.md` 附录 C）。开工按下述门执行：
  - 补验 I0.2 的 G-1 通过（`write` 调用 `completed` + 文件存在 + 内容一致）→ AC-01 / AC-06 / AC-11 在**真实 DSH** 上跑；
  - G-1 不通过 → AC-01 / AC-06 / AC-11 改在「可写文件的夹具宿主」上跑，验收记录注明「真实 DSH 只验链路、不验落盘」；
  - 无论哪种，**夹具里禁止硬编码 `bash`**，工具名按平台取。

**夹具准备（用于真实 DSH 无法稳定复现的场景）**

| 夹具开关 | 用来构造什么 | 支撑的 AC |
|---|---|---|
| `--permission=ask` | 任务停在一个需要放行的动作上 | AC-17 |
| `--permission=deny` | 审批被拒 | AC-18 |
| `--noise-on-session-new` | 会话刚建好就发无关刷新消息 | AC-19 |
| `--session-missing` | 会话已关闭或不存在的错误 | AC-20 |
| `--host-error` | 宿主在执行中报错 | AC-21 |
| `--unknown-error` | 宿主返回没见过的错误 | AC-22 |

| `--turn-delay-ms` | 长时间静默 | AC-23 |
| `--hold-session` | 会话建好但停住不投递 | AC-15 / AC-16 |

| `--slow-tool` + 工具名 | 让工具调用过程可观测 | AC-16 / AC-25 |

> 夹具是本迭代的交付物之一（1.3 范围内第 8 条）。它替代的是"还没有的审批界面"和"真实宿主不可控的时序"，不是产品功能。

## 附录

### A. 术语表

| 术语 | 含义 |
|---|---|
| 实例 | 一次任务的运行单元，有实例号（如 `INST-001`）。一次 `orch run` 产生一个实例 |
| 节点 | 编排单位，一个"要做的事"。本迭代一个实例只有 1 个节点 |
| 会话 | 执行单位，一个跑在宿主里的对话。本迭代一个节点对应一个新会话 |
| 交接包 | 把"要做什么、依据是什么"交给一个执行单位的结构化包裹。本迭代由核心构造并投给同一节点的会话 |
| **已完成（节点）** | 核心核对产出通过，这件事算做完 |
| **已完成（交接包）** | 目标节点产出已提交并被核对通过。**与节点"已完成"不是同一件事** |
| **已接受（交接包）** | 对方开始干了，但还没干完 |

> 为避免混读，所有状态输出都带层名前缀（`实例 …` / `节点 …` / `会话 …` / `交接包 …`）。
