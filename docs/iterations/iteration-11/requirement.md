## 一、背景与问题

### 1.1 现状与问题

到 I1.10a 收口，Maestro 有了一个能双击启动、能看全局实例列表、能看角色流程图的桌面应用。但**"看见"和"能处理"之间还差一整段路**，这段路今天全部落在终端上：

- **需要人时没人叫他**。实例因为轮次超限、连续失败、证据缺失而被挂起时，界面只会把健康度变成"需关注"，但这要求人正盯着屏幕。人一旦把窗口关到托盘去干别的事，实例就静静挂在那里，可能挂一整夜。基线要求"至少一种触达方式（托盘通知 / 面板轮询 / IM）"（`docs/index.md` 512 行），今天一种都没有。
- **处理一次要回到终端敲命令**。`orch escalate list`、`orch escalate resolve ESC-001 --decision retry`、`orch approve APR-001 --decision allow` 三套命令，还要记住 `--instance`、`--decision` 的取值；跨多个实例时要先 list 再逐条挑。人不在终端前，这条链路就断了，而阶段一退出条件要求"桌面应用可独立完成日常操作，不依赖 CLI 或浏览器"（629 行、913 行）。1044 行把"桌面应用能否独立完成日常操作"明确列为 **I1.11 / I1.12 验收**的核心判据。
- **升级和审批是两个世界**。基线要求两者统一为"可查询队列，面板和 CLI 均可处理"（511 行）；今天升级只能 `escalate list`、审批只能 `approve`，界面上一个都没有。
- **判断"为什么失败"只能看终端摘要**。执行摘要（命令、退出码、关键输出行数、日志引用）已经在 I1.9 落进事件日志（506 行），但面板上没有一屏能按节点看；人要判断"这次失败是测试真的红了，还是命令压根没跑起来"，还得去终端翻。
- **配置看不见**。角色、技能、工作流三类资产只有 `orch role|skill|workflow list|show`；想知道"这个角色引用了哪些技能、契约填全了没有、这套工作流有几个角色几条回流"，必须一条条敲。基线要求在桌面端提供"资产库：角色 / 技能 / 工作流"（32 行）。
- **角色占用只能一个实例一个实例看**。一个角色在多个实例里同时服务是常态（基线 222 行允许 `max_concurrent_sessions` 到 3–5），但今天没人能回答"开发这个角色现在总共被几个实例占着、开了几条会话"。
- **托盘只是个开关**。今天的托盘只有"打开主窗口 / 退出"两项，不显示实例数与待处理升级数，也没有"暂停"（基线 34 行要求"显示实例数 / 待处理升级数，通知，暂停/退出"）。

不解决会怎样：桌面应用永远停在"只读看板"，人一旦要处置就必须回终端，阶段一退出条件不可能达成；而托盘通知缺位意味着"需要人"这件事根本无法在无人值守时传达出去。

### 1.2 目标与成功衡量

做完之后，用户可观测的变化：

1. **需要人时会响**：升级产生、实例完成、实例异常三类事件在 2 秒内触达托盘通知，通知里带实例号与原因摘要；关掉窗口去干别的事也不会漏。
2. **处置不必回终端**：所有待处理升级与待审批合并成一个队列，五种动作（继续 / 重派 / 终止 / 允许 / 拒绝）在面板上点完即生效；处理完最后一条后实例自己继续跑，不需要再补一步"恢复"。
3. **判断有据**：任一节点都能在证据视图看到命令、退出码、关键输出行数与产物引用；失败原因不再靠猜。
4. **配置可读**：角色库、技能库、工作流库可在面板上浏览列表与详情，并标注校验是否通过；工作流画布按定义画出角色图（含回流），与实例流程图同一套布局规则。
5. **占用可查**：角色库的运行时子视图按角色聚合跨实例占用——参与几个实例、几条活跃会话、服务哪些节点。
6. **托盘能值守**：托盘显示实例数与待处理升级数并随状态更新；可一键暂停全部运行中实例并恢复；退出语义与 I1.10a 一致。
7. **不添乱**：除五种处置动作外，浏览库 / 画布 / 证据都不改任何状态、不写资产文件、不追加审计；`dependencies` 仍为 `{}`，既有 CLI 与既有接口输出逐字不变。

### 1.3 范围

**范围内（本次让用户获得的新能力）**：

- **托盘通知**：升级待处理、实例完成、实例异常三类事件触达系统托盘通知；通知带实例号、编号、节点与轮次、原因摘要；点击通知打开主窗口并定位到队列对应条目；通知有总开关与三类分项开关，按本机记住；同一升级 10 秒内不重复、同一实例同类异常 60 秒内合并为一条；系统通知不可用时不阻断任何流程。
  - **来源说明（D-02）**：开关（BR-03）、去重窗口（BR-04）、点击定位（BR-02）三项都是 880 行「托盘通知」这一能力的**可用性细化，不新增能力域**——通知的类别与触发点仍严格取自 880 原文三类；一个点不进去、会重复轰炸的通知不构成 881–888 行要求的可用触达。本迭代**不引入**通知历史、通知声音 / 免打扰时段、IM / Webhook。
- **人工干预队列**：跨实例合并全部**待处理**升级与**待审批**为一个队列；每行给出实例、类型、编号、节点与角色、轮次或次数、原因摘要与产生时间；固定排序；空态。
- **五种决策动作**：升级的「继续」（判通过并继续推进）、「重派」（重新分配会话，轮次 +1）、「终止」（取消该实例）；审批的「允许」「拒绝」。动作与条目类型匹配，不匹配的置灰并说明原因；终止需二次确认。**一次只处置一条**，不提供多选（成组处置见范围外）。
- **处理后续跑**：处理完某实例最后一条待处理项后，实例自动继续推进，队列条目消失，托盘待处理数与列表"待处理数"同步减少。
- **角色库 / 技能库 / 工作流库浏览**：列表（名称、来源内置/项目、校验状态；角色与技能另给分组，工作流另给节点数与边数）+ 详情（角色契约与技能引用、技能适用与命令、工作流节点与边）；校验失败的资产照常可浏览并标注失败原因；资产目录不可读、单个资产不可解析或引用缺失时有中文降级。
- **角色库运行时子视图（全局占用）**：按角色聚合跨实例占用（参与实例数、活跃会话数、服务节点、占用状态）；无运行时数据时给空态并把注册表角色标为"未参与"。
- **工作流画布（只读）**：按工作流定义画出定义态角色图（角色 / 人工 / 升级 / 子工作流节点与正向、回流边），复用实例流程图的布局算法；不显示运行时状态色、会话数与异常角标；**定义取不到（文件不存在 / 无读权限）或内容为空或解析成功但零节点时显示「定义 空」**，**文件在但结构不可解析时显示「定义不可读 · 仅显示可解析部分」**，**校验失败但结构可解析时照常画出并标注「校验不通过」**。
- **证据浏览独立视图**：按节点查看产出证据——命令、退出码、关键输出行数、日志引用、产物引用（含校验时间）；缺项显示"未提供"；引用不可读时标注且不崩溃；只展示摘要与引用，不展示完整日志正文。
- **托盘交互**：托盘显示实例数与待处理升级数并 2 秒内更新；新增"暂停"（暂停全部运行中实例的推进，同一项在暂停后变为"继续"）；退出确认语义与 I1.10a 完全一致。

### 2.2 托盘通知：需要人时把人叫回来

- **使用角色**：把主窗口关到托盘、正在做别的事的人；值班人。
- **使用场景**：某个实例升级了等人裁决；某个实例跑完了；某个实例出了异常（失败、中断、健康度转"需关注"）。
- **用户操作**：无需操作，通知自己出现；想处理时点通知。
- **预期效果**：
  - 三类事件各给一条通知，标题与正文逐字见附录 A-1。正文按**固定段序**给出五段：`实例 {实例号} · 升级 {编号} · 节点 {节点号} {角色} · 第 {n} 轮 · {原因摘要}`；完成与异常两类按同一段序取可用项，取不到的段渲染 `—`、**不省略**。正文不含会话内容、日志正文、产物内容。
  - 通知出现得及时：事件发生到通知出现 ≤ 2 秒。
  - 点击通知：主窗口被唤到前台，直接停在人工干预队列，并选中对应那条（该条高亮、滚动到可见位置）。若这条已被别处处理过，仍停在队列并提示"已处理（{结论}），无需再次处理"。
  - 同一升级 10 秒内只通知一次；同一实例的同类异常在 60 秒内合并为一条，正文标注"共 N 次"；同一实例的完成只通知一次。
  - 通知可以被关掉：**人工干预队列页顶部的设置区**有总开关与三类分项（不新增独立设置视图、不新增菜单项）；关掉后不再产生该类通知，但队列与托盘数字照常更新。开关按本机记住，重启应用后仍生效。
- **异常情况**：系统通知不可用或被系统拒绝时，不弹通知、不影响任何实例与队列；界面给一次中文提示（逐字见附录 A-2），队列与托盘数字照常更新，且不会每条事件都弹一次提示。通知投递失败不做重试、不阻塞实例推进。
- **边界说明**：通知是"触达"，不是"状态"——收到通知不等于处理过；通知不改变任何节点、会话、交接包、升级、审批状态（判定见 AC-01 的五组状态对比）。暂停期间的实例不再推进，因此不会因暂停产生新的完成 / 异常通知。

### 2.3 人工干预队列：一处看全、一处处理

- **使用角色**：值班人；同时有多个实例的人；被通知叫回来的人。
- **使用场景**：早上打开应用先看"有哪些事在等我"；被通知点回来；处置完一批继续干别的。
- **用户操作**：打开主窗口 → 切到"人工干预队列"（或点通知直接到此处）；点某一行展开本条详情；用行内按钮处置（一次一条）。
- **预期效果**：
  - 队列把**所有实例**的待处理升级与待审批合并在一起。**每一行（含审批行）都给出同样八项**：类型（升级 / 审批）、编号、实例号、节点与角色、轮次或次数、状态词、原因摘要、产生时间（逐字见附录 A-3）。审批行的原因摘要位固定写动作名（`动作 write` 形态），因此"这是哪个实例、第几轮、什么时候来的"在看审批时同样一眼可辨。
  - 排序固定：升级在审批之前；同类按编号升序；跨实例按实例号升序。用户不需要自己找"最急的那条"。
  - 队列会自己变：新升级 / 新审批 2 秒内出现在队列里（BR-37）；处置后该行立即消失；不需要手动刷新，也没有"刷新"按钮。
  - 没有待处理项时显示"待处理 无"，并保留"查看实例列表"的入口。
  - 队列数字与另外两处必须口径一致：同一时点，队列总条数 = 全部待处理升级 + 全部待审批；托盘上的"待处理升级"只数升级；实例列表每行的"待处理数" = 该实例的待处理升级 + 待审批。审批减少只让队列与列表变小，托盘升级数不变。
- **异常情况**：守护进程断开时，队列保留最后一次看到的内容并显示"已断开 · 正在重连…"，恢复后自动补全；不把旧内容当最新状态悄悄留着（BR-36）。某条目的实例状态不可读时，该行仍出现并标注"状态不可读"，其余行照常可处置。
- **边界说明**：队列只显示**待处理**条目，已处理记录不在此处堆积（历史见既有事件日志与 CLI 的 `--all`）；队列不做筛选器组合、不做搜索、不做自定义列。

### 2.4 五种决策动作与处理后续跑

- **使用角色**：有处置权的人（本迭代不区分权限，所有能打开面板的人都能处置）。
- **使用场景**：判断某次失败该重做、该换会话重派、还是该整个放弃；某次工具调用请求需要放行或拒绝。
- **用户操作**：在队列行上点动作按钮；终止时在确认框里确认。一次只处置一条。
- **预期效果**（按钮与结果文案逐字见附录 A-4）：
  - **升级 · 继续**：判该轮通过并继续推进（升级行变为"已处理（通过）"）。实例随后按节点位置落定：**该节点是终态节点时实例进入"已完成"**；**不是终态节点时实例保持"运行中"、下游节点被唤醒并继续**（D-39）。仅当该升级是"轮次超限"类时可用；其它升级上该按钮置灰、点不动，悬停说明"该升级只能重派或终止"。
  - **升级 · 重派**：把该节点重新分配给一个会话、轮次 +1（升级行变为"已处理（重新分配）"）。
  - **升级 · 终止**：放弃该实例（实例进入"已取消"，节点不再推进）。必须先确认，确认句带实例号。
  - **审批 · 允许**：放行该次动作（审批行变为"已通过"）。
  - **审批 · 拒绝**：拒绝该次动作（审批行变为"已拒绝"）。
  - 点下动作后 2 秒内看到结果或"处理中"；不会出现点了没反应。
  - **处理后续跑**：处理完某实例最后一条待处理项后，该实例在 5 秒内自动继续推进，队列中它不再出现，托盘待处理数与列表"待处理数"同步减少；不需要用户再点一次"恢复"。
- **异常情况**：
  - 条目在你点之前已被别处（另一个窗口或终端）处理：提示"已处理（{结论}），无需再次处理"，不重复写入，队列自动刷新。
  - 实例已不在挂起状态（另一处已恢复）：提示"实例 {id} 当前不是挂起状态，不能处理升级"。
  - 审批对应会话已经不在运行：提示"审批 {id} 已失效：会话不在运行"。
  - 动作与条目类型不匹配（例如对审批点"重派"）：按钮本就不出现；若因数据刷新导致错配，提示"升级 {id} 不支持该动作"（审批同形态）并保持原状态。
  - 任何失败都不关闭队列、不清空已展开的那一条，用户可以再点别的条目。
- **边界说明**：本迭代只提供这五种动作，**不提供**"判失败"这一独立动作（该语义由"重派"后的再次失败自然产生，或由"终止"直接结束实例）；不提供"改轮次上限""改超时""调并发"等参数编辑；不做动作审批链（谁能点属 I1.12 治理）。

### 2.5 角色库 / 技能库 / 工作流库浏览

- **使用角色**：设计角色与工作流的人；排查"为什么这个角色没被唤醒"的人；刚接手项目的人。
- **使用场景**：想知道项目里有哪些角色、它们属于哪一组、引用了哪些技能、契约填全没有；想确认这套工作流有几个角色、几条回流；想确认某个资产是否通过校验。
- **用户操作**：切到"资产库" → 在三个分页之间切换 → 点列表项看详情。
- **预期效果**（行文案逐字见附录 A-5）：
  - **列表**：每一行都给**名称、来源（内置 / 项目）、校验状态（通过 / 不通过）**；角色与技能另给分组（技能的"适用分组"就是它的分组），工作流另给节点数与边数（工作流定义里没有分组字段，不新造一列）。三个分页各有自己的计数（例如"角色 12 个（内置 9 · 项目 3）"）。
  - **角色详情**：中文名、分组、产物类型、副作用等级、最大并发会话、引用的技能清单、工具集、唤醒白名单，以及校验状态与不通过原因。
  - **技能详情**：中文名、适用分组、命令、摘要、正文摘要（只给前若干行，不整篇铺开），以及校验状态。
  - **工作流详情**：中文名、节点数与边数、节点清单（类型：角色节点 / 人工节点 / 升级节点 / 子工作流）、回流条数，以及校验状态与不通过原因。
  - 校验不通过的资产仍出现在列表里（不隐藏），行上标"不通过"，详情里给失败原因；这与 CLI `validate` 的原文一致，不自造解释。
- **异常情况**：资产目录不存在或不可读时，该分页显示"资产不可读 · {目录}"，其它分页照常可用；单个资产文件坏了时，该行标注"不可读"并可点开看到原因，不影响其它行；找不到某个资产（例如角色引用的技能不存在）时，详情里该引用标"缺失"。
- **边界说明**：库是**只读浏览**——没有新建、编辑、导入、导出、删除、触发校验的按钮；这三类资产的写操作仍只在 CLI。校验状态是"上次输出的结果"还是"现算"不影响用户判断，但同一资产在列表与详情里必须给出同一个结论。

### 2.6 角色库运行时子视图：全局角色占用

- **使用角色**：想知道"开发这个角色现在被几个实例占着、开了几条会话"的人；准备再起一个实例、先看还有没有余量的人。
- **使用场景**：多个实例同时跑，同一个角色在多个实例里服务；准备扩一个实例前确认并发余量。
- **用户操作**：在角色库里切到"运行时占用"。
- **预期效果**（行文案逐字见附录 A-6）：
  - 按角色聚合：角色名、占用状态（可用 / 服务中 / 冷却中 / 不可用 / 未参与）、参与实例数、活跃会话数、正在服务的节点（超 2 个折叠）、涉及宿主。
  - 排序固定：服务中在前，其次可用、冷却中、不可用、未参与；同档按角色名升序。
  - 只列**当前有运行时记录**的角色，另把只存在于注册表、本机没有任何实例使用的角色标为"未参与"，不显示为"不可用"。
  - 占用变化 2 秒内反映到该视图（BR-37），与实例流程图里的角色状态同源（同一角色在同一时点两处不能一个说"服务中"一个说"可用"）。
- **异常情况**：一个实例的状态不可读时，它的角色不计入占用，视图底部标注"1 个实例状态不可读，已跳过"；**全部实例状态都不可读、或没有任何实例**时显示"角色占用 无"。
- **边界说明**：这里的"占用"是**跨实例的运行时事实聚合**，不改变任何角色实例；不提供"释放占用""踢掉会话"这类操作。

### 2.7 工作流画布（只读）：定义里到底画了什么

- **使用角色**：设计工作流的人；核对"这套流程有没有回流、人工节点在哪"的人。
- **使用场景**：新拿到的项目工作流要先看懂；校验失败时想知道解析出来的是什么样。
- **用户操作**：在工作流库点某个工作流的"查看画布"。
- **预期效果**（标签逐字见附录 A-7）：
  - 画布按**定义**画出角色图：角色节点、人工节点、升级节点、子工作流折叠组；边按定义画，回流边是反向弧线。标题给出名称、节点数与边数。
  - 布局与实例流程图同一套规则：按拓扑层次从左到右、同层并行上下排列、回流不改层次；同一份定义两次打开坐标一致。
  - **不显示**运行时信息：没有状态色、没有活跃会话数、没有异常角标、没有连接线聚合状态——定义里没有这些。
  - 只读交互：可缩放、可平移、可复位；不能拖拽保存、不能编辑、不能下钻（点节点只做选中高亮）。
- **异常情况**：定义内容整体解析不了时，画布显示"定义不可读 · 仅显示可解析部分"，能解析的节点与边照常画出（一个都解析不出时画布为空，但仍保留返回入口）；定义取不到（文件不存在 / 无读权限 / **内容为空**）或解析成功但一个节点都没有时，显示"定义 空"并保留返回入口；校验失败但结构可解析时，画布照常画，并在标题旁标注"校验不通过"。
- **边界说明**：画布是**定义态**，不是某个实例的运行时图；想看运行时请看实例的角色流程图（既有能力）。画布不承担编辑与保存。

### 2.8 证据浏览独立视图：这个节点到底跑了什么

- **使用角色**：判断"为什么失败"的人；需要确认产物是否真的产出的人。
- **使用场景**：实例失败或升级，人想知道执行了什么命令、退出码是多少、产物在哪、有没有日志可查。
- **用户操作**：切到"证据"视图 → 选实例 → 选节点 → 看该节点的证据。
- **预期效果**（行文案逐字见附录 A-8）：
  - 每个节点给出五项：命令、退出码、关键输出行数、日志引用、产物引用（含校验时间）。有多次尝试时按最近一次展示，并标注轮次。
  - 缺项显示"未提供"，不省略行、不留空白。
  - 只显示摘要与引用；完整日志正文不在面板里展示，界面明确写出"完整日志留在宿主"。
  - 换节点即换内容；没有证据的节点仍可被选中并显示"未提供"，不会因为没证据就从列表里消失。
- **异常情况**：产物引用指向的路径不存在时，该项标"引用不可读"；日志引用不可读时同样标注；两种情况都不隐藏其它四项、不崩溃、不影响选其它节点。
- **边界说明**：证据视图是**独立视图**，从实例的节点清单进入，不依赖角色下钻与节点详情（I1.10b）；不做证据导出、不做产物内容预览、不做完整日志查看。

### 2.9 托盘交互：一眼知道有多少事、一键停下

- **使用角色**：长期挂着应用的人；需要临时腾出机器资源的人。
- **使用场景**：开会前想确认有没有待处理；要跑占资源的任务，先把所有实例暂停；回来再继续。
- **用户操作**：看托盘菜单；点"暂停"；需要时再点"继续"；要彻底停止时点"退出"。
- **预期效果**（逐字见附录 A-9）：
  - 托盘菜单最上方是一行只读信息："实例 N · 待处理升级 M"；N 为全部实例数，M 为待处理升级数。两者随状态变化 2 秒内更新，与实例列表、队列同源。
  - 菜单项固定顺序：信息行 → 打开主窗口 → 暂停 → 退出。没有运行中实例时"暂停"置灰。
  - 点"暂停"：所有运行中实例停止推进，实例行显示"运行中（已暂停）"；该项变为"继续"，再点恢复推进。暂停期间不产生新的完成 / 异常通知。
  - 点"退出"：与 I1.10a 完全一致——有运行中或已挂起实例时先确认（确认句逐字沿用既有文案），确认后停止守护进程；暂停不是退出，暂停后仍需"退出"才真正停止。
- **异常情况**：暂停时某实例已结束或状态不可读：跳过它并继续处理其余实例，结束后提示"N 个实例已暂停，M 个已跳过"；全部跳过时提示"没有可暂停的实例"。恢复同理。托盘信息行在守护进程断开时显示"实例 — · 待处理升级 —"，不显示旧数字冒充最新。
- **边界说明**：托盘不提供逐实例操作（逐实例请进面板）；不提供"暂停单个实例"的托盘入口；不改变 I1.10a 的单击托盘图标行为（有窗口则唤醒，无窗口则打开列表）。

### 2.10 功能之间的衔接

把 §2.2 ~ §2.9 串起来，用户走完一遍是这样一条体验：

1. **正常干活（§2.9）**：应用缩在托盘，菜单最上面写着"实例 3 · 待处理升级 0"。
2. **被叫回来（§2.2）**：某实例轮次超限，2 秒内弹出通知"升级待处理 · INST-001"，正文带节点与原因。
3. **一步到位（§2.2 → §2.3）**：点通知，主窗口到前台、直接停在队列并选中"升级 ESC-001"；队列里同时能看到别实例的一条待审批。
4. **先看证据再决定（§2.8）**：点开该条的节点证据，看到命令、退出码 1、产物引用与日志引用——判断是测试真的红了，不是命令没跑起来。
5. **处置（§2.4）**：点"重派"，2 秒内该行变为"已处理（重新分配）"；实例自动继续推进，5 秒内队列里不再有它，托盘"待处理升级"减一。
6. **顺手放行（§2.4）**：另一条审批点"允许"，审批行变为"已通过"，会话继续。
7. **核对配置（§2.5、§2.7）**：怀疑这套流程缺回流，去工作流库看详情并打开画布，确认回流边确实存在、人工节点在第 2 层。
8. **确认余量（§2.6）**：准备再起一个实例，先看"开发"角色当前参与 2 个实例、3 条活跃会话；确认还有余量再启动。
9. **收工（§2.9）**：先"暂停"全部实例，再"退出"，退出确认照旧。

**走不通时用户看到什么（降级分支，同样属于本迭代的衔接体验）**：

- **系统通知不可用（§2.2）**：界面给一次"通知不可用 · 队列仍可用"的提示，队列数字与托盘数字照常更新；人打开窗口仍能看到待处理。（AC-07 覆盖）
- **队列条目已被别处处理（§2.3、§2.4）**：提示"已处理（{结论}），无需再次处理"，队列自动刷新，不产生重复写入。（AC-15 覆盖）
- **资产 / 画布 / 证据读不到（§2.5、§2.7、§2.8）**：目录级显示"资产不可读 · {目录}"、单个文件级显示"角色 broken-role · 不可读"、画布显示"定义不可读 · 仅显示可解析部分"或"定义 空"、证据显示"引用不可读"，其余部分照常可用。（AC-24、AC-46、AC-31、AC-45、AC-33、AC-42 覆盖）
- **守护进程断开（§2.3、§2.9）**：队列显示"已断开 · 正在重连…"，托盘信息行显示"—"，恢复后自动补全。（AC-47、AC-42 覆盖）

简言之：**托盘看数（§2.9）→ 通知叫人（§2.2）→ 点进来处置（§2.3/§2.4）→ 处置前看证据（§2.8）→ 处置后自动续跑（§2.4）→ 顺手核对配置与占用（§2.5/§2.6/§2.7）→ 收工暂停再退出（§2.9）**，构成一条完整的"无人值守—被叫回—处置完毕"闭环，全程不需要终端；任何一步走不通都有上面四条中文降级路径。

### 2.11 用户可见的业务规则

- **BR-01**：托盘通知覆盖三类事件——升级待处理、实例完成、实例异常；每类各一条，标题与正文逐字见附录 A-1；事件发生到通知出现 ≤ 2 秒；通知不改变任何编排状态。
- **BR-02**：点击通知把主窗口唤到前台并停在人工干预队列、选中对应条目；该条已被处理时停在队列并提示"已处理（{结论}），无需再次处理"。
- **BR-03**：通知有总开关与三类分项开关，入口在人工干预队列页顶部的设置区；关闭后不再产生该类通知，但队列与托盘数字照常更新；开关按本机记住，重启后仍生效。
- **BR-04**：同一升级 10 秒内只通知一次；同一实例同类异常 60 秒内合并为一条并在正文标注"共 N 次"；同一实例的完成只通知一次。
- **BR-05**：系统通知不可用或被拒时不阻断任何流程：队列与托盘数字照常更新，界面只给一次中文提示，不逐条弹提示、不重试、不影响实例推进。
- **BR-06**：人工干预队列跨实例合并**全部待处理**升级与待审批；**每一行（含审批行）**都给出同样八项：类型、编号、实例、节点与角色、轮次或次数、状态词、原因摘要、产生时间。
- **BR-07**：队列排序固定：升级在审批之前；同类按编号升序；跨实例按实例号升序。空态显示"待处理 无"。
- **BR-08**：五种动作与条目类型严格匹配：升级只有继续 / 重派 / 终止，审批只有允许 / 拒绝；"继续"仅对轮次超限类升级可用，其余升级上该按钮置灰、点不动并说明只能重派或终止。"继续"判通过后实例按节点位置落定：**终态节点 → 实例「已完成」；非终态节点 → 实例保持「运行中」且下游节点被唤醒**（D-39），不得一律写成"运行中"。
- **BR-09**：条目已被别处处理时提示"已处理（{结论}），无需再次处理"，不重复写入、队列自动刷新；实例已不挂起、审批会话已失效、动作与类型错配三种情况各有固定中文提示，且不改变原状态。
- **BR-10**：处理完某实例最后一条待处理项后，该实例 5 秒内自动继续推进；队列中该项消失，托盘待处理数与列表"待处理数"同步减少。
- **BR-11**：终止必须先二次确认，确认句带实例号；确认前不改变任何状态。
- **BR-12**：同一时点三处数字口径一致——队列总条数 = 全部待处理升级 + 全部待审批；托盘"待处理升级"只数待处理升级；实例列表每行"待处理数" = 该实例的待处理升级 + 待审批。处置后三处在 2 秒内同步变化，且审批减少只影响队列与列表、不影响托盘的升级数。
- **BR-13**：角色库 / 技能库 / 工作流库浏览、运行时占用子视图、工作流画布、证据浏览、托盘信息行全部只读：不改资产文件、不改实例状态、不追加审计事件。
- **BR-14**：三类资产库每一行都列出来源（内置 / 项目）与校验状态（通过 / 不通过）；角色与技能另给分组（技能为适用分组），工作流另给节点数与边数（定义里没有分组字段，不新造）。校验不通过的资产照常出现在列表里并标注，不隐藏；单个资产文件不可解析时该行标"不可读"。
- **BR-15**：资产详情给出契约要点与引用关系：角色给分组、产物类型、副作用、并发上限、技能引用、工具集、唤醒白名单；技能给适用分组、命令、摘要与正文摘要；工作流给节点清单（含类型）与回流条数。找不到的引用标"缺失"。
- **BR-16**：角色运行时子视图按角色跨实例聚合占用——角色名、占用状态、参与实例数、活跃会话数、服务节点、宿主；"全局"= 本机当前守护进程所辖、本项目根下的全部实例（D-07）；数据来自运行时事实，不用注册表凑。
- **BR-17**：占用视图只列有运行时记录的角色，并把只在注册表出现、本机未使用的角色标为"未参与"；**全部实例状态都不可读、或没有任何实例**时显示"角色占用 无"；不把"没有运行时数据"显示成"不可用"。
- **BR-18**：工作流画布是定义态只读图：画角色 / 人工 / 升级 / 子工作流节点与正向、回流边；布局与实例流程图同一套规则；不显示运行时状态色、会话数、异常角标与连接线聚合状态。
- **BR-19**：工作流画布的降级分工按「有没有可解析输入」划（D-17/D-23）：**文件不存在 / 无读权限 / 内容为空 / 解析成功但零节点 → 「定义 空」**；**文件在但结构不可解析 → 「定义不可读 · 仅显示可解析部分」**（能解析的节点与边照常画出）；校验失败但结构可解析 → 照常画出并在标题旁标「校验不通过」。画布不白屏，四种情形都保留返回入口。
- **BR-20**：证据视图按节点给出五项——命令、退出码、关键输出行数、日志引用、产物引用（含校验时间）；多次尝试按最近一次展示并标注轮次；缺项显示"未提供"。
- **BR-21**：引用不可读时该项标"引用不可读"，不隐藏其它项、不崩溃；证据只展示摘要与引用，完整日志正文不在面板展示。
- **BR-22**：托盘信息行显示"实例 N · 待处理升级 M"，2 秒内随变化更新，与列表、队列同源；守护进程断开时显示"—"。
- **BR-23**：托盘"暂停"把全部运行中实例置为暂停推进，菜单项变为"继续"；再点恢复；没有运行中实例时该项置灰、点击提示"没有可暂停的实例"；暂停逐实例执行，个别失败只跳过并汇报。
- **BR-24**：托盘"退出"语义与 I1.10a 完全一致（有运行中或已挂起实例时先确认）；暂停不是退出。
- **BR-25**：面板的写操作只有三类：五种处置动作（一次一条）、托盘暂停/继续，以及**本机通知开关偏好**（只写 `.orch/desktop/prefs.json`，不碰实例状态、资产与事件日志）；其余浏览一律只读。
- **BR-26**：所有新增中文只来自 `src/cli/labels.js`；`desktop/ui` 与 `desktop/harness` 零中文字面量；壳层（`desktop/src-tauri/src/**`）的字符串字面量只允许 `config.rs` 的 `Labels` 结构与既有同形态的 baked-in 中文默认值，其余一律经 `/ui/labels` 覆盖。不自造同义词（升级仍叫升级，审批仍叫审批，处置词只用继续 / 重派 / 终止 / 允许 / 拒绝）。
- **BR-27**：状态词沿用基线：实例七态（已创建 / 运行中 / 已完成 / 失败 / 已取消 / 已中断 / 已挂起）与"（已暂停）"限定、升级三态（待处理 / 已处理 / 已作废）、审批四态（待处理 / 已通过 / 已拒绝 / 已作废）、角色五态（可用 / 服务中 / 冷却中 / 不可用 / 未参与）、节点九态与看板七列词；不自造词。
- **BR-28**：界面层零第三方依赖、零打包器（纯静态 ESM），`dependencies` 恒为 `{}`。
- **BR-29**：通知、队列、资产库、占用、画布、证据全部经本机回环通道取数；不监听外部网卡、不新增远程入口。
- **BR-30**：本迭代不假设 I1.10b 存在：队列条目点击只展开本条详情，不打开节点详情、不下钻角色、不跳转宿主会话；证据浏览是独立视图，不依赖节点详情入口。
- **BR-31**：既有 CLI 输出与既有 HTTP 面行为逐字不变：`escalate list|resolve`、`approve`、`role|skill|workflow list|show|validate`、`status`、`instance status|graph` 两种格式，以及既有 8 条 HTTP 路径与响应键集合。
- **BR-32**：队列、资产库、画布、证据、通知五处的失败路径都给中文提示且界面保持可用，不白屏、不打印堆栈、不丢失其它可用内容。
- **BR-33**：通知正文按固定段序 `实例 {实例号} · 升级 {编号} · 节点 {节点号} {角色} · 第 {n} 轮 · {原因摘要}` 生成（五段，` · ` 分隔，段内补充说明用 `，`）；完成与异常两类按同一段序取可用项，取不到的段渲染 `—` 不省略；正文不含会话内容、日志正文、产物内容。
- **BR-34**：点下处置动作后 2 秒内看到结果或"处理中"；不允许出现无反馈的点击。
- **BR-35**：暂停期间实例不推进，因此不产生新的"实例完成 / 实例异常"通知；暂停前已产生的升级通知与队列条目照常保留。
- **BR-36**：守护进程断开时，队列与占用视图**保留最后一次成功取到的内容**并标注「已断开 · 正在重连…」（托盘信息行置 `—`），**不把旧内容/旧数字当作最新**；恢复后 2 秒内自动补全，不需要用户点「刷新」。
- **BR-37**：队列与占用的新鲜度：新升级 / 新审批产生后 **2 秒内**出现在队列；占用变化 **2 秒内**反映到角色占用视图。两处都经推送或 ≤2 秒轮询达成，**不需要用户手动刷新**，也不出现旧数字冒充最新（与 BR-36 的断线口径衔接）。

## 三、验收标准（用户视角）

### 3.1 功能验收标准（AC）

> **判定口径（六条，所有 AC 适用）**：
>
> 1. **界面输出的一致性判定**：界面里看到的队列行、资产行、占用行、画布标签、证据行、托盘菜单文本、通知文案，由 `desktop/ui` 下的纯投影/渲染模块生成；验收用 `desktop/harness/*.mjs` 直接 import 同一批模块并逐字断言。窗口只是宿主，不另写一套渲染逻辑。
> 2. **窗口、托盘与通知的判定**：应用接受 `--probe <文件>` 与 `--ctl <目录>` 两个仅测试用参数。启动、窗口显隐、托盘创建、菜单触发、通知意图与投递结果、导航都会追加事件到探针文件；`--ctl` 目录里的文件用于触发与真实菜单/交互相同的处理函数（本迭代在既有 `close-window` / `tray-open` / `tray-quit` / `tray-quit-confirm` / `open-instance/<id>` 之外新增 `notify-open`、`tray-pause`、`tray-resume`、`queue-open`）。**通知类 AC 一律以探针事件为判据，不以"人看一下有没有弹"为判据**；无头 / CI 环境允许系统通知投递失败，此时探针必须记录 `delivered=false` 与原因，判定只看"意图已产生且流程未受阻"。
> 3. **夹具口径**：每个 AC 使用独立项目根，放在 `/tmp/maestro-i11-*`（macOS 的 `$TMPDIR` 等价位置），绝不进仓库；一律注入 `NODE_ENV=test`；宿主一律 `--host mock`（`.orch/hosts/mock.json` 指向仓库内 `test/fixtures/mock-acp-agent.js`）；本迭代验收**不依赖真实 DSH、不依赖 I1.10b**。
> 4. **机检命令形态**：所有文本扫描一律用 `grep -E` / `grep -RE` 或 `rg`，禁止 `grep "...\|..."` 这类 BRE 交替写法（本机 `grep` 是 toybox shim，`\|` 恒不匹配，会让违规代码也输出"零命中"而假通过）。每条架构检查必须写明期望结果："零命中（exit 1）"或"恰好 N 条命中（exit 0）"；含中文的扫描同样走 `grep -RE`。**基线口径说明**：锚点点名的 `desktop/ui/{queue,assets,occupancy,canvas,evidence,notify}/`、`desktop/harness/*.mjs`、`src/daemon/{queue,notify,occupancy,assets-view,evidence,canvas}.js`、`test/wp14/` 属 D-11 的 **S2 才创建**产物，在 `66e5a6b` 上扫描会得到 `No such file or directory`（exit 2）；这属**预期**，不判锚点失效。实现完成后这些路径必须存在，并把 exit 2 变成该条要求的 exit 0 / exit 1。凡是在**既有文件**上做的断言，基线上已实跑过，真实输出写在括号里。

### 3.2 非功能验收标准

- **NF-1（通知及时性）**：升级、完成、异常三类事件发生到托盘通知出现 ≤ 2 秒；同一升级 10 秒内不重复，同类异常 60 秒内合并。
- **NF-2（处置反馈）**：点下动作后 2 秒内看到结果或"处理中"；处理完最后一条后实例 5 秒内自动继续推进。
- **NF-3（数字与新鲜度）**：队列、托盘信息行、列表"待处理数"三处变化后 2 秒内一致；队列新行出现与占用刷新同样 ≤ 2 秒（BR-37）。
- **NF-4（首屏速度）**：在 50 个资产、20 个待处理条目的项目里，切到任一资产分页或证据视图 ≤ 1 秒看到首屏。
- **NF-5（稳定性）**：连续 20 次处置 + 30 次视图切换后界面不崩、守护进程不重启、实例状态与操作次数一致；暂停/继续各 10 次后实例仍可正常推进。
- **NF-6（无回归与零依赖）**：三条主链输出逐字不变；既有 CLI 与既有 HTTP 面不变；`dependencies` 为 `{}`；全量测试失败集合与基线差集为 0。
- **NF-7（只读与本地性）**：除五种处置动作、托盘暂停/继续与只写 `prefs.json` 的通知开关偏好外无写操作；全部数据经本机回环地址；不监听外部网卡。
- **NF-8（中文唯一来源）**：全部新增用户可见中文来自 `src/cli/labels.js`；`desktop/ui` 与 `desktop/harness` 零中文字面量；壳层只允许 `config.rs` 的 `Labels` baked-in 默认值（新增键必须先落 `labels.js` 再由 `/ui/labels` 覆盖）；不自造状态词。

### A-2 通知开关、提示与选中提示


- 第 1 项 `通知` 是总开关；第 **2~4** 项（`升级待处理` / `实例完成` / `实例异常`）是分项开关名，与总开关同组；开关状态按本机记住。

```

```

- 两类行（升级行 / 审批行）是**同一套八字段模板**，只是层名前缀与"原因摘要"位取值不同：升级为 `reasonDetail`，审批固定为 `动作 {action}`。段序固定：`<层名> <编号> · 实例 <实例号> · 节点 <节点号> <角色> · 第 <n> 轮 · <状态词> · <原因摘要> · <产生时间>`。
- **审批行不再复用 CLI 的审批行**（D-13/F-01）：CLI 的 `renderApprovalLine` 在 `single` 模板下连节点都不输出、更没有实例号与时间，跨实例队列里 `APR-001` 可能重号，靠 CLI 行无法区分。审批行由桌面自有模板 `DESKTOP_QUEUE_ROW_APR` 渲染；CLI 输出本身**不改**（BR-31）。

- 排序：升级在审批之前；同类按编号升序；跨实例按实例号升序（上例即该顺序）。
- 时间取条目产生时间（ISO 8601，秒级）。

### B-1 术语

- **人工干预队列**：跨实例合并待处理升级与待审批的统一列表；面板与 CLI 均可处理（基线 511 行）。
- **继续 / 重派 / 终止 / 允许 / 拒绝**：本迭代对用户暴露的五种处置动作；分别对应升裁判通过、重新分配、取消实例、审批放行、审批拒绝。
- **全局角色占用**：按角色聚合跨实例的运行时占用（参与实例数、活跃会话数、服务节点、状态），与单个实例里的角色流程图不是同一视图。
- **定义态**：来自工作流 YAML 的静态声明（节点类型、边、回流），不含任何运行时状态。
- **画布投影的 `readable` / `valid`**（D-6 的补充口径，AC-29 / AC-31 / AC-45 共用）：`readable` 只描述"定义能解析到多少"，`valid` 只描述"校验是否通过"，两者**正交**。三态：① `readable === true` = 整体解析成功（含"解析成功但零节点"，此时显示「定义 空」）；② `readable === false && nodes.length > 0` = **部分可解析**，只显示可解析部分、**不显示「定义不可读」**；③ `readable === false && nodes.length === 0` = 整体不可解析，显示「定义不可读 · 仅显示可解析部分」。**没有可解析输入**（文件不存在 / 无读权限 / 内容为空）按 ① 同样处理：`readable === true`、零节点，显示「定义 空」——三态表只约束"有文件输入"的情形，取不到输入的显示由文件存在性先行判定。`valid === false` 时**无论 `readable` 取哪一态**，都在标题旁标「校验不通过」。
- **证据**：节点的执行摘要（命令、退出码、关键输出行数、日志引用）与产物引用；完整日志留在宿主（基线 506 行、546 行）。
- **通知意图 / 投递结果**：前者是"该发一条通知"的判定与文案，后者是系统通知是否真的弹出；CI 只判前者与"失败不阻断"。
- **暂停**：实例仍在"运行中"，但推进被挂起，行上显示"（已暂停）"；与"已挂起"（等待人工裁决）不是一回事。

## 附录 D · 实现约束（技术要点，仅供编码参考，不进入验收判定）

> 本附录是需求对实现的约束摘要，写代码的 Agent 据此落地；评审对需求的判定不依赖本附录。

### D-1 新增数据接口与写入边界

既有 HTTP 面一律不动（只加不改）。新增只读接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/queue` | 跨实例待处理升级 + 待审批的统一队列快照 |
| GET | `/queue/stream` | 队列变化推送（SSE，500ms 合并） |
| GET | `/assets/roles`、`/assets/skills`、`/assets/workflows` | 三类资产列表（含校验状态） |
| GET | `/assets/roles/:id`、`/assets/skills/:id`、`/assets/workflows/:id` | 资产详情 |
| GET | `/occupancy/roles` | 全局角色占用 |
| GET | `/workflows/:id/canvas` | 定义态画布投影 |
| GET | `/evidence/:instanceId` | 节点证据列表 |
| GET | `/evidence/:instanceId/:nodeId` | 单节点证据 |
| GET | `/notifications/stream` | 通知意图推送（SSE） |

写入接口只允许下列五条，且必须经既有裁决/控制入口，不得直接改状态数组：

- `POST /queue/escalations/:id/decision`（`decision: pass|retry`；`cancel` 走下一条）
- `POST /queue/approvals/:id/decision`（`decision: allow|deny`）
- `POST /instances/:id/cancel`（终止，等价既有 `orch cancel`）
- `POST /control/pause` / `POST /control/resume`（托盘暂停/继续，逐实例调用既有 `workflow.pause` / `workflow.resume`）

决策必须经 `orchestrator.resolveEscalation` / `approval.resolve` 的 CAS 路径，**不得绕过 `transit()`**、不得在 HTTP 层写 `state.json`。五条写接口一律**一次处理一条**。

> **批量能力已按 D-01 移出本迭代范围**：本需求不提供多选、批量调用、批量汇总，也不存在"逐条循环调用"的批量授权；上表五条接口**只服务单条处置**（队列一次只处置一条，见 BR-25）。批量若在后续迭代引入，届时另立需求并重新评审写面。

### D-2 通知产生与去重

- 检测点全部落在守护进程对**既有事件总线**的订阅上，不改核心：① 新 `escalation` 进入 `pending`；② 实例状态变为 `completed`；③ 健康度转为 `需关注` 或实例状态变为 `failed` / `interrupted`（且不是由新升级引起，避免与①重复）。
- 去重键：升级用 `escalationId`（窗口 10s）；异常用 `(instanceId, kind)`（窗口 60s，窗口内累加 `mergedCount`）；完成用 `instanceId`（实例生命周期内一次）。
- 窗口实现必须是可注入时钟的纯调度器（`now` 参数 + 可注入定时器），便于用固定时钟断言 9999ms / 10001ms 边界。
- 投递由壳层执行；投递失败只记录 `delivered=false` 与原因，不重试、不抛异常、不阻塞事件消费。
- 暂停期间不产生新的完成 / 异常通知（暂停即不推进，自然满足）。

### D-3 队列投影与动作映射

- 投影来源：遍历本机实例，读 `state.escalations` 中 `state === 'pending'` 与 `state.approvals` 中 `state === 'pending'`；实例号、节点、角色、轮次从既有快照字段取，不重算。
- 排序：`type`（escalation 先）→ `id` 升序 → `instanceId` 升序。
- 动作映射：继续 → `pass`（仅 `rounds_exceeded`）；重派 → `retry`；终止 → 实例取消；允许 → `allow`；拒绝 → `deny`。**不暴露** `fail`。
- 错误映射：`ESCALATION_NOT_PENDING` → 已处理；`INSTANCE_NOT_SUSPENDED` → 不是挂起状态；`APPROVAL_NOT_PENDING` → 已处理；`APPROVAL_SESSION_GONE` → 已失效；动作错配由服务端返回显式 `ACTION_NOT_SUPPORTED`，界面映射为固定文案。
- 队列数字与托盘、列表必须同源：三处都读同一份投影，禁止各自计数。

### D-4 资产库投影

- 复用既有注册表读取与校验（`src/registry/*`、CLI 侧 `validate` 输出），**不在界面层重跑 schema 校验**，也不复制 CLI 渲染函数。
- 详情字段只透传：角色（分组 / `artifact_type` / 副作用 / `max_concurrent_sessions` / `skills` / `tools` / 唤醒白名单）、技能（适用 / 命令 / 摘要 / 正文前 N 行）、工作流（节点类型计数 / 边数 / 回流数）。
- 校验状态取该资产最近一次校验结果（缺失时现算一次并缓存到请求内）；失败原因必须与 CLI 原文逐字一致。
- 只读：任何资产接口都不得写 `.orch/roles|skills|workflows`。

### D-5 全局角色占用聚合

- 遍历本机全部实例 → 对每个实例调用既有 `buildRoleInstances`（或等价的只读投影）→ 按 `roleId` 合并：`instances` 计数、`activeSessions` 求和、`servingNodes` 并集、`status` 取"最忙"（服务中 > 可用 > 冷却中 > 不可用 > 未参与）。
- 注册表只补中文名与分组；**注册表为空不得把角色判 `unavailable`**（沿用既有投影口径）。
- 不落盘、不缓存跨请求、不写事件；实例状态不可读时跳过并计数。
- 与实例流程图同源：两处都使用同一份角色实例投影，不各算一套。

### D-6 工作流画布投影

- 输入：`.orch/workflows/<id>.yaml` 解析结果；输出：`{nodes, edges, title}`，节点不带运行时字段。
- 布局复用既有布局纯函数（`desktop/ui/graph/layout.js`），**不得复制第二套实现**；回流边按 `kind === 'backflow'` 走弧线。
- 节点类型只从 `node_type` 读；未知类型按角色节点渲染并保留 ID。
- `readable` / `valid` 按附录 B-1 的三态口径：整体解析成功（含"成功但零节点"）→ `readable=true`；部分可解析（有可画节点）→ `readable=false` 且 `nodes.length>0`，只输出可解析部分、**不得**显示「定义不可读」；整体不可解析 → `readable=false` 且 `nodes.length===0`，显示「定义不可读 · 仅显示可解析部分」。**没有可解析输入**（文件不存在 / 无读权限 / 内容为空）按"成功但零节点"处理：`readable=true`、`nodes` 空、显示「定义 空」。`valid` 与 `readable` 正交：`valid=false` 时恒在标题旁标「校验不通过」。

### D-7 证据投影

- 数据源：① `state.nodes[nodeId].artifactRefs`（含 `verifiedAt`）；② `events.jsonl` 中该节点最近一次 `execution.summary` 事件（`command` / `exitCode` / `keyOutputLines` / `logRef`）；③ 轮次取节点 `round`。
- 只读且只 `stat`：不得 `readFile` 日志正文，不得读会话消息内容；引用不存在时单项标 `unreadable`。
- 响应体对每节点给出固定五项 + 轮次，缺项为 `null`（界面渲染为 `未提供`）。
- 与 I1.10b 的接口约定：将来节点详情可直接复用本投影，调用方不变；本迭代不提供跳转入口。

### D-8 托盘与暂停

- 菜单：信息行（只读项）→ 打开主窗口 → 暂停/继续 → 退出；信息行文本由守护进程投影计算后下发，壳层只渲染，不重算。
- 暂停：逐实例调用既有 `workflow.pause`，收集成功/跳过；全量失败不报错，返回"N 已暂停 / M 已跳过"；无运行中实例时菜单项 `enabled=false`。
- 退出路径保持 I1.10a 原样（确认 → 停止 → 结束进程）；暂停不等于退出，也不触发停止。
- 托盘数字每 2 秒或收到推送时更新；守护进程断开时置 `null` 显示"—"。
