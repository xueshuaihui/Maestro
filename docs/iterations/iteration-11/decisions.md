## D-01 · 批量处置：判为越界，移出范围

- **触发点**：`review-round1.md` F-18 / F-16 / F-17；需求 §2.4、BR-09、AC-13 引入了「多选同类条目批量执行同一动作 + 逐条回报 + 批量终止确认句」。
- **依据**：规划 881 行原文只有「一键继续/重派/终止/允许/拒绝」，**没有多选与批量语义**；执行模板红线 14「不许夹带规划之外的新能力」，且 §1.2「不能为了让覆盖表变绿而改方向」同样禁止反向扩张。
- **决定**：**删除批量能力**——删除 BR-09；AC-13 的批量现场改为「跨实例两条目分别处置、互不影响、三处数字各自同步」（该场景是 BR-13 三处数字一致的必需覆盖，规划 881 统一队列 + I1.10a 实例列表「待处理数」均有来源）；BR-12 去掉「批量终止确认句带条数」；§2.4 的批量段与 A-4 的批量确认句同步删除。批量作为后续迭代（I1.12 或更后）的候选，写入 §1.3 范围外。
- **影响面**：BR 由 36 条降为 35 条；AC 仍为 43 条（编号不变，AC-13 主题变更）；§2.4、§2.11、附录 A-4、AC-11/13/16 需同步；附录 C 记录本次删除。

## D-17 · 「定义 空」与「定义不可读」的分工：按「有没有可解析输入」划

- **触发点**：修复 Agent 回执问题 2；F-03 要求两处文案分明。

- **决定**：确认修复方写法——**文件不存在 / 无读权限 / 内容为空 → 「定义 空」**；**文件在但整体不可解析 → 「定义不可读 · 仅显示可解析部分」**。两处文案在 A-7 各占一行，AC-31 分现场逐字断言。

## D-19 · 审批行的「第 N 轮」取所属节点当前轮次，缺节点时显示「—」

- **触发点**：修复 Agent 回执问题 4；`state.approvals[]` 的既有字段是 `approvalId / nodeId / sessionId / action / state / createdAt`，**没有轮次字段**。

## D-21 · 门禁判据不得写 `fail === 0`：本基线本身有 4 条已裁决失败

- **触发点**：`review-round2.md` G-04；§3.3 写「后续各批门禁 `fail === 0 && pass === tests && tests >= 1425`」。
- **依据**：主控实测基线 `1425 / 1420 pass / 4 fail / 1 skip`，那 4 条是**已裁决的允许项**（历史 8 条中的 3 条 + 裁决 R-08 的 AC-04）。写 `fail === 0` 会让每批门禁**永远红**，等于逼实现方去改历史断言——正是红线 1 禁止的事。
- **决定**：门禁判据统一为「**失败集合与判定基线（历史 8 条 + 裁决 R-08 的 AC-04）差集为 0，且 `tests >= 1425`**」。仓库已有同口径实现 `scripts/desktop/gate.mjs`（TAP 解析 + 基线差集 + 条数下限 + 文件级 flake 确认），I1.11 的门禁**复用该口径**，不许另写一套「零失败」判定。
- **影响面**：§3.3、AC-41、S2 各批任务书、S4 报告。

## D-22 · AC-17 审批行不比对「逐字相同」，只比字段值

## D-56 · AC-27 `unavailable` 锚点归位：禁的是「自造状态」，不是引用既有词表键
