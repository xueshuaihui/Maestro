## 一、背景与问题

### 1.1 现状与问题

到 I1.9 收口时，Maestro 的“能做事”已经齐了：实例能跑、能回流、能升级、能算健康度、能展开追踪。但**人要看这些结论，只能回到终端**：

- 用户想知道“现在有几个实例、哪个要管”，必须逐个执行 `orch status` / `orch instance status`，再把四档健康度、待处理数、进度在心里拼起来；实例一多就拼不过来。
- 角色之间的协作关系**根本看不见**。谁在服务谁、哪条交接被拒绝、哪条在等投递、哪条已回流过一轮，今天只能从事件行里逐条读；角色级的“团队在怎么协作”这件事没有一屏能回答。
- 含人工节点、升级节点、子工作流的实例，今天在 CLI 里只是一串节点行；拓扑是否完整、有没有悬空的边，用户无从判断。
- 即使有人愿意一直开着终端，**也不会有人一直盯着终端**。没有常驻的桌面入口，没有托盘，没有“关掉窗口也不影响后台继续跑”的形态。
- 规划里已经定义的实时推送能力（角色变化实时、连接线 1 秒合并、会话变化不重绘）今天完全没有承载者；没有界面，也就没有任何可验证的节奏。

不解决会怎样：阶段一的退出条件是“桌面应用可独立完成日常操作，不依赖 CLI 或浏览器”（`docs/index.md` 629 行、913 行）。I1.10a 是这条退出条件的**第一块地基**——没有它，后面的下钻（I1.10b）、通知与人工干预队列（I1.11）都无处挂载；同时“角色流程图能否完整表达含人工/子工作流的拓扑”这条关键判断点（1042 行）也无从裁决。

### 1.2 目标与成功衡量

做完之后，用户可观测的变化：

1. **双击就能看全局**：双击应用图标，3 秒内主窗口出现并列出全部实例，每行同时给出工作流、阶段、进度、待处理数与健康度；不打开终端、不打开浏览器。
2. **一屏看懂协作**：点击任一实例进入角色流程图，角色节点的状态色、活跃会话数、服务节点、宿主与异常角标一屏可见；连接线的 7 种聚合状态各有固定视觉；回流是反向弧线而不是新的一条正向线。
3. **特殊拓扑不缺角**：含人工节点、升级节点、子工作流折叠组的实例，图上节点与边齐全、没有悬空端点；子工作流以折叠组呈现并标注角色数。
4. **关窗不中断**：关闭主窗口后窗口消失、托盘常驻、守护进程继续运行（同一进程号、实例状态可继续读取）；只有从托盘“退出”才真正停止。
5. **界面不打摆子**：角色变化实时到达（≤500ms）；同一连接线 1 秒内多次变化只刷一次、且是最后一次的状态；会话状态变化只更新指示器通道，不触发流程图重排。
6. **零回归、零新依赖**：CLI 与核心既有输出逐字不变，`dependencies` 仍为 `{}`，全量测试失败集合与 I1.9 收口基线差集为 0。
7. **发版不再靠某台机器**（v3 新增）：维护者推一个 `v*` tag，就能在 GitHub Releases 拿到三个平台的可下载安装包与校验和清单；不要求任何人在自己电脑上手工构建、手工传包，也不需要个人凭据。衡量口径：一次 tag 推送后，Releases 页出现该版本条目，访客能下载到与版本、架构对应的安装包；质量门禁或产物冒烟没过时**不产生**可下载的包。

### 1.3 范围

**范围内（本次让用户获得的新能力）**：

- **桌面应用壳**：Tauri 优先的可双击启动应用；主窗口；系统托盘常驻；关闭窗口缩到托盘、守护进程继续运行；托盘菜单只有“打开主窗口 / 退出”两项，退出前对运行中实例做一次确认。用户机器上不需要预装 Node / Rust / Python 等运行时（这是用户可见结论，实现路径见附录 D-14，不进验收判定）。
- **全局实例列表**：实例 ID、工作流、阶段、进度、待处理数、健康度六项一屏并列；按健康度分档置顶；空态、不可读实例、实例增减都有明确表现。
- **新建实例入口**：在应用内选工作流 → 填任务说明 → 启动；成功、校验失败、启动失败三条路径都有中文反馈，全程不离开应用。

### 2.2 桌面壳与系统托盘：用户能做什么，看到什么

- **使用角色**：所有用户；尤其是同时照看多个实例、需要长期挂着界面的人。
- **使用场景**：一天开始时打开应用看全局；工作中把窗口关掉但仍希望后台实例继续跑；一天结束时从托盘退出。
- **用户操作**：
  - 双击应用图标启动。
  - 第一次使用时，主窗口提示填写**项目目录**；填入后进入实例列表，之后再次双击会直接进入上次的项目。
  - 关闭主窗口（点窗口关闭按钮）；需要时从托盘图标重新打开主窗口。
  - 需要彻底停止时，从托盘菜单选“退出”。
- **预期效果**：
  - 双击后 3 秒内主窗口出现，默认就是实例列表，不需要先登录、不需要开终端、不需要打开浏览器。
  - 关闭窗口后窗口消失，**托盘图标仍在**，后台守护进程继续运行；已运行实例的进度继续推进，再从托盘打开窗口时看到的是最新状态。
  - 托盘菜单固定两项：“打开主窗口”“退出”。
  - 托盘“退出”时，如果还有实例在运行，先弹一次确认（逐字见附录 A-6）；确认后守护进程停止、托盘消失；没有运行中实例时直接退出。
  - 应用自带运行环境：用户机器上不需要预装 Node、Rust、Python 之类的东西。
- **异常情况**：
  - 项目目录没填或填了不存在的目录：主窗口停在提示页，显示“项目 未指定 · 请填写项目目录”或“项目 不可用 · {path}”，不进入列表、不崩溃；填入一个可用目录后进入实例列表。
  - 守护进程还没起来：列表区显示“正在连接守护进程…”，连上后自动换成列表；超过 10 秒仍连不上则显示“连接守护进程失败 · 请确认项目目录后重试”，并保留“重试”入口，点重试后无需重开应用。
  - 用户重复双击图标：不产生第二个窗口、不产生第二个守护进程；已有窗口被激活到前台。
- **边界说明**：本迭代一个窗口只服务一个项目根；不做多窗口、不做项目切换器、不做通知与托盘计数（后者属 I1.11）。桌面通道在守护进程启动时开启；本迭代不提供对“已在运行、但未开桌面通道的守护进程”中途开启的入口（登记见附录 B 的 U-13）。

### 2.3 全局实例列表：用户能做什么，看到什么

- **使用角色**：同时有多个实例的人、值班人、刚接手项目的人。
- **使用场景**：打开应用先看“现在有哪些实例、哪个需要我处理”。
- **用户操作**：打开主窗口（默认页面）；点击任意一行进入该实例的角色流程图；用列表上方的“新建实例”启动新实例。
- **预期效果**：
  - 每一行固定六项，顺序固定：实例 ID、工作流、阶段、进度、待处理数、健康度（逐字见附录 A-1）。
  - 工作流显示中文名（单节点 / 编码闭环 / 通用任务闭环）；阶段显示实例当前状态（运行中、已挂起、已完成、已取消、失败、已中断等）；进度显示“已完成节点数 / 节点总数”；待处理数是待处理升级与待审批之和；健康度是四档之一。
  - 排序固定：需关注 → 慢 → 正常 → 已结束；同一档内按最近更新时间倒序。异常实例永远在最上面，用户不需要自己找。
  - 鼠标停在健康度上，能看到具体原因（复用 I1.9 的原因句，逐字见附录 A-7）；原因句只来自既有八类，没有原因时只显示“健康度 正常”，不自造新句。
  - 列表会自己变：新实例启动后 2 秒内出现在列表里；实例状态或健康度变化后 2 秒内该行更新；不需要手动刷新，也没有“刷新”按钮。
  - 没有实例时显示“实例 无”，并保留“新建实例”入口。
  - 某个实例的状态文件坏了：该行仍出现在列表里，显示“实例 {id} · 状态不可读”，其余行照常可用。
- **异常情况**：守护进程断开时，列表保留最后一次看到的内容并显示“已断开 · 正在重连…”，恢复后自动补全；不把旧内容当成最新状态悄悄留在屏幕上。
- **边界说明**：列表只给实例级结论（基线 424 行“不展示角色和节点”）；角色与节点信息只在点进实例后出现。

### 2.4 新建实例：用户能做什么，看到什么

- **使用角色**：想立刻起一个工作流的人。
- **使用场景**：刚看完列表，想直接开一个新任务，不想切回终端。
- **用户操作**：点“新建实例” → 在面板里选工作流（单节点 / 编码闭环 / 通用任务闭环）→ 填写任务说明 → 点“启动”。
- **预期效果**：
  - 三个工作流都是当前真正能跑的；默认选中“单节点”。
  - 启动成功后，面板关闭，列表顶部附近出现带提示“已启动 {id}”，该实例 2 秒内以“运行中”出现在列表里。
  - 编码闭环 / 通用任务闭环需要任务说明里带“产物：…”那一行时，界面按既有规则原样接受，不做额外加工。
- **异常情况**（逐字见附录 A-5）：
  - 没选工作流就点启动：提示“请选择工作流”，面板不关闭。
  - 任务说明为空：提示“请填写任务说明”，面板不关闭、不发起。
  - 工作流对任务说明有要求但没满足（例如编码闭环缺少“产物：”一行）：显示与 CLI 完全一致的既有提示（`ERROR_TEMPLATE` 里的原文），面板不关闭，不产生实例。
  - 启动时宿主失败 / 目录冲突 / 实例已存在：显示 `启动失败 · <既有错误原文>`（逐字见附录 A-5 最后一条），面板不关闭，列表不变。
  - 无论哪种失败，界面都保持可用，不白屏、不打印堆栈。
- **边界说明**：面板只负责“选工作流 + 填任务说明 + 启动”三件事；不提供宿主选择、并发参数、权限策略等高级项（这些仍走 CLI 或后续迭代）。

### 2.5 数据怎么送到界面：快照与实时推送

- **使用角色**：使用界面的所有人；以及需要确认“界面数字是否可信”的验收方。
- **使用场景**：打开某个实例的流程图；实例在后台继续运行；网络/进程短暂断开后恢复。
- **用户操作**：正常浏览，无需操作。
- **预期效果**：
  - 进入流程图时界面先拿到一份**完整快照**（节点、连接线、图例），一次画全。
  - 之后的变化通过一条**本机推送通道**送过来：角色状态变化立即推；连接线聚合状态变化 1 秒内只推一次；会话状态变化只推指示器类事件。
  - 只有图元素真的变了界面才重画：节点状态、连接线、特殊节点、实例状态变化会重画对应部分；会话状态变化不会让流程图重绘，也不会挪动任何节点。
  - 断线后界面显示“已断开 · 正在重连…”，恢复连接时重新拿一份完整快照，丢掉断线期间的中间状态，只保留最新状态，不重复叠加。
  - 这条通道只在本机回环地址上开、每次启动换一个访问凭据；界面之外的进程拿不到凭据就取不到数据。
- **异常情况**：实例已被删除或从未存在：界面显示“实例 {id} · 不存在”，并可返回列表。某条连接线的聚合状态在 1 秒内反复变化：界面只看到最后一次，不会闪 5 次。会话在 1 秒内连续变化多次：流程图坐标与尺寸不变，不重排。
- **边界说明**：本迭代只提供“读”与“新建实例”两类数据交互；推送使用规划允许的 WebSocket/SSE 中的一种（本需求取 SSE，见附录 B 的 U-5 与附录 D 的 D-2）。字段级契约、事件名与连接方式不属于用户可见范围，见附录 D。

### 2.6 角色流程图上的角色节点：用户能做什么，看到什么

- **使用角色**：需要判断“谁在干活、谁闲着、谁挂了”的人。
- **使用场景**：进入实例流程图，想快速知道每个角色此刻的状态与服务对象。
- **用户操作**：点击列表里的实例进入流程图；鼠标悬停角色节点（高亮其所有上下游连接线，其它元素降低不透明度）；双击角色节点（进入聚焦模式，见 §2.10）。
- **预期效果**：每个角色节点固定五要素（逐字见附录 A-9）：
  - **状态色**：可用（绿）/ 服务中（蓝）/ 冷却中（灰）/ 不可用（红）/ 未参与（灰、弱化）。同一时刻只呈现一种。
  - **活跃会话数**：服务中时显示“N 个活跃会话”；N 大于 1 时角标堆叠（例如 `×2`），用户一眼知道这个角色同时开了几条会话。
  - **服务节点**：当前绑定的节点编号列表，多个用 `, ` 分隔（例如 `服务 T-001, T-002`）；超过 2 个时折叠为“服务 T-001 等 3 个”。
  - **宿主图标**：右下角标出该角色所在宿主（DSH / Cursor / GPT / WorkBuddy）；一个角色跑在多个宿主上时并列显示。
  - **异常角标**：该角色身上挂着“已升级”节点时，右上角出现红色感叹号角标，并显示异常数量。
- **异常情况**：角色不可用（会话崩溃或宿主不可达）时显示红色状态点，节点本身仍可读、仍能看出它服务过哪些节点；角色未参与本实例时不参与路由，以灰色弱化显示，不显示活跃会话。
- **边界说明**：角色节点只表达角色级信息（基线 547 行）；节点级与会话级细节在 I1.10b 的下钻里看。

### 2.7 特殊节点：人工、升级、子工作流

- **使用角色**：使用含人工验收、升级裁决、子流程的工作流的人。
- **使用场景**：进入一个拓扑里带人工节点或子流程的实例，确认“该有的节点都在、该连的线都连上了”。
- **用户操作**：正常浏览流程图；把鼠标停在特殊节点上看提示。
- **预期效果**（逐字见附录 A-10）：
  - **人工节点**：灰色盾牌图形，状态复用节点状态词（待执行 / 执行中 / 待校验 / 已完成 / 已升级等）；标签显示节点标题。
  - **升级节点**：红色感叹号图形，状态复用节点状态词；有升级待处理时角标为红色并带脉冲。
  - **子工作流**：折叠组节点，标注“子工作流：{name} · N 角色”；N 是该子工作流里角色节点的个数。子工作流内部只要有一个“已升级”节点，折叠组就显示为异常（红色），否则为正常。
  - 三类特殊节点**参与拓扑**：定义里连到它们的边、从它们出发的边都画出来；不会出现“线连到画布外”或“节点悬空”的情况。
- **异常情况**：
  - 子工作流定义读不到：折叠组仍显示，标注“子工作流 {id} · 角色数未知”，状态为灰色、不显示红色脉冲，流程其余部分照常可用（提示逐字见附录 A-13）。
  - 特殊节点在运行时状态里没有记录：按“待执行”呈现，不隐藏、不报错。
- **边界说明**：点击特殊节点本迭代**不跳转、不下钻**（人工任务详情、升级队列、子工作流内部图都属 I1.10b）；只做选中与高亮。

### 2.8 连接线：7 种聚合状态与回流弧线

- **使用角色**：关心“交接走到哪一步、有没有被拒绝、回流了几轮”的人。
- **使用场景**：一次交接被拒绝或过期；一次回流发生；并行交接同时发生。
- **用户操作**：看连接线；悬停连接线高亮两端角色、其余元素降低不透明度。
- **预期效果**：
  - 每一对角色之间，**正向一条线、回流一条弧线**，分开画。回流永远画成反向弧线（从下游回到上游的弧），并保持同一对角色只出现两条（正向 + 回流）。
  - 连接线有 7 种聚合状态，每种固定视觉（逐字见附录 A-11）：已拒绝（红色实线 + 回流箭头）、已过期（橙色虚线 + 感叹号）、待投递（黄色虚线）、已投递（蓝色实线 + 流动动画）、已接受（蓝色实线 + “处理中”）、已完成（绿色实线）、未开始（灰色虚线，默认隐藏，可在工具栏打开显示）。
  - 同一方向有多条并行交接时合并为一条线，线加粗并标注“N 并行交接”。
  - 同一对角色存在多个交接包时按固定优先级取一个总状态：已拒绝 > 已过期 > 待投递 > 已投递 > 已接受 > 已完成 > 未开始。
  - 多轮回流只在弧线上体现“最近一轮”；历史轮次的细节留给 I1.10b 的连接线详情。
- **异常情况**：没有交接包的角色对显示“未开始”（默认隐藏）；连接线指向的角色在当前视图被折叠时，线改为连到组节点，不留下悬空线。
- **边界说明**：连接线是派生视图，不单独审计（基线 628 行）；本迭代不提供点击展开交接包列表（I1.10b），点击红色/橙色连接线也不跳转升级处理面板（I1.11，见 §1.3 范围外）。

### 2.9 布局：从左到右的层次、同层并行、回流不改层次

- **使用角色**：所有看图的人。
- **使用场景**：实例角色多、有并行、有回流。
- **用户操作**：无需操作，进入即按固定规则排布。
- **预期效果**：
  - 按工作流拓扑层次从左到右排列：入口角色在最左，下游依次向右；同一层有多个角色时上下并排。
  - 回流边**不改变层次**，只画成反向弧线；不会因为有一条回流就把上游角色推到右边去。
  - 同一份数据、同一窗口尺寸下，两次打开得到的位置完全一致（不会每次打开都换一个排法）。
  - 图例固定在画布左下角，两行说明状态色、特殊节点与正向/回流线（逐字见附录 A-8）；缩放与平移不改变它的锚点位置。
- **异常情况**：图里存在定义层可达但运行时无状态的节点时，按“待执行”占位，不影响其它节点的层次；若某条边两端节点都被折叠，连线改挂到组节点（见 §2.10）。
- **边界说明**：本迭代不做自动换行/自动适配窗口大小的动态重排；窗口缩放只影响观看缩放比例，不改变布局坐标。

### 2.10 交互：缩放平移、聚焦、折叠、拖拽

- **使用角色**：需要在大图里定位的人。
- **使用场景**：图超出可视区域；想只看某条链路；角色太多看不下；想按自己的习惯摆放节点。
- **用户操作**与**预期效果**：
  - **缩放平移**：滚轮/触控板缩放，范围 50%–200%（到边界不再继续缩小/放大）；拖动空白处平移画布；工具栏“复位视图”一次性恢复 100%、回到原点、清除手动拖拽偏移。
  - **聚焦模式**：双击任一节点进入聚焦，只显示该节点 2 跳以内的节点与它们之间的线；画布顶部显示“聚焦 {nodeId}（2 跳）”与“退出聚焦”；按 Esc 或再双击退出，恢复全图。聚焦不改变节点的相对层次。
  - **折叠分组**：子工作流始终以折叠组呈现（本迭代不展开内部）；当图里可见的角色节点超过 12 个时，自动按角色所属分组折叠为组节点，组节点标注“分组 {group} · N 角色”；每个组节点可单独展开/收起，展开后组内角色出现在原层次位置，组间连线自动改为连接组节点。
  - **手动拖拽**：拖动任一节点改变位置；该位置按实例记住，下次打开同一实例时仍然生效；不同实例互不影响；复位视图会清除拖拽偏移。
- **异常情况**：拖拽后实例被删除/重建：视图偏好按实例号失效即忽略，不报错；折叠状态下双击组节点不进入聚焦（组节点不是可聚焦对象）。
- **边界说明**：点击（单击）角色/特殊节点本迭代只做选中高亮，不进入下钻（I1.10b）；不做框选、多选、连线编辑。

### 2.11 异常高亮：角标 + 红色脉冲，不改变尺寸

- **使用角色**：值班人、正在盯异常的人。
- **使用场景**：某个角色身上有“已升级”节点，或某条连接线被拒绝/过期。
- **用户操作**：无需操作。
- **预期效果**：
  - 异常角色/特殊节点右上角出现红色感叹号角标，并带**红色脉冲**（呼吸式明暗），在满屏节点里第一眼就能看到。
  - 异常元素**浮到最上层**（不被其它节点或连线遮挡），但**位置、宽度、高度都不变**；其它节点也不因它异常而挪位。
  - 异常连接线同时按 §2.8 的视觉编码呈现（红色实线 + 回流箭头 / 橙色虚线 + 感叹号）。
- **异常情况**：多个异常同时存在时，全部带角标与脉冲，不做“只留一个”；异常解除后角标与脉冲立即消失，位置仍然不变。
- **边界说明**：脉冲只是视觉效果，不改变布局、不触发重排、不影响点击命中区域大小；点击角标本迭代不跳转升级处理面板（属 I1.11）。

### 2.12 节点看板：可选的另一种看法

- **使用角色**：习惯看板的人；需要按任务状态清点的人。
- **使用场景**：流程图看不出“有多少任务卡在待校验”，切到看板一眼清点。
- **用户操作**：在流程图右上角切到“节点看板”；需要时切回“流程图”。
- **预期效果**：
  - 看板固定 7 列，顺序固定：被阻塞、可调度、执行中、待校验、已完成、失败、已升级（逐字见附录 A-12）。
  - 每个节点卡片只落在其中一列：待执行但上游还没全部完成的在“被阻塞”，上游全部完成（或没有上游）的在“可调度”；已取消的节点折叠在“已完成”列的“已取消 N”里，默认不占卡片。
  - 本迭代看板**只读**：不能拖动卡片、不能在列间移动、不能批量操作。
  - 切回流程图时，缩放、平移、拖拽偏移、折叠状态都还在，不会被重置。
- **异常情况**：某节点状态不在 7 列映射范围内（例如旧数据里的未知值）：落到“被阻塞”列并在卡片上标注“状态未知”，不丢卡片、不崩溃。
- **边界说明**：看板是实例内全部节点的另一种视图；角色下钻里的卡片列表属 I1.10b，两者不是同一个东西。

### 2.13 标签策略与推送节奏

- **使用角色**：长时间开着界面的人。
- **使用场景**：图很大、线很多；实例在后台频繁变化。
- **用户操作**：不用操作；需要细节时把鼠标停在连接线上。
- **预期效果**：
  - **标签策略**：默认只显示**异常标签**（已拒绝 / 已过期 / 待投递）；已完成、已接受、已投递、未开始这些正常状态的标签平时不显示，鼠标悬停到该连接线上才显示；移开即恢复。角色节点上的服务节点、活跃会话数、宿主图标属于节点内容，始终显示，不受这条规则影响。
  - **角色实例实时推送**：角色状态一变（可用→服务中、服务中→不可用等），界面 0.5 秒内看到新颜色。
  - **连接线合并**：同一条连接线在 1 秒内变化多次，界面只刷一次，且刷出来的是这一秒里最后一次的状态；不会出现连续闪 5 次。
  - **会话状态不重绘流程图**：会话状态变化不改变流程图上任何节点的位置与尺寸，也不触发流程图重绘；只有当这次变化真的改变了角色状态或异常角标时，才升级为一次角色更新。
- **异常情况**：一秒内既有角色变化又有连接线变化：角色变化立即到、连接线变化按窗口合并到；两者互不阻塞。
- **边界说明**：卡片上的会话指示器本身属 I1.10b；本迭代只保证“不重排”和“事件已按指示器类型分好类”。

### 2.14 功能之间的衔接

把 §2.2 ~ §2.13 串起来，用户走完一遍是这样一条体验：

1. **双击打开（§2.2）**：主窗口出现，默认是实例列表；第一次用时填一次项目目录，之后直接进入。
2. **一眼分诊（§2.3）**：列表按“需关注 → 慢 → 正常 → 已结束”排好，最上面那行就是现在最该看的那一个；鼠标停在健康度上能看到原因。
3. **没有实例就直接开一个（§2.4）**：点“新建实例”，选工作流、写任务说明、启动，新实例 2 秒内以“运行中”出现在列表里。
4. **点进实例看图（§2.6 ~ §2.9）**：点一行进入角色流程图，先拿到完整快照一次画全；角色节点五要素、特殊节点、连接线 7 态、回流弧线、层次布局一次到位，图例在角落说明怎么读。
5. **图太大就用交互（§2.10）**：缩放平移、双击聚焦 2 跳、角色超过 12 个时按分组折叠、拖到自己顺手的位置并记住；复位视图一键回到默认。
6. **异常一眼看到（§2.11、§2.13）**：异常角色带角标与红色脉冲浮在最上层，位置不挪；默认只显异常标签，正常标签悬停才出现。
7. **让它自己更新（§2.5、§2.13）**：角色变化实时到、连接线变化 1 秒合并、会话变化只动指示器不重排；断线自动重连并补全量快照。
8. **换一种看法（§2.12）**：切到 7 列节点看板清点任务，再切回流程图，缩放与位置都还在。
9. **关窗走人（§2.2）**：关闭窗口，窗口消失、托盘还在、后台继续跑；回来从托盘打开，看到的还是最新状态；要彻底停止才从托盘“退出”，有实例在跑时先确认一次。

**走不通时用户看到什么（降级分支，同样属于本迭代的衔接体验）**：

- **守护进程不在 / 连不上（§2.2、§2.3）**：列表区先显示“正在连接守护进程…”，超过 10 秒仍连不上则转为“连接守护进程失败 · 请确认项目目录后重试”并出现“重试”；点“重试”，守护进程就绪后列表补全，不需要重开应用。（AC-30 覆盖）
- **图数据取不到（§2.5、§2.7）**：实例不存在时停在“实例 INST-999 · 不存在”，可返回列表；工作流定义读不到时提示“流程图定义不可读 · 已按内置模板显示”，其余元素照常；子工作流定义读不到时折叠组显示“子工作流 child-x · 角色数未知”，其余图照常可读。（AC-30 覆盖）
- **新建实例启动失败（§2.4）**：面板不关闭，显示 `启动失败 · <既有错误原文>`，列表实例数不变，用户可改参数再点“启动”。（AC-06 覆盖）
- **连接断开又恢复（§2.5、§2.13）**：断开期间保留最后一次看到的内容并显示“已断开 · 正在重连…”，恢复后重新取一份完整快照、丢掉断线期间的中间状态，只保留最新状态，不叠加。（AC-08 覆盖）

简言之：**打开就分诊（§2.2/§2.3）→ 需要就新建（§2.4）→ 点进看协作（§2.6–§2.9）→ 用交互定位（§2.10）→ 异常一眼可见（§2.11/§2.13）→ 自己保持最新（§2.5/§2.13）→ 看板换视角（§2.12）→ 关窗不打断（§2.2）**，构成一次完整的“日常值守”闭环，不需要终端；中途任何一步走不通，都有上面四条中文降级路径，不会白屏或停在无说明的状态。

### 2.15 用户可见的业务规则

- **BR-01**：双击应用图标后 3 秒内出现主窗口并停在实例列表；关闭主窗口只隐藏窗口、缩到托盘，守护进程不停止；只有托盘“退出”才真正停止守护进程；有运行中实例时退出前必须先确认一次。

- **BR-05**：没有实例时显示“实例 无”；实例状态文件损坏时该行仍出现并显示“状态不可读”，不隐藏、不阻断其它行。

## 三、验收标准（用户视角）

### 3.1 功能验收标准（AC）

> **判定口径（五条，所有 AC 适用）**：
>
> 1. **界面输出的一致性判定**：界面里看到的列表行、节点行、连接线、图例与看板列，由 `desktop/ui` 下的纯渲染模块生成；验收用 `desktop/harness/*.mjs` 直接 import 同一批模块并对文本/结构逐字断言。窗口只是这些模块的宿主，不另写一套渲染逻辑。
> 2. **窗口与托盘的判定**：应用接受 `--probe <文件>` 与 `--ctl <目录>` 两个仅测试用参数；启动、窗口显隐、托盘创建、菜单触发、退出都会把事件追加到探针文件，控制目录里的 `close-window` / `tray-quit` / `tray-quit-confirm` 文件用于触发与真实菜单项相同的处理函数。验收读探针文件、并独立核对守护进程进程号与状态。
> 3. **夹具口径**：每个 AC 使用独立项目根，放在 `/tmp/maestro-i10a-*` 下，绝不进仓库；一律注入 `NODE_ENV=test`；宿主一律 `--host mock`（`.orch/hosts/mock.json` 指向仓库内 `test/fixtures/mock-acp-agent.js`）；本迭代验收**不依赖真实 DSH**。
> 4. **机检命令形态**：所有文本扫描一律用 `grep -E` / `grep -RE`（ERE 交替）或 `rg`，**禁止** `grep "...\|..."` 这类 BRE 交替写法——本机 `grep` 是被替换过的 toybox shim，`\|` 恒不匹配，会让违规代码也输出“零命中”而假通过。每条架构检查必须写明期望结果：“零命中（exit 1）”或“恰好 N 条命中（exit 0）”。含中文的扫描同样走 `grep -RE` 或 `rg`。
> 5. **测试执行方式**：每条机检点名的测试文件一律**直接运行**，且命令形态为先断言文件存在再运行：`test -f test/wp13/<file>.test.js && NODE_ENV=test node --test test/wp13/<file>.test.js`，并断言 `# pass ≥ 1`、`# fail 0`；不得用 `test/**/*.test.js` 全量 glob 代替——文件缺失时 Node 22 会以 `fail 0 / exit 0` 静默返回，等于假通过，因此 `test -f` 前置断言不可省略。
>
> AC 标题沿用本项目既有的 `**AC-xx · …**` 形态（不改为 `#### AC-`）；机械取号用 `grep -cE '^\*\*AC-'`。

**AC-01 · 双击应用图标打开主窗口，停在实例列表**
- 场景类型：功能 / 桌面壳
- 风险：高（规划验收句第一段的直接判据）
- 引用：BR-01, BR-02, BR-03

- 夹具：静态契约机检只用仓库内文件，不读写 `/tmp` 业务数据；真实面用一次性 `v0.x.y` 测试 tag（用后删除，取证帧保留在 `evidence/`）。
- 架构检查：发布定义不得引入 `package.json` 的 `dependencies` / `devDependencies` 新条目（BR-22 红线）；不得改动 `src/**`、`desktop/ui/**` 的既有行为；`grep -REn "secrets\\.[A-Z]" .github/` 除仓库自带凭据外**零命中**。

**AC-39 · 三平台安装包与校验和齐全且对得上**
- 场景类型：功能 / 产物分发（v3 新增）
- 风险：高（缺一个平台或校验和对不上，用户下载到错包/坏包）
- 引用：BR-34, BR-38
- **Given** 某次 tag 的构建全部完成，用户打开该版本的 Releases 页。
- **When** 用户下载页面列出的安装包与校验和清单，并自行核对下载文件。
- **Then** 能拿到 macOS Intel、macOS Apple Silicon、Windows x64 三个安装包，文件名带版本与架构；另有一份 `SHA256SUMS.txt`，清单里每一行都能对上实际下载到的文件、逐行校验一致；不出现「清单有但页面没有」或「页面有但清单漏掉」的条目。
- 机检：`node probe/acc10-release-verify.mjs <tag> --check assets` 取远端资产名与字节数，断言三平台包 + 清单共 4 项齐全、架构后缀齐全；下载后本地重算 SHA-256 与 `SHA256SUMS.txt` 逐行比对并落 `evidence/`。
- 夹具：真实 Release 页面；不使用伪造的本地资产目录冒充。
- 架构检查：三个平台各自在自家构建机上产出，不做跨架构装配（包内运行时架构与构建机架构必须一致，不一致即判失败）；`grep -REn "universal|fat-binary" .github/ scripts/` 零命中。

**AC-40 · 门禁与产物冒烟不过就不出包**
- 场景类型：非功能 / 发布可靠性（v3 新增）
- 风险：高（否则会把跑不起来的包发出去）
- 引用：BR-37
- **Given** 某次改动让质量门禁不过，或构建出的应用无法启动 / 鉴权守卫失效 / 签名丢失。
- **When** 维护者照样推一个 tag 触发发布。
- **Then** 构建记录显示失败并给出可读的失败环节；**该次发布不产生任何新的可下载资产**；用户不会在 Releases 页看到一个跑不起来的包；修复后重推同名 tag 能重新出包。
- 机检：`test -f test/wp13/release-contract.test.js && NODE_ENV=test node --test test/wp13/release-contract.test.js` 静态断言门禁步骤在打包步骤之前、产物冒烟步骤在上传步骤之前、且冒烟覆盖「应用可启动 + 鉴权守卫 + 签名验签 + 安装包完整性」四项；`node probe/acc10-release-verify.mjs <tag> --check gating` 断言失败构建的 Release 资产数为 0。
- 夹具：构造一次故意失败的试跑（走 AC-42 的草稿通道），保留失败原始帧，不污染正式 Releases。
- 架构检查：质量门禁调用的是仓库既有判定命令（全量单测失败集合与基线差集为 0），不得为发布单开一套宽松判定；冒烟脚本不得用 `--skip-smoke` / `--skip-gates` 跳过。

**AC-41 · 版本与通道：包内版本一致、预发布与正式版不串档**
- 场景类型：功能 / 版本管理（v3 新增）
- 风险：中（版本串档会让用户装到旧代码却以为装了新版）
- 引用：BR-35, BR-34
- **Given** 仓库里应用版本号只有一个来源。
- **When** 分别推 `v0.x.y` 与 `v1.0.0` 两种 tag。
- **Then** 前者在 Releases 页标「预发布」、后者标正式版；两种情况下安装包文件名里的版本都与包内版本一致；改一处版本号后，产物名、包内版本、清单同步变化，不出现四处各写各的。
- 机检：`test -f test/wp13/release-contract.test.js && NODE_ENV=test node --test test/wp13/release-contract.test.js` 断言版本单点（其余位置由同一来源派生或校验对齐）、`v0.* → 预发布` 与 `v1+ → 正式` 两条分支都在；`node probe/acc10-release-verify.mjs <tag> --check channel` 断言远端 `prerelease` 标记与 tag 前缀一致。
- 夹具：两种 tag 各一次；静态契约机检不依赖网络。
- 架构检查：版本号不得在四个位置各自硬编码；`grep -REn "0\\.1\\.0" package.json desktop/src-tauri/Cargo.toml desktop/src-tauri/tauri.conf.json scripts/desktop/build.mjs` 除唯一来源外零命中。

**AC-42 · 试跑不污染正式发布**
- 场景类型：功能 / 试运行通道（v3 新增）
- 风险：中（试跑若对外可见或自我循环，会把 Releases 页弄脏）
- 引用：BR-36
- **Given** 维护者想在正式打 tag 前验证整条流水线。
- **When** 在 Actions 页手动运行一次发布流水线。
- **Then** 三个平台照常构建；产物进入一个**访客在 Releases 页看不到**的草稿；这次试跑不会再触发一次新的发布；维护者验证完可以一键删除该草稿，正式 Releases 列表条数不变。
- 机检：`test -f test/wp13/release-contract.test.js && NODE_ENV=test node --test test/wp13/release-contract.test.js` 断言手动通道产出草稿、且草稿标识不以 `v` 开头（避免再次命中 tag 触发）；`node probe/acc10-release-verify.mjs <dryrun-tag> --check draft` 断言远端 `draft=true` 且正式（非草稿）Release 数未增加。
- 夹具：`workflow_dispatch` 一次，取证后按发布手册清理草稿与其 tag。
- 架构检查：手动通道与 tag 通道共用同一套构建与冒烟步骤，不得为试跑另开一条宽松链路。

**AC-43 · 失败重跑与重复 tag 不产生重复 Release**
- 场景类型：非功能 / 幂等与可恢复（v3 新增）
- 风险：中（重跑失败会让维护者不敢再发版，重复 Release 会让用户选错版本）
- 引用：BR-37, BR-39
- **Given** 某次构建有一个平台失败、另两个平台成功；或同名 tag 的 Release 已经存在。
- **When** 维护者修复后重跑，或对同名 tag 再推一次。
- **Then** Releases 页始终只有该版本**一个**条目；重跑是更新/补齐这个条目的资产，不是新建第二个；三个平台产物最终齐全；同一时刻两次触发不会互相覆盖出半套资产。
- 机检：`test -f test/wp13/release-contract.test.js && NODE_ENV=test node --test test/wp13/release-contract.test.js` 静态断言「已存在则补传、否则创建」的分支、覆盖式上传、以及同版本并发互斥；`node probe/acc10-release-verify.mjs <tag> --check idempotent` 断言远端同名 Release 计数为 1 且资产齐全。
- 夹具：构造一次单平台失败的试跑后重跑；保留两次构建记录。
- 架构检查：任一平台失败不得阻塞其它平台产出自己的产物（不因一红全停）；但汇总发布必须等全部平台成功，缺一不发。

**AC-44 · 下载的包能装、能开，且与本机双击是同一个应用**
- 场景类型：功能 / 开箱即用（v3 新增，与 AC-29 衔接）
- 风险：高（CI 产物与本机产物不一致是最容易漏的一类缺陷）
- 引用：BR-38, BR-02, BR-34
- **Given** 用户从 Releases 页下载到与自己机器架构匹配的安装包。
- **When** 用户按常规方式安装并双击打开（macOS 挂载安装包拖入应用目录；Windows 运行安装程序）。
- **Then** 应用正常启动、3 秒内出现主窗口并停在实例列表；不报「已损坏，无法打开」；不需要预装 Node / Rust / 不需要开终端；看到的应用与本机 `npm run desktop:build` 产出的 `Maestro.app` 是同一版本、同一行为。
- 机检：`test -f test/wp13/release-smoke.test.js && NODE_ENV=test node --test test/wp13/release-smoke.test.js` 断言产物冒烟四项（启动探针出现 `ready`、无凭据请求返回 401、`codesign --verify --deep --strict` 通过、安装包镜像完整性校验通过 + 挂载后再次验签）；`# pass ≥ 1`、`# fail 0`；架构一致性硬校验（包内运行时架构 == 构建机架构，不符即失败）。
- 夹具：临时数据目录 + 独立端口，进程与挂载点退出时清理；不使用固定 `sleep` 判定就绪。
- 架构检查：真机安装/首启、Gatekeeper 放行路径属人工核验项（§3.3 与附录 D-15），**不得**用本机自动化冒充已通过；冒烟脚本须覆盖「安装包里那份应用」而不是只验构建目录里的 `.app`。

### 3.2 非功能验收标准

- **NF-1（开屏速度）**：双击图标到主窗口出现 ≤ 3 秒；从点击实例到流程图完整绘出 ≤ 1 秒（含一次快照请求）。
- **NF-2（实时性）**：角色状态变化到界面更新 ≤ 500ms；连接线合并窗口 1 秒，合并后 ≤ 1.2 秒内刷到最终态。
- **NF-3（重连）**：断开后 5 秒内自动重连成功并完成全量快照恢复；重连期间有可见提示，不静默。
- **NF-4（稳定性）**：连续打开/关闭 10 次窗口、切换 20 次视图，界面不崩、守护进程不重启、实例状态不变。
- **NF-5（资源）**：窗口关闭后 1 分钟内界面进程 CPU 占用 ≤ 1%；主窗口空闲常驻内存不超过同类 Tauri 应用常规量级（不作为卡点，仅记录实测值）。
- **NF-6（无回归）**：三条主链输出逐字不变；`orch instance status` / `instance graph` 两种格式逐字不变；全量测试失败集合与 I1.9 收口基线差集为 0，测试条数只增不减。
- **NF-7（零依赖）**：`dependencies` 为 `{}`；界面层不引入 npm 包；用户侧不需要额外安装运行时。
- **NF-8（发布零回归，v3）**：新增发布能力不得改变 AC-01~37 的任何既有判据、三条主链逐字输出、`USAGE_LINES` 25 行、`dependencies` 为 `{}`；全量测试失败集合与判定基线差集仍为 0，测试条数只增不减。发布相关文件不进 `src/core`、`src/daemon` 的 31 词扫描范围（属覆盖扩大，不是断言修改，见附录 D-11）。
- **NF-9（产物可追溯，v3）**：每个可下载安装包都有 SHA-256 且清单逐行对得上；用户下载后能自行对账；一次发布能回溯到具体 commit 与构建记录。
- **NF-10（发布可靠性，v3）**：单个平台构建失败不影响其它平台产出自己的产物，但缺少任一平台资产时不得创建/更新正式 Release；同名版本并发触发互相排斥，不产生半套资产。

### 3.3 验收前置条件

- **环境（本机，已核实）**：macOS 26.6.2（x86_64）；Node `v22.22.2`；`rustc 1.98.1` / `cargo 1.98.1`；Xcode 位于 `/Applications/Xcode.app`。Tauri 在本机可构建。首次构建需要一次 cargo 依赖拉取（联网）；离线环境先执行一次 `cargo fetch` 预热，不作为本迭代的验收判据。
- **构建命令**：`cd "$MAESTRO_REPO" && npm run desktop:build`，产物固定在 `desktop/src-tauri/target/release/bundle/macos/Maestro.app`；应用二进制为 `Maestro.app/Contents/MacOS/maestro`。构建脚本只做复制与 `cargo build`，不引入 npm 依赖。
- **验收级别（B 类，另有构建环境约束）**：**本迭代验收不依赖真实 DSH**。具体为 **B 级**——mock 宿主 + 真实 core / daemon，**不接真实 DSH、不需要模型凭据**。所有 AC 的 Given 都能在本机用 mock 数据构造出来；真实宿主取证留作本机保留项，不在本迭代判定。**构建环境约束**（Rust / Xcode / 首次 cargo 拉取）只影响“能不能把应用打出来”，不是 DSH 依赖：没有 DSH 的机器只要有 Node 22 与这套构建链，就能完成全部 AC。
- **项目根与夹具位置**：每个 AC 的独立项目根放在 `/tmp/maestro-i10a-*`，绝不放进仓库；一律注入 `NODE_ENV=test`。
- **宿主夹具**：在夹具根 `.orch/hosts/mock.json` 中把 `launch.command` / `launch.args` 指向仓库内 `test/fixtures/mock-acp-agent.js`；启动时带 `--host mock`。`orch run` 必须带 `--cwd .`。
- **快照夹具的启动顺序（必须照做）**：核心启动时会把不属于当前核心代的 `created` / `running` 实例判为已中断，因此快照夹具必须**先在空目录拉起核心**（执行一次 `node "$MAESTRO_REPO/bin/orch.js" instance status INST-001`，返回“不存在”即可），**再写** `state.json` / `traces.jsonl` / 工作流定义，最后才打开界面；快照统一带 `schemaVersion: 2`。
- **测试配置目录**：`MAESTRO_CONFIG_DIR` 指向夹具内目录，用于存放“已记住的项目根”（`projects.json`）；`--project` 参数优先于它。首次无配置时界面走“项目 未指定”路径（AC-31 覆盖）。
- **应用测试接缝（仅测试）**：`--probe <文件>` 追加启动/关闭/托盘/退出事件；`--ctl <目录>` 通过创建 `close-window`、`tray-open`、`tray-quit`、`tray-quit-confirm`、`open-instance/<id>` 文件触发与真实交互相同的处理函数。两个接缝只在明确传入参数时生效，生产启动不写探针文件。
- **服务端测试接缝（仅测试）**：`NODE_ENV=test` 时才注册 `POST /__test__/graph/pulse`（`kind: role|connection|session`、`count`、`intervalMs`），用于构造节流与重连场景；生产进程不注册该路由。
- **数据接口获取方式**：界面与 harness 都从 `.orch/desktop.json` 读取 `{port, token}`，请求头带 `Authorization: Bearer <token>`；该文件由守护进程在启用桌面通道时原子写入，退出时删除。
- **等待与轮询口径**：探针文件、推送帧、实例行出现一律用“条件成立即继续”的轮询（每 100ms 一次，上限 30 秒），**不使用固定 `sleep` 判定**；1 秒合并窗口的边界用注入时钟的单元测试覆盖，不在窗口级用真实时间赛跑。
- **回归基线**：全量测试以 I1.9 收口 `1157 tests` 为对照，收口判据是“失败集合与 `docs/iterations/iteration-7/baseline-failures.txt` 的差集为 0”，不以“零失败”判定；测试条数只增不减。
- **命令口径**：所有 CLI 命令在夹具目录内以 `node "$MAESTRO_REPO/bin/orch.js" ...` 执行；路径断言只用相对路径或结尾匹配，不断言 `/tmp` 与 `/private/tmp` 的差异。
- **发布面验收口径（v3 新增，与 B 类判定分开）**：AC-38~44 中「远端 Release 存在 / 资产集合 / 草稿可见性 / 预发布标记」属**真实 GitHub 面**，前置条件是仓库可访问、能推测试 tag、能读 Actions 与 Releases；取证一律走只读 REST（`api.github.com` 直连）+ `git credential fill` 取凭据，凭据不写入任何证据文件。按 `docs/index.md` 675 行口径，**DSH 是 AI 宿主依赖、GitHub 是发布通道依赖，两者是不同类别**：新增发布面真实取证**不改变本迭代 B 类判定**（B 类只约束「不接真实 DSH」）。禁止把真实面改写成静态文件存在来「变绿」（`docs/index.md` 710 行第 3 条）。
- **发布面证据分级**：`已实测（真实 GitHub 面）` / `mock 实测（静态契约机检）` / `阻塞`；AC-38~44 每条都要标级别并留原始帧，静态契约机检不得单独判该 AC 通过。
- **测试 tag 与草稿的清理**：一次性测试 tag 与试跑草稿在取证后删除，取证帧（REST 响应、构建记录链接、资产清单、SHA-256 对账结果）保留在 `docs/iterations/iteration-10a/evidence/release/`；删除动作本身也要留证，避免「查不到」被误读成「没发过」。
- **本机验收仍可用**：AC-01~37 继续按上面「构建命令」在本机执行；v3 新增 AC 的静态契约机检在本机可跑，真实面需联网。
- **人工核验项（不得自动化冒充）**：真机安装与首次打开、Gatekeeper 放行路径、Windows SmartScreen 引导，登记为「阻塞/待人工」，不计入 AC 自动通过数。
- **历史行号引用**：v1/v2 的评审与理解纪要（`review-round1.md`、`review-round2.md`、`requirement-understanding.md`）中指向本文件的行号以 v2 快照为准；v3 在其后新增内容，旧引用不回改。

## 附录 A · 输出基线（用户可见文案）

> 所有用户可见中文取自 `src/cli/labels.js`；界面层通过 `GET /ui/labels` 取键值，不硬编码。以下为逐字基线，实现必须按此输出；“逐字”的边界由 **A-0 可变值约定**界定，A-1 ~ A-13 每一节都适用。

### A-0 可变值约定（适用 A-1 ~ A-13）

> “逐字”= 除下列**可变值**外，文字、空格、缩进、分隔符（` · ` / `→` / `：` / `，`）、标点与顺序完全相等。断言时先把可变值替换为夹具实际值，再逐字比较。

**逐字固定（不得随夹具变）**：

- 六档文案只用既有词：健康度 `正常` / `慢` / `需关注` / `已结束`；角色 `可用` / `服务中` / `冷却中` / `不可用` / `未参与`；节点 `待执行` / `执行中` / `待校验` / `已完成` / `失败` / `已取消` / `已升级`；交接包 `已构造` / `已投递` / `待投递` / `已接受` / `已完成` / `已拒绝` / `已过期`；实例 `已创建` / `运行中` / `已完成` / `失败` / `已取消` / `已中断` / `已挂起`。

## 附录 B · 术语与未决问题

### B-1 术语

- **主窗口**：桌面应用唯一窗口，默认页是实例列表。
- **托盘**：系统菜单栏常驻图标；本迭代只有“打开主窗口 / 退出”两项。
- **实例列表**：实例级视图，只给六项结论，不展示角色与节点（基线 424 行）。
- **角色流程图**：实例层主视图，只展示角色级与交接级信息（基线 547 行）。
- **角色实例**：运行时角色，由角色注册表与实例状态派生；本迭代的状态词为可用 / 服务中 / 冷却中 / 不可用 / 未参与。
- **特殊节点**：`human`（人工）、`escalate`（升级）、`subworkflow`（子工作流折叠组）三类节点的统称。
- **折叠组**：角色超过 12 个时按分组聚成的组节点；与子工作流的折叠组节点不是同一概念，标签前缀分别为“分组”与“子工作流”。
- **聚合状态**：一对角色之间由多个交接包按优先级合并出的连接线状态，7 种。
- **异常置顶**：把异常元素的层级提升到最上层并加高亮，**不改变坐标与尺寸**。
- **图版本号**：界面判断“是否需要重画”的单调计数；只由影响图元素的事件推进。
- **指示器事件**：会话状态变化专用的事件类型；不改变图版本号。

### B-2 未决问题

- **U-1（不阻塞，需评审确认交互）**：项目根的绑定方式取“`--project` 参数 > 环境变量 > 已记住的项目 > 首次填写项目目录”，不提供系统文件夹选择器。理由是避免为选目录再引入原生对话框依赖；若评审要求文件夹选择器，需在拆分阶段追加依赖评估。

- **U-3（不阻塞）**：界面文案通过 `GET /ui/labels` 下发，而不是在构建期把 `labels.js` 复制进界面包。两种方式都满足“唯一来源”；选下发是为了让新增文案只改一处。若评审要求构建期复制，只需改一处构建脚本。
- **U-4（已裁决，不阻塞）**：规划验收要求“含人工节点和子工作流的实例在流程图上拓扑完整”。当前运行时（内置三模板）**没有** `human` / `escalate` / `subworkflow` 节点，也还不能用 `orch run` 绑定工作流资产。本迭代的做法是：图投影只读实例快照里的 `workflowRef`（指向 `.orch/workflows/<id>.yaml`），由夹具构造这类实例并验证拓扑完整；运行时绑定与推进明确留在后续（§1.3 范围外）。**裁决（round1，写回本文件）**：渲染语义下的「拓扑完整」可由夹具构造的实例满足——规划 840–857 与阶段一退出条件（913 行）只要求「完整表达拓扑」，`docs/index.md` 基线未承诺运行时推进 human / subworkflow；AC-26 的 `INST-001` 已标注由夹具构造，避免被读成运行时可达。

## 附录 D · 实现约束（技术要点，仅供编码参考，不进入需求判定）

> 本附录是需求对实现的约束摘要，写代码的 Agent 据此落地；评审对需求的判定不依赖本附录。

### D-1 进程、端口与本地凭据

- 守护进程的桌面通道**不经 CLI 命令表**：由 `src/daemon/serve-entry.js`（已存在的守护进程入口）承担桌面入口，启动形态为 `node src/daemon/serve-entry.js --project <root> --desktop`（等价于 `createServer({ http: true })`）。该路径**不触碰 `src/cli/main.js` 的命令表（`COMMANDS`）、两层子命令表（`RUNTIME_SUBS`）与 `USAGE_LINES`**；不传 `--desktop` 时**完全不监听 HTTP**，既有测试与 CLI 行为零变化（这是回归红线的一部分）。
- 监听 `127.0.0.1:0`（临时端口），启动后原子写入 `<root>/.orch/desktop.json`：`{port, token, pid, generation, startedAt}`，token 为 32 字节随机十六进制；退出（含 `core.stop`）时删除该文件。
- 所有请求必须带 `Authorization: Bearer <token>`；缺失或错误一律 `401`，响应体只含错误码，不含任何实例数据。
- HTTP 层不得出现中文；所有响应体使用英文状态码与英文键，中文由独立接口下发（D-7）。
- 启动顺序：先 `listen` 成功、再写 `desktop.json`；写文件失败视为桌面通道启动失败，**不影响** IPC 主通道。

### D-2 数据接口与推送帧

所有接口均为只读，只有 `POST /instances` 会启动实例：

| 方法 | 路径 | 用途 | 成功响应要点 |
|---|---|---|---|
| GET | `/instances` | 实例列表 | `{ items: [{instanceId, template, templateTitle, phase, progress:{done,total}, pending:{escalations,approvals}, health:{level,reasons}, updatedAt, readable}] }` |
| GET | `/instances/stream` | 列表变化推送 | SSE；事件 `instances.changed`，500ms 合并 |
| GET | `/instances/:id/graph` | 图快照 | `{ rev, instanceId, template, state, nodes[], edges[], workflow:{ref,readable} }` |
| GET | `/instances/:id/graph/stream` | 图推送 | SSE；首帧 `graph.snapshot`，增量 `role_instance.updated` / `connection.updated` / `special_node.updated` / `session.indicator` |
| POST | `/instances` | 新建实例 | `{ instanceId }`；参数 `{template, task}`，透传 `run.start`（`cwd` = 项目根、`earlyReturn: true`） |
| GET | `/workflows` | 可选工作流 | `{ items: [{id, title}] }`，只列三个可运行内置模板 |
| GET | `/ui/labels` | 文案表 | `{ keys: { "<KEY>": "<文案模板>" } }`，键集合见附录 A-14 |
| GET | `/ui/*` | 界面静态资源 | 来自 `desktop/ui/`，只读 |

- SSE 帧格式：`event: <type>\ndata: <json>\n\n`；`data` 至少含 `{rev, instanceId, type, key, payload}`。
- `rev` 为图版本号：取“图版本号白名单”事件（节点状态、交接包状态、升级、实例状态、特殊节点）的最大事件序号；`session.state`、`execution.summary`、`health.changed` **不**推进 `rev`。无白名单事件时为 `0`。
- 重连（新连接）一律先发 `graph.snapshot`（含当前 `rev`），随后只发 `rev` 大于客户端 `sinceRev` 的增量；客户端不传 `sinceRev` 时等价于全量。
- `nodes[]` 字段：`{id, type: role|human|escalate|subworkflow|group, title, roleId?, status, statusReason?, activeSessions, servingNodes[], hostIcons[], abnormal, abnormalCount, nodeIds[], memberCount, collapsed, lastActivity}`。
- `edges[]` 字段：`{id, from, to, direction: forward|backflow, aggregateStatus, handoffIds[], parallelCount, latestRound, visual:{color,dash,arrow,animation,badge}, labelVisible}`。
- 错误码沿用既有语义：实例不存在 `404 NOT_FOUND`；快照损坏 `422 STATE_CORRUPT`；启动失败透传 `ERROR_TEMPLATE` 的码；凭据错误 `401 UNAUTHORIZED`；未知路径 `404 NOT_FOUND`。
- `POST /instances` 与只读接口共用同一鉴权；请求体大小上限 32KB；不只接受 GET 之外的写操作（除该 POST）。

### D-3 图投影规则（只读派生）

- **模块划分**：`src/daemon/graph.js` 负责把 `state` + 图定义 + 角色投影组装成 `nodes/edges/rev`；不读盘、不写盘、不取系统时间（时间由调用方传入）。`src/daemon/http/*.js` 只做路由、鉴权与序列化。
- **图定义解析顺序**：① 实例快照 `workflowRef` → `<root>/.orch/workflows/<ref>.yaml`；② 内置模板（`instance.template`）；③ 都取不到时用空图（`nodes: []`, `edges: []`）并在响应里标 `workflow.readable=false`。
- **节点**：
  - `role`：以**角色实例**为单位（不是工作流节点），来自角色实例投影（`src/registry/role-instances.js` 的 `buildRoleInstances`）。传入的 `roles` 必须包含图声明的角色（缺注册表时按“图声明即已知”处理，**不得**因注册表为空把全部角色判成 `unavailable`）。
  - `human` / `escalate`：来自定义层 `node_type`，状态取 `state.nodes[nodeId]`，缺失则 `pending`。
  - `subworkflow`：折叠组；`memberCount` = 子工作流定义中 `node_type === 'role'` 的去重数；`abnormal` = 子工作流内任一节点在 `state.nodes` 中为 `escalated`；子定义读不到时 `memberCount = null`、状态灰色、`abnormal = false`。
  - `group`：仅当可见角色节点 > 12 时生成（见 D-4），`nodeIds` 为成员，`memberCount` 为成员数。
  - 未知 `node_type` 按 `role` 渲染并保留 ID，不丢节点。
- **边**：
  - 端点为角色时按角色实例 ID 聚合；端点为特殊节点时按节点 ID 保留。
  - 同一 `(from, to, direction)` 合并为一条；`parallelCount` 为合并的交接包数（>1 时标签加“N 并行交接”）。
  - `aggregateStatus` 按固定优先级：`rejected > expired > pending > delivered > accepted > consumed > not_started`。
  - `direction` 由定义边 `kind` 决定：`backflow` → `backflow`，其余（含 `retest`）→ `forward`。
  - 无交接包但定义里有边 → `not_started`。
- **健康度**：列表与图都直接读 I1.9 的 `state.health`（`level` + `reasons`），**不得**在 HTTP 层或界面层重算；`instance.get` 的读取时重算路径保持不变。
- **最近动作**：角色 `lastActivity` 优先取 `instance.trace` 已落地跨度中该角色最新一条的 `end_time`；没有跨度时回落 `state.updatedAt`。读取追踪用只读接口，不触发健康度写路径。
- **只读**：投影过程中禁止调用 `saveState`、`emit`、`appendSpan`、升级生成或调度接口。

### D-4 布局与视图模型（纯函数，可被 Node 直接 import）

- 文件：`desktop/ui/graph/layout.js`（布局）、`desktop/ui/graph/view.js`（缩放/平移/聚焦/折叠/拖拽）、`desktop/ui/board/board.js`（看板投影）、`desktop/ui/labels/labels.js`（标签可见性）。这些文件**不得**访问 DOM、`fs`、`Date.now`、`window`。
- 常量：节点宽 180、高 80；层间距 240（x = layer × 240）；同层行距 140（y = 行序 × 140）；回流弧控制点相对两端连线的中点向上偏移 40。
- 层次：只按 `forward` 边做最长路径分层（`backflow` 不参与）；同一层内按“定义顺序（`order`）→ 节点 ID”稳定排序。
- 异常：`z = abnormal ? 1 : 0`；坐标与尺寸不参与异常计算。
- 折叠：可见角色节点（含组内成员判断前）> 12 时，按角色 `group` 分组生成组节点；组节点坐标取成员层号的最小值与成员行序的中位值；展开后成员回到原层原序。子工作流恒折叠。
- 聚焦：以被双击节点为起点做无向 BFS，保留距离 ≤ 2 的节点；边保留两端都可见的；坐标不重算（只过滤可见集合）。
- 缩放/平移：`zoom ∈ [0.5, 2.0]`，`pan` 为像素偏移；渲染时用变换矩阵，布局坐标不变。
- 拖拽：偏移写入 `<root>/.orch/desktop/views/<instanceId>.json`：`{ "offsets": { "<nodeId>": {"dx":40,"dy":60} }, "updatedAt": "..." }`；读取时叠加到基础坐标；复位视图清除该文件中的偏移。
- 看板：列为 `blocked / ready / running / review / done / failed / escalated`；`pending` 节点按“所有上游 forward 前驱均为 `done`（或无前驱）→ ready，否则 blocked”归类；`cancelled` 归入 done 列的折叠计数；未知状态落 blocked 并标 `状态未知`。
- 标签：默认可见集合 = 聚合状态属于 `{rejected, expired, pending}` 的连接线；悬停某条线时把该线加入可见集合。

### D-5 推送节流

- 角色变化：事件到达即推送（不做窗口合并），端到端 ≤ 500ms。
- 连接线：按 `(instanceId, edgeKey)` 维护固定窗口 1000ms；窗口从该键**第一次**变更起算，不因后续变更延长；窗口结束时推送一次，值为窗口内最后一次状态；窗口内无第二次变更时仍在窗口结束时推送（保证首个变更不丢）。
- 会话：`session.indicator` 原样推送（不合并），不推进 `rev`；仅当该会话变化导致角色状态或异常角标变化时，额外产生一次 `role_instance.updated`。
- 实现要求：调度器接受注入的 `now()` 与定时器接口，单测注入固定时钟即可断言“恰好 1000ms 不重复推送、1001ms 推送一次”。

### D-6 桌面壳与托盘

- 技术选型：Tauri（优先，基线 43 行）；若 WebView 出现兼容问题再回退 Electron，回退只影响壳层，不影响 D-2 的接口。
- 托盘：只建两个菜单项（`DESKTOP_TRAY_OPEN` / `DESKTOP_TRAY_QUIT`）；点击“打开主窗口”显示并聚焦已有窗口；点击“退出”时先查运行中实例数（`GET /instances` 过滤 `running`/`suspended`），大于 0 则弹确认。
- 窗口：关闭事件拦截为“隐藏”，不退出进程；`hide` 后托盘仍在；只有退出流程才 `core.stop` + 结束进程。
- 单实例：第二次双击激活已有窗口，不建第二个窗口、不拉起第二个守护进程（用应用级单实例锁）。
- 打包：应用资源目录包含自带运行时（解释器 + `bin/` + `src/`），启动子进程时使用**包内绝对路径**，不读 `PATH`。构建脚本只做复制与 `cargo build`；`package.json` 只允许新增 `scripts` 字段。
- 测试接缝：`--probe` / `--ctl` 只在启动参数出现时启用；探针文件为追加式 JSON Lines，每行一个事件；`--ctl` 目录里的文件出现即触发、触发后改名为 `.done`。

### D-15 发布流水线契约（v3 新增，参考实现，不进入验收判定）

> 来源：本机 `/Users/xuesh/www/agent-task-board`（`xueshuaihui/agent-task-board`）的 `.github/workflows/release.yml`、`scripts/package-release.sh` / `package-release-win.sh`、`docs/发布手册.md`。该链路**已实测跑通**：远端 18 个 Release，资产为 `*_x64.dmg` / `*_arm64.dmg` / `*_x64-setup.exe` / `SHA256SUMS.txt`。以下仅为编码参考，**AC-38~44 的判定只看 §3.1 的用户视角句子，不以本节任何实现形态为准**。

- **触发**：推 `v*` tag 走正式通道；手动 `workflow_dispatch` 走试跑通道。试跑的草稿标识刻意**不以 `v` 开头**，避免再次命中 tag 触发形成自我循环；草稿在当前提交上就地建出，验证后连同 tag 一起删除。
- **矩阵**（每个架构在自家构建机上产出，不做 universal / 跨架构装配）：macOS Intel → x64 dmg；macOS Apple Silicon → arm64 dmg；Windows x64 → NSIS `.exe`。任一平台失败不阻塞其它平台产出，但汇总发布必须等全部成功。冷编译需给足超时（参考项目 120 分钟）。
- **步骤链**：拉取代码 → 准备 Node 22 与稳定 Rust → 依赖缓存 → **质量门禁** → 构建 → 装配随包运行时 → 打包 → **包元数据对齐校验**（应用标识 / 产品名 / 版本与配置一致） → **签名 + 验签** → 生成安装包 → **产物冒烟** → SHA-256 → 上传中间产物 → 汇总发布。
  - 产物冒烟四件套（参考项目靠它抓出过「缺依赖 / 未签名报已损坏 / dmg 装了旧包」三个真实缺陷）：应用能启动并打印就绪标记、无凭据请求被拒、签名验签通过、安装包镜像完整性 + **挂载后对镜像里那份应用再次验签**（不能只验构建目录里的 `.app`）。
  - 已知坑：打包工具若先出了未签名的安装包必须作废、签名后重新生成；每架构只生成一次镜像（二次生成会挤爆 runner 磁盘）；生成前先清理残留挂载点，否则报资源忙；包内运行时二进制的架构必须与构建机架构一致，不符直接失败。
- **版本与通道**：版本号单点来源；`v0.x.*` 标预发布、`v1.0.0` 起标正式版；tag 一律 annotated 并写清发布口径与已知限制。是否强制 tag 数字 == 包版本见 U-13。
- **凭据与幂等**：只用仓库自带 `GITHUB_TOKEN`（`contents: write`），不需要个人 token；同名 Release 已存在则补传资产（覆盖式）、否则创建；同版本并发互斥。
