## 〇、先看这四句

1. **交付定义是"需求被完整实现"，不是"做出了一个能跑的东西"**。70 条 AC 就是验收清单，一条不落地全部实现并通过验收；不许用"先做核心几条，剩下的排下个迭代"来收尾（§1.6）。
2. **第一步不是写代码，是把需求推到"可开发"**。**v23 已经定稿**（六轮独立评审 PASS），底子很扎实（70 条 AC 连续、46 条 BR 全部被 AC 引用、每条 AC 都有 Then 与判定锚点）；剩下的是产出任务拆分文档，外加 3 项小缺口（§1.4）。
3. **I1.4 不是加新功能，是给已有核心补一层契约**。共享工作区、交接包校验、信箱、审批、暂停、裁决，全部长在 I1.1~I1.3 已经跑通的那套引擎上。所以"不回归"比"新功能好用"更重要。
4. **这个迭代不需要 DSH**。70 条 AC 全部用仓库内 mock ACP agent 验收（需求 §3.3 第 3 条自己这么定的）。环境只要 Node ≥ 22 + Git Bash。

**工作方式**：这份文档给的是**判定原则**，不是待办确认清单。过程中遇到的所有"要不要这样做"，都用 §1.2 的偏离判定 + §1.2.1 的裁决优先级自己拍板，**不要逐步来问**；每个自主裁决按 §6 留痕，交付时一次性审。

### 1.2 「偏离基线」的三种判定（拿这三条卡自己的每个决定）

1. **契约偏离**：任何对 I1.1~I1.3 的数据结构、状态机、输出文案、测试断言的改动，**必须能在 M-1~M-12 或 C-01~C-14 里找到对应条目**。找不到就是偏离 —— 要么补需求授权（走评审），要么不做。典型越界：觉得 `snapshotOf` 少个字段顺手加了、觉得某条测试断言"太严"顺手放宽了。
2. **范围偏离**：§1.3「范围外」列了 10 件事，全部属于 I1.5~I1.12（角色注册表、ACP 会话恢复、桌面通知、worktree、链式哈希…）。**这一轮一件都不做**。典型越界：`attach` 想顺手支持注入输入（那是 I1.8）、`graph` 想顺便画角色实例（那是 I1.5）。
3. **规划偏离**：§1.3.1 是"规划条目 → 需求节 → AC"的三向映射表。**新增任何需求节都必须在表里有落点；任何规划条目都必须至少有一条 AC 兜底**。实现时如果发现"必须新开一节才说得清"，说明需求漏了 —— 先补需求与映射，再写代码。

一句话记法：**M/C 清单是允许改的边界，范围外清单是禁止碰的边界，§1.3.1 是必须对上的账。**

### 1.2.1 遇到冲突时，按这个优先级自己裁（不需要问）

当两份材料说法不一致、或者需求没写到某个细节时，**从上往下取第一条能覆盖的**：

### 1.4.1 「完善需求」的边界：只能补，不能减

这一步的目的是把需求推到**可开发**，不是把它改到**好实现**。允许动和禁止动是明确的：

**允许改（这四类之外不要动正文）**

1. 修笔误（如 §3.3 的 Node 版本）
2. 把附录 B.2 的「假设」写成结论（B-01 `stage/` 可见域、B-02 `shared/` 谁写）
3. 补缺口：某条 AC 说有输出但 A 里没有对应版式、D-10 漏列的授权断言
4. 补定稿后的版本记录（**仅当又做了需求修订时**；v23 本身已是定稿，不必为了"仪式感"再动头部）

**禁止改**

1. 删减、合并、降级任何一条 AC（70 条是交付清单，不是建议清单）
2. 放宽 `Then` 的判定强度（"逐字一致"不许改成"包含"、"必须"不许改成"应当"）
3. 把 §1.3 范围内条目挪到范围外
4. 因为"实现起来难"去改契约而不走 M/C 补授权
5. 新增未经评审的大块功能（要加就单独提，不在"完善"里夹带）

判定口径：改完之后 §1.5 的机械扫描仍然全绿、70 条 AC 一条不少、46 条 BR 仍被全覆盖。**如果"完善"之后 AC 变少了或者判定变松了，那就是改错了方向。**

这次的任务是**实现需求**，不是"实现一个能满足主要场景的版本"。收尾时必须同时满足：

| # | 条件 | 判定 |
|---|---|---|

| 2 | **回归不破**：418 条既有测试全绿，`single`/`code-loop`/`task-loop` 输出逐字不变 | AC-54/AC-55 本身就是 AC，回归不是"附加要求" |

| 4 | 证据落盘到 `docs/iterations/iteration-4/evidence/`，可独立复核 | 不许只留一句"已确认" |
| 5 | 报告收口：`report.md` + `acceptance-*.md`，结构照 iteration-3 | |
| 6 | 决策台账 `decisions.md` 完整（§6） | 每条自主裁决可追溯 |

**三种"看起来完成但其实没完成"的形态，别出现**：

1. **只做主链**：`doc-pass` 能跑通就宣布完成，坏包、重试、审批、暂停、裁决这些异常路径的 AC 全部跳过 —— 这批 AC 占 70 条里的三分之二，恰恰是这个迭代的主体。
2. **用"看起来对"替代机检**：`Then` 写"输出 X"，就手敲一遍看到像就判通过；实际要求是逐字比对 + 原始帧落盘。
3. **把观测不到写成通过**：某条 AC 在夹具上停不稳，就直接写"通过（人工确认）"。正确做法是判 `阻塞` 并写清尝试路径 —— **阻塞不算失败，伪通过才是**。

需求范围里的每一项都要落地，包括那些"用起来不起眼"的：`status.md` 的刷新时机、信箱的原子写、`pending` 期间的重试计数、审批号跨实例歧义、旧格式实例只读可查。这些正是这个迭代要解决的问题本身。

## 二、开发方式：沿用 Agent 协同

### 2.1 节奏（I1.1~I1.3 都是这么跑通的）

```
需求定稿 → 任务拆分 → 逐包实现（SubAgent）→ 每包门禁 → 主控复核 diff
        → 全量验收（SubAgent 分批取证）→ 缺陷单线修复 → 主控独立复跑 → 报告收口
```

关键点：**实现与验收分离**。写代码的 Agent 不给自己判 AC；验收 Agent 只写用例与取证、不改产品代码。

### 2.2 SubAgent 任务书六段式（缺一段就会返工）

1. **背景**：仓库根、HEAD、当前测试基线（418 条）、这次要做什么、不要做什么
2. **必读**：需求的具体行号区间 + 参考实现文件 + 样板用例（**明确"自己读，不要问我"**）
3. **判据**：逐条抄需求的 Then/And，写清"一个 Then 至少一条核对项"
4. **硬约束**：禁止改哪些目录、发现缺陷怎么办（**不许修，登记台账**）、是否允许提交 git
5. **门禁**：四条命令 + 具体数字（全绿 / 扫描 exit 0 / 主链 exit 码）
6. **返回格式**：要它回什么（改动文件与行号、断言要点、门禁数字、缺陷清单），**明确"不要贴大段代码"**

### 2.3 并发与批次规则

- **一次最多 2 个大 Agent，3 个会触发平台 429**（I1.3 实测）。宁可慢一点，也别一次派 4 个。
- 每个 Agent 要求**分批落盘证据**，防中断丢成果（I1.3 有一次跑到一半被掐，重跑浪费 20 分钟）。
- 相互独立的工作才能并行；**同一批文件不许两个 Agent 同时改**（会互相覆盖 + commit 混在一起）。
- 修复类任务**永远单线**派，不和功能开发并行（diff 才能干净归因）。

### 2.4 缺陷单独派单，不夹在功能包里

发现缺陷 → 登记到台账（现象 / 最小复现命令 / 原始输出片段 / 疑似代码位置 / 级别）→ **另派一个修复 Agent** → 修完必须复跑"受影响的那几条 AC + 可能连带的 3~5 条"。

理由：I1.3 收口的 6 个缺陷（2 个 P1）如果夹在功能包里改，diff 无法归因，回归范围也说不清。

### 2.5 主控不可托管的三件事

1. **不采信 SubAgent 的自述结论**。它说"通过"，你要自己 `node -e` 读一遍 state/events 原始帧，或者自己复跑 3~5 条关键 AC（并发/暂停类、门禁类、异常路径）。
2. **裁决"判定过严 vs 产品缺陷"**。I1.3 的 AC-35（时间戳差 4~8ms）看着像吹毛求疵，实际是真偏差 —— 这类必须回需求原文裁，不许让 Agent 自己放宽断言。
3. **报告与提交**。验收报告、`git add` 的范围、commit message 全部主控做。

## 三、I1.1~I1.3 累积的硬约束（照抄，别重新试错）

### 3.1 架构与状态（P0 级，破了就是全盘随机失败）

1. **状态迁移唯一入口是 `orchestrator.transit()`**：以磁盘最新快照为 `from` 重新校验 + `save(expectedState)` 做 CAS。**任何地方不许直接 `store.save` 改状态**，否则终态会被内存副本静默覆盖。
2. **CAS 形状 I1.4 要从三键扩到四键**：`{state, halted, rev, paused}`。`casSnapshot` / `compareExpected` / `expectedOf` 三处同步；旧快照缺 `paused` 按 `false` 处理（D-10 第 1.1 条已授权，`test/wp1`、`test/wp8/f3-cas` 的 `actual` 深比较要跟着补，**只改 actual，不改冲突语义**）。
3. **`rev` 无条件基于磁盘现值递增**，进程重启不回 1，否则 CAS 必然误判。
4. **`halted` 必须独立一次 `saveState`**，不与升级条目合并写。
5. **事件先落盘再广播**：`emit` 失败不得改内存状态。
6. **忙检查放在写锁之前**：I1.3 的教训是检查在锁内 → 同目录并发要等 60s 才报「未知错误：IPC_TIMEOUT」。正确做法是 `@dir` 锁之前先做占用快检（复用 `findDirBusy` 口径），锁内保留一次复核防竞态。I1.4 新增的 `pause`/`resume` 也要遵守"锁外快检、锁内复核"。
7. **四个新模块必须保持纯净**：`workspace.js` / `handoff-schema.js` / `inbox.js` / `approvals.js` 不 import CLI、不出现模板名与角色名、`handoff-schema` 必须是纯函数返回 `{ok, code, detail}`。

### 3.2 提示词与路径

8. **提示词给一律绝对路径**。这是 I1.3 的 P1 缺陷：审核节点给相对 `out/review.json`，同屏又给「工作区：<绝对路径>」，真实模型 3 次里 2 次写进了实例工作区。I1.4 的 `status.md`、`shared/`、`stage/` 路径同理（C-01 已明文规定）。
9. **提示词真正的产出点是 `advance.js` 的 `planAdvance`**（经 `plan.promptText`），不是 `orchestrator` 里的兜底分支。改提示词先改这里，否则改了不生效。
10. **模板字符串本身尽量别动**：提示词有逐字断言（`test/templates/task-loop.test.js`），改文案会连带踩 I1.1/I1.2 的零回归红线。优先改"传进去的变量值"。

### 3.3 事件与时间戳

11. **事件 `ts` 必须复用状态变更的同一时刻**。`startedAt`/`endedAt` 各自 `iso()` 会差 4~8ms，而 AC 里写的是严格等式。`event-bus.emit()` 已支持可选 `ts`，直接用。
12. **事件 `seq` 严格单调，`ts` 不得早于同实例上一条**。
13. **I1.4 新增事件（`handoff.inboxed`、`handoff.pending`、`approval.*`、`escalation.resolved`、`workflow.paused` 等）必须带齐 `object/reason/result/detail`**，因为 AC-57 会逐个核。

### 3.4 渲染与文案

14. **`task-loop` 与 `code-loop` 的事件行渲染必须分流**。I1.3 的 P1 缺陷：`task-loop` 的 note 行泄漏了 5 个英文 reason，还重复追加了「原因」段。改公共分支会踩 AC-36 的逐字红线。
15. **`single` 和 `code-loop` 的输出是逐字红线**，任何渲染改动后必须逐行比对（AC-54 就是干这个的）。
16. **所有中文只在 `src/cli/labels.js`**。I1.4 新增的审批/暂停/重新分配/新错误码文案全部走这里；`status.md` 的状态词要与 `labels.js` 逐字一致，并用一条对照测试锁住（D-11 第 3 条）。

### 3.5 测试与夹具环境

17. **测试命令是 `node --test "test/**/*.test.js"`**。`npm test` 在本机报 `MODULE_NOT_FOUND`，别用。当前基线 **418 / 418**。
18. **项目根一律放 `%TEMP%`**，不要放仓库目录。原因：夹具会写 `.orch/`、`.mock/`，放仓库里污染工作树，还会让实例 id 冲突。
19. **同进程串行跑场景 > 10 个会耗尽资源**（`session/new` 全部失败）。每 10 个场景 `forceKillCore` 一次，或用 runner 自动回收。
20. **`driver --keep` 被强杀时进程退出码可能是 13，那不是产品码**。退出码断言只对完整跑做。
21. **`orch core stop` 会把非终态实例对账成 `interrupted`**。中间态要在断言时刻用 `c.snap(root,'state.live')` 抢先落盘。
22. **验收脚本禁止硬编码测试条数**。用 `fail===0 && pass===tests && tests>=418`，不是 `tests===418`（I1.3 就因为这个过拟合，加一条测试就红）。
23. **`NODE_ENV=test` 漏了会静默空转**（表现为 60s 超时而不是断言失败），环境注入要检查。
24. **架构扫描要用 11 词并集**（v23 已扩表，不再是 I1.3 的 7 词）：`task-loop,researcher,writer,reviewer,研究员,撰写者,审核者,code-loop,developer,tester,coordinator`。`purity-check.mjs` 的**默认表只有 I1.2 四词**，必须用 `--forbid` 显式传全表，否则等于没扫；**英文注释也会命中**。

### 3.6 I1.4 特有的高危区（我从需求里读出来的，按风险排序）

| 风险 | 出处 | 为什么危险 |
|---|---|---|
| **暂停 × 派发的原子性** | D-7.4 | 需求为这一处连改了三轮（v12/v13/v14）：落包与派发必须**单次 CAS** 一次提交（包推入 + 轮次/派发计数 + 节点与实例状态），事件在 CAS 后发。否则会出现"暂停先落盘却被派发覆盖"或"假 CAS 冲突" |
| **CAS 扩到四键** | M-10 / D-10 1.1 | 漏改任何一处深比较，所有并发用例假失败；改错语义（把冲突当成功）会更糟 |
| **`pending` 首次有产生路径** | M-4 / C-10 | 状态机新增 `delivered→pending`、`pending→delivered`、`pending→expired`、`pending→rejected`，`test/wp2/state-machine.test.js` 有 4 处排他断言要同步改（D-10 第 5 条点名） |
| **交接包 16 键 → 25 键** | D-10 第 7 条 | `test/templates/fake-graph.test.js` 是精确键集合断言，漏一个键就红 |
| **审批拒绝不许造第二套文案** | B-08 / AC-62 | 单节点沿用「审批被拒绝，任务中止于 <动作>」，多节点走既有 `refusal` 升级路径 |

| **多节点提示词「工作区上下文」段** | v23 新增 A-6 / D-11 | 9 个多节点提示词末尾都要追加该段，`single` 图只有 1 个节点因而不追加；**判定只按节点数、不按模板名**，否则核心会踩架构纯净红线。审核提示词已有 `工作区：`，末尾只追加后三行，不能重复 |

### 3.7 环境结论：不需要 DSH

- **实现**：Node ≥ 22 + Git Bash + 仓库本身。**零运行时依赖**（`dependencies` 必须保持 `{}`），不用 `npm install`，不用联网。
- **验收**：70 条 AC 全用 `test/fixtures/mock-acp-agent.js`。需求 §3.3 第 3 条已定："需要真实宿主的 AC 使用仓库内 mock ACP agent"。
- **审批类 AC（31~35）只能靠夹具**：mock 已自带 `--permission=ask`（会发 `session/request_permission`），既有 `test/wp8/f1-permission.test.js` 已用 `permissionPolicy:'hold'` 造出「等待审批」。反过来，真实 DSH 写 cwd 内文件**不触发** permission，真机反而做不出来。
- **`attach` 不涉及 ACP**：只读跟随我们自己写的 `events.jsonl`；真正的会话恢复是 I1.8。

### 6.1 三类高频情形的处理剧本

**① 需求与基线说法不一致**
按 §1.2.1 的优先级从上往下取，取到就执行 —— **不要"先按实现方便的来"**。裁决记台账，写清取的是哪一级、为什么。

**② 某条 AC 在夹具上观测不到 / 停不稳**
判 `阻塞`，记录三件事：需求要求什么、试过哪些路径、为什么观测不到（附原始输出）。然后**继续推进其它 AC**，不要为了这一条停住。阻塞在交付时集中看，不算失败。

**③ 门禁从绿变红，但你判断不是自己的改动**
先建立基线：`git stash` 后复跑到 HEAD，或直接 `git worktree add` 一个干净副本跑同一命令。确认基线本身是绿的，再归因到自己的 diff；若确认是并行产物踩脏（`.orch/`、`.mock/` 残留），自己清理并隔离重跑。**归因结论记台账**，别把"我这边是好的"当结论。

### 6.2 只有这两类事需要集中评审（其余一律自己定）

1. **两条 AC 在最高优先级上真的互斥**，无法同时满足（例如同一输出被要求两种逐字版式）。
2. **某条 AC 的实现必须改动 M/C 清单之外的既有契约**，且不改就做不出来。

处理方式：写进 `decisions.md` 的「待评审」段，**只标这一个点，其它 AC 照常推进**，交付时一并提交。不要因为这两类问题卡住整体进度，也不要自行扩大契约改动范围。

### 6.3 一句总结

**过程你自己把控，标准是需求原文；交付时我要看到"70 条全实现、门禁全绿、每条裁决可追溯"。** 中间不用问我"这样可以吗" —— 按 §1.2.1 裁，按 §6 留痕，就是可以的。

另外，`docs/iterations/iteration-1~3/requirement.md` 与 `iteration-3/acceptance-*.md` 是最值得抄的作业：前者看"一份需求怎么写才可验收"，后者看"证据要落到什么颗粒度才算数"。
