# v1.2 发布说明（开发者版）

本文面向正在使用本产品、准备升级到 v1.2 的开发者与集成方。内容聚焦升级决策需要关注的能力变化和操作步骤，不替代随版本发布的完整 changelog、API diff 与迁移指南。

v1.2 的升级重点不是增加一套新概念，而是让配置错误更早暴露、日志更易关联、命令行更适合自动化，并减少重复执行带来的等待。下面先说明这些能力对现有项目的影响，再给出可执行的升级路径。

## 新功能

### 1. 配置校验前移，错误定位到文件与字段

v1.2 在启动阶段增加配置校验，检查字段名、值类型和已废弃项；校验失败时，错误信息会指出问题所在的配置文件与字段。

**对开发者的影响**

- 配置错误不再等到某个请求或任务触发时才暴露，可以在本地启动、CI 或 staging 阶段发现。
- 排查时不需要在多个配置文件之间猜测，按错误提示直接定位。

**升级注意**

- 过去被静默忽略的非法配置，在 v1.2 中可能直接导致启动失败。升级前应先跑一次配置校验，不要等到发布窗口再处理。
- 多环境项目要分别校验开发、测试和生产配置，避免只验证了默认 profile。

### 2. 结构化日志与关键路径关联信息

v1.2 的日志增加了结构化字段，并为关键执行路径补充关联标识和追踪信息，便于把一次请求或任务产生的日志串联起来。

**对开发者的影响**

- 日志平台可以按字段检索、聚合和告警，不再依赖全文匹配。
- 排障时可以用同一个请求或任务标识关联入口、执行过程和下游调用。

**升级注意**

- 新增字段通常向后兼容，但自定义采集规则、索引模板、仪表盘和告警查询需要同步字段映射。
- 如果现有脚本解析人类可读日志，建议改为消费结构化字段，避免日志文案调整导致脚本失效。

### 3. CLI 支持 dry-run 与 JSON 输出

v1.2 的命令行工具支持先预览变更再执行，并可输出机器可读的 JSON，方便 CI 和自动化脚本消费。

**对开发者的影响**

- 执行前可以核对将要变更的对象和范围，降低误操作风险。
- 流水线可以直接解析 JSON 结果，不必再对终端文本做正则匹配。

**升级注意**

- 依赖人类可读输出的脚本，应切换到 JSON 输出，并为使用的字段补充契约测试。
- 不要把展示用的文案当作稳定接口；需要长期依赖的字段应写入集成测试。

### 4. 增量执行与并发度配置

v1.2 支持对重复任务复用缓存、减少全量执行，并允许配置并发度。具体收益取决于项目规模、缓存命中率和可用资源，本文不给出固定倍数的承诺。

**对开发者的影响**

- 本地构建和 CI 中重复任务的等待时间有机会缩短。
- 可以根据机器规格和下游承压能力调整并发，不必始终使用固定值。

**升级注意**

- 缓存键规则发生变化时，应清理旧缓存后再执行，避免读到不兼容的缓存内容。
- 提高并发前先评估 CPU、内存、下游限流和锁竞争；建议保持原并发度完成首次升级，稳定后再单独调整。

## 升级步骤

建议按以下顺序执行，并在 staging 或预览环境验证通过后再进入生产。不要在同一批次里同时升级运行时、业务代码和并发配置，否则出问题时很难判断原因。

### 1. 升级前检查与基线记录

1. 确认当前版本、运行时版本、包管理器版本和依赖锁文件状态，确保工作区干净、锁文件已提交。
2. 对照随版本发布的 changelog、API diff 和迁移指南，列出与本项目相关的变更，并标记为“无影响 / 需改配置 / 需改代码 / 需迁移数据”。
3. 记录当前部署包或镜像的版本号与校验值，保留上一稳定版本的部署产物和配置快照。
4. 对配置和关键数据做可恢复备份，并实际验证备份可读；只做备份但不验证，等于没有备份。
5. 确认 v1.2 支持的运行时和依赖版本范围与当前环境匹配。不匹配时先升级运行时，再单独安排 v1.2 升级。
6. 选择低峰维护窗口，明确执行人、观察人和沟通渠道。

### 2. 锁定并安装 v1.2 精确版本

从发布渠道获取 v1.2 对应的精确补丁版本，写入依赖清单并更新锁文件。不要使用 `latest`、`next` 或未锁定的浮动范围，以保证本地、CI 和生产可以复现同一版本。

以下命令仅示范写法，`<package>` 和 `<v1.2-exact-version>` 必须替换为实际包名与发布页给出的精确版本：

```bash
# npm
npm install <package>@<v1.2-exact-version> --save-exact

# pnpm
pnpm add <package>@<v1.2-exact-version> --save-exact
```

安装后提交依赖清单与锁文件。若项目包含多个包，应统一更新到同一发布批次，避免新旧版本混用。

### 3. 处理配置与代码变更

1. 查看 CLI 帮助中的配置校验子命令，对每个环境的配置文件执行校验，修正字段名、值类型和废弃项。
2. 对 changelog 中标记为 breaking 的变更逐项替换；在 PR 中附上旧写法与新写法的对照，以及对应的回归用例。
3. 更新日志采集规则、索引模板、仪表盘和告警查询中的字段映射，确认新增字段能被正确采集。
4. 更新消费 CLI 输出的脚本：能改用 JSON 的改用 JSON，并为关键字段增加断言。
5. 如果本次升级涉及数据迁移，先在备份副本上演练并记录耗时；确认迁移脚本的输入、输出和失败处理方式后再用于目标环境。

### 4. 清理缓存并重新构建

先清理旧构建缓存和增量缓存，再按锁文件重新安装依赖并构建。不要沿用升级前生成的缓存产物。

```bash
# 示例：Node.js 项目；请按项目实际技术栈替换
npm ci
npm run build
```

构建完成后检查产物版本号与依赖树，确认没有残留的旧版本包。若构建产物包含构建信息，确认其中的版本号已经指向 v1.2。

### 5. 运行测试与 dry-run 预演

1. 运行单元测试、集成测试和端到端测试，重点覆盖启动、鉴权、核心业务路径和错误处理。
2. 执行一次 dry-run，核对预览出的变更对象、数量和范围是否符合预期。
3. 在 staging 使用与生产同构的配置完整启动一次，检查健康检查、日志字段和下游连接。
4. 对自动化脚本执行一次真实调用，验证 JSON 输出字段、退出码和错误分支。
5. 对比升级前后的日志与关键指标，确认没有新增的异常类型。

### 6. 灰度发布与观察

先让一小部分流量或任务进入 v1.2，保持并发度和其他变更不变，观察以下信号：

- 错误率和超时是否上升；
- 启动、健康检查和重启是否正常；
- 日志字段是否完整，关联标识是否可用于排障；
- 下游依赖是否出现限流、连接数上升或锁竞争；
- CLI 与自动化脚本是否按预期返回。

观察窗口内没有新增异常后，再逐步扩大范围。不要在同一时间同时扩大流量和调整并发度；把两个变量分开，才能判断变化来自哪里。

### 7. 升级完成判定与收尾

满足以下条件后，可判定本次升级完成：

- 运行版本和构建产物均指向 v1.2；
- 健康检查持续通过，核心业务用例和鉴权测试通过；
- 错误率、延迟没有超出团队设定的可接受范围；
- 日志采集和关键告警正常，CLI 自动化脚本通过；
- 灰度范围已扩大到计划中的全量范围。

收尾时更新 CI 镜像、部署清单、内部文档和值班手册中的版本号；保留上一稳定版本的部署产物与配置快照，待观察期结束后再按团队规范清理。将本次升级遇到的配置问题、脚本改动和验证结果记录到变更单，供后续版本参考。

## 回滚方案

回滚不是升级失败后的临时操作，而是发布方案的一部分。执行前先判断“应用能否直接退回旧版本”和“数据是否仍与旧版本兼容”，再决定回滚顺序。原则是：优先恢复服务，使用已验证的上一稳定产物，不做未经演练的反向迁移，不在故障中重新构建新包。

### 1. 回滚触发条件与决策人

**触发条件**（发布前写进变更单并明确阈值）：

- 健康检查或启动连续失败，实例无法稳定提供服务；
- 核心业务路径、鉴权或关键集成出现大面积失败，且无法在约定修复窗口内止血；
- 错误率、延迟或超时相对升级前基线明显恶化，达到团队预设的回滚阈值；
- 出现数据写入异常、数据不一致、迁移失败，或旧版本无法读取新结构；
- 关键依赖、运行时、缓存或队列与 v1.2 不兼容，继续运行会扩大影响；
- 发现安全、权限或合规问题，热修复来不及覆盖发布窗口；
- 日志、监控或告警缺失到无法判断系统状态，且短时间无法恢复可观测性。

**决策人与职责**：

- 回滚由值班发布负责人（Release Owner）下达，值班 SRE/运维负责人和业务负责人共同确认；涉及数据恢复时必须有数据负责人参与。发布前指定主决策人、备份决策人和通知渠道，避免故障时临时找人。
- 执行人、观察人、数据负责人和沟通负责人各自明确。任何生产回滚都应先通知相关方，不允许无记录地单独操作。
- 决策时记录时间、触发指标、影响范围、预计数据损失（RPO）和恢复时间目标（RTO）。若回滚代价高于继续修复，需由上述负责人共同决定“前向修复”，并同样记录理由。
- 回滚窗口和备份保留时长在升级前确定；超过窗口仍无法恢复时，升级为重大事故流程。

### 2. 应用层回退到上一稳定版本

1. 先止血：将流量从 v1.2 摘除或切回旧版本，暂停 v1.2 的定时任务、消费者、迁移任务和批量写入，避免回滚过程中继续产生新格式数据。保留现场日志、指标和当前部署清单。
2. 从升级前记录的基线中取出上一稳定版本的镜像或部署包，核对版本号与校验值、镜像 digest。不要从当前分支重新构建，也不要用 `latest` 或未验证的缓存产物。
3. 在编排平台或部署系统中把副本、路由和流量切回旧版本；如果是灰度发布，先将灰度流量切回稳定版本，再逐步下线 v1.2 实例。确认所有实例都指向同一旧版本，避免新旧版本同时处理同一类任务。
4. 恢复与旧版本配套的启动参数、环境变量和配置版本。配置恢复见下一节；不要只回滚镜像而保留 v1.2 的配置。
5. 如果旧版本无法读取迁移后的数据或消息格式，停止应用层回滚，先按第 5 节处理数据兼容性；不要带病启动旧版本继续写入。
6. 记录每一步的开始和结束时间、执行人、使用的版本与 digest、命令或流水线链接，以及失败重试情况。

**判定点**：旧版本实例启动成功、健康检查通过，且没有旧版本不认识的配置或数据格式，才进入后续验证。

### 3. 依赖与锁文件恢复到升级前版本

- 从升级前的发布标签或提交恢复依赖清单与锁文件，不要在旧锁文件上逐个手工降级。应用回滚若直接使用上一稳定构建产物，可跳过重新安装，但仍需确认运行时和依赖与产物一致。
- 如果升级时同时调整了运行时，必须一并恢复到基线版本；无法降低宿主机运行时时，改用携带固定运行时的上一稳定镜像或容器，避免“旧应用 + 新运行时”的组合。
- 使用锁文件做干净安装并重新构建，确认依赖树中没有 v1.2 引入的包。以下为示例，按实际包管理器替换：

```bash
git switch --detach <last-stable-tag>
npm ci
npm run build
npm ls <package>
```

- 检查构建产物中的版本信息和依赖清单，确认 CI 与生产使用同一份锁文件。不要把 `npm install` 产生的隐式升级带入回滚。
- 若某个下游 SDK 或协议已经按 v1.2 升级且无法降级，应把它当作数据或协议兼容问题处理，而不是强行覆盖依赖版本。

### 4. 配置快照恢复与旧缓存清理

1. 从升级前保存的配置快照恢复对应环境的配置，逐项 diff 后再应用。禁止把开发或测试环境快照应用到生产。
2. 密钥、证书和令牌从密钥管理系统恢复或轮换，不把明文密钥写入配置文件或发布说明；确认旧版本使用的密钥引用仍然有效。
3. 恢复功能开关、限流、并发度和队列配置到升级前值。首次回滚不要顺便调整并发度或容量，避免引入第二个变量。
4. 清理 v1.2 生成且旧版本可能误读的缓存，包括构建缓存、增量缓存、应用层缓存和共享缓存中的相关命名空间。优先按版本或前缀隔离并删除 v1.2 命名空间，不要清空整库。
5. 如果缓存键规则已经变化，应在旧版本开始服务前完成清理或切换命名空间；CDN 和边缘缓存只在确认内容与版本相关时按 URL 或标签精准失效。
6. 保留缓存清理记录和清理范围。清理后可按需预热，但预热必须使用旧版本能够识别的数据。

### 5. 数据迁移不可逆时的处理与备份恢复

升级前必须在变更单中把迁移标记为“向后兼容”“可逆”或“不可逆”，并记录备份位置、保留时间、RPO/RTO。回滚时按以下顺序判断：

1. **结构向后兼容**：旧版本仍能读写新结构时，可先回滚应用，保留新结构，后续再安排清理。不要为了“看起来干净”立即执行反向迁移。
2. **迁移可逆且产品明确支持**：只使用产品提供的、已在 staging 演练过的回滚命令，并由数据负责人确认影响范围。不要手写 SQL 反向修改生产数据。
3. **迁移不可逆或旧版本不兼容**：不要直接反向执行迁移脚本，也不要让旧版本连接新结构继续写入。应停止写入和后台任务，保留当前数据库快照作为现场证据，然后从升级前备份恢复。

备份恢复的操作要求：

- 先验证备份可读、校验值正确，并在隔离实例中实际恢复一次；只检查“备份任务成功”不算验证。
- 优先恢复到新实例，验证表结构、关键数据量、索引和权限后，再切换连接；不要直接覆盖生产库，除非已确认无法保留现场且获得数据负责人批准。
- 记录备份时间点与恢复点之间的数据窗口，评估需要补回的数据。可从审计日志、消息队列、导出文件或业务补偿中重放；重放前做幂等检查，避免重复扣款、重复通知等副作用。
- 切换连接后，将旧库或旧实例保持只读一段时间，确认没有遗漏写入后再按规范下线。数据库账号、连接串和密钥同步恢复到可用状态。
- 如果恢复无法满足业务可接受的 RPO，或备份不可用，应停止回滚并评估前向修复 v1.2；此时必须由业务、数据和发布负责人共同确认，不得用“先上线再说”掩盖数据损失。

**外部副作用无法自动回滚**：邮件、短信、支付、Webhook、对象存储、搜索索引和第三方系统调用可能已经生效，需要列出清单并执行补偿或人工核对。应用回滚完成不代表业务副作用已经消失。

### 6. 回滚后的验证清单

回滚后逐项确认并记录结果：

- [ ] 所有实例的版本号、镜像 digest 或部署包校验值与上一稳定版本一致，没有残留 v1.2 实例。
- [ ] 启动日志无配置解析错误，存活和就绪健康检查持续通过，依赖连接正常。
- [ ] 鉴权、权限、核心业务路径、关键集成和错误分支通过冒烟与回归用例。
- [ ] 数据表结构、迁移记录、关键记录数和业务对账结果与预期一致；不可逆迁移已按第 5 节完成恢复或补偿。
- [ ] 配置与升级前快照一致，功能开关、限流、并发度和密钥引用均已恢复。
- [ ] 旧版本能够正确读取缓存；没有命中 v1.2 专用键，缓存命中率和下游压力正常。
- [ ] 日志采集、字段解析、追踪标识和关键告警恢复正常；旧版本日志格式与现有看板、查询兼容。
- [ ] CLI、CI 流水线和自动化脚本的退出码、JSON 字段与回滚前一致。
- [ ] 错误率、延迟、超时和资源使用回到升级前基线附近，外部副作用已完成对账。
- [ ] 相关方已收到回滚结果、影响范围、数据恢复情况和下一次更新时间。

验证不通过时不要宣布回滚完成；继续按事故流程处理，并防止旧版本在异常数据上扩大写入。

### 7. 观察、沟通与复盘

- 回滚后保持比平时更密集的监控，观察窗口由团队在变更单中约定，建议至少覆盖一个完整业务高峰或关键批处理周期。重点看错误率、延迟、健康检查、队列积压、数据一致性和日志采集。
- 在状态页、事故群和客户支持渠道同步信息：发生了什么、影响了谁、是否回滚、是否有数据损失、下一次更新时间。对外沟通不猜测根因，不承诺未经验证的恢复时间。
- 观察期内保留上一稳定版本、配置快照、备份和回滚前的现场数据，不要立即清理。确认稳定后，再按保留策略处理。
- 记录完整时间线：触发指标、决策人、回滚步骤、数据恢复点、验证结果和遗留问题。复盘聚焦可改进项，明确修复负责人和截止时间。
- 在根因修复、回归测试通过并重新演练“升级 → 回滚”之前，不重新发起同一版本升级。若必须再次发布，使用新的变更单并重新评估数据迁移和备份。

### 8. 回滚演练与完成标准

发布前在 staging 至少演练一次完整回滚：使用与生产同构的配置和备份，记录各步骤耗时，确认上一稳定产物可部署、备份可恢复、旧版本能读取数据。演练发现的问题应在正式发布前修复。

满足以下条件才可判定回滚完成：服务恢复且版本回到基线；核心用例、鉴权和数据校验通过；异常指标回到可接受范围；数据损失与外部副作用已确认并记录；相关方已收到通知；回滚记录和后续修复计划已归档。
