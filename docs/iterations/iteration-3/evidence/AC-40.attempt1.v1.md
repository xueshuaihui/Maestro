# DevKit v1.2.0 发布说明

> 适用对象：已在项目或 CI 中使用 DevKit v1.x 的开发者  
> 目标版本：v1.2.0  
> 上一稳定版：v1.1.4

v1.2.0 聚焦构建效率、可观测性、配置治理和网络策略。默认行为尽量与 v1.1.x 保持一致，升级的主要动作是更新依赖、执行一次配置迁移，并把 CI 的 Node.js 与缓存配置对齐到新版本。

建议先通读「升级步骤」，在独立分支完成升级和验证，再按灰度节奏发布。

## 新功能

### 1. 增量构建与内容寻址缓存

`devkit build` 默认启用增量构建：只重新构建受变更影响的模块，并把结果写入内容寻址缓存。重复构建时可以直接复用缓存，减少本地和 CI 中的重复工作。

- 缓存目录：`.devkit/cache/v2`
- 缓存键包含锁文件、构建配置和 DevKit 版本
- 升级后旧缓存不会命中，会按需重建
- 可用 `--no-cache` 临时绕过缓存

```bash
# 默认使用缓存
devkit build

# 绕过缓存，用于排查缓存相关问题
devkit build --no-cache
```

CI 中如需跨任务复用缓存，请持久化 `.devkit/cache/v2`，并让缓存键包含锁文件和配置文件的哈希。不同分支或不同 Node.js 大版本建议使用不同的缓存命名空间，避免缓存相互污染。

缓存主要减少重复构建；实际收益取决于项目结构、变更范围和缓存命中情况。

### 2. 结构化日志与 OpenTelemetry 导出

新增 `--log-format json`，每条日志输出为一行 JSON，便于日志平台按字段检索。默认仍为人类可读文本，现有日志解析不受影响。

新增 `DEVKIT_OTLP_ENDPOINT`，用于把 trace/span 导出到支持 OTLP/HTTP 的采集端。

```bash
# JSON 日志
devkit run --log-format json

# 导出 trace/span
DEVKIT_OTLP_ENDPOINT=http://localhost:4318 devkit run
```

PowerShell 中设置环境变量：

```powershell
$env:DEVKIT_OTLP_ENDPOINT = "http://localhost:4318"
devkit run
```

注意事项：

- 日志中的敏感字段默认脱敏；自定义字段不要写入密钥、令牌或个人信息。
- 接入前确认采集端支持 OTLP/HTTP，并按团队规范配置采样与保留策略。
- 若只在部分环境启用，建议通过环境变量或 CI 配置控制，不要写死在共享配置里。

### 3. 配置校验与迁移命令

新增两个命令：

- `devkit config validate`：校验配置文件语法、字段名和值类型，报错包含文件、行号和修复建议。
- `devkit config migrate`：把 v1.1 的配置迁移到 v1.2.0 结构。

```bash
# 基础校验
devkit config validate

# 严格校验：未知字段视为错误，建议在 CI 中使用
devkit config validate --strict

# 先预览迁移改动
devkit config migrate --from 1.1 --dry-run

# 确认后写入
devkit config migrate --from 1.1 --write
```

建议先执行 `--dry-run`，确认 diff 后再 `--write`。迁移会重写配置文件，执行前请确保文件已提交或已备份。迁移后仍需人工 review diff，不要盲目接受全部改动。

本地首次升级如果历史遗留字段较多，可以先不加 `--strict`，待清理完再在 CI 中启用。

### 4. 可配置的重试与超时策略

新增以下配置项，用于控制网络请求的超时与重试：

```yaml
network:
  timeoutMs: 30000
  retry:
    maxAttempts: 3
    backoffMs: 500
```

- 默认值与 v1.1.x 行为一致；只有显式配置才会改变行为。
- 默认只对幂等请求重试。非幂等操作需要显式开启；重试只表示允许再次尝试，不代表请求一定成功。
- `backoffMs` 是退避基准值，请结合依赖服务的承载能力设置，避免集中重试放大压力。

## 升级步骤

以下步骤以 npm 为例，pnpm、yarn 在依赖安装处给出等价命令。建议在独立分支完成升级，并逐步验证。

### 1. 升级前准备

1. 新建升级分支，确认工作区干净，便于审查和追踪变更。
2. 备份 `devkit.config.*`、锁文件、CI 配置和当前构建产物。
3. 记录当前版本和提交：

   ```bash
   devkit --version
   git rev-parse HEAD
   ```

4. 确认 Node.js 版本：

   ```bash
   node --version
   ```

   v1.2.0 最低要求 Node.js 18.17，建议使用 20 LTS。

5. 确认本次升级的 breaking changes：
   - Node.js 16 不再支持，最低要求为 18.17。
   - 缓存目录从 `.devkit/cache` 变为 `.devkit/cache/v2`。
   - 部分旧配置键已弃用，需通过迁移命令处理。
   - v1.2.0 不涉及持久化数据或服务端 schema 迁移。

### 2. 升级依赖

按项目使用的包管理器选择一种：

```bash
# npm
npm install -D devkit@1.2.0

# pnpm
pnpm add -D devkit@1.2.0

# yarn
yarn add -D devkit@1.2.0
```

如果项目直接依赖多个 DevKit 子包，请全部对齐到 `1.2.0`，避免 v1.1.4 与 v1.2.0 混用。安装后检查锁文件变更，确认没有引入非预期的版本。

```bash
npm ls devkit
```

### 3. 迁移配置

```bash
# 1) 预览迁移内容
devkit config migrate --from 1.1 --dry-run

# 2) 确认无误后写入
devkit config migrate --from 1.1 --write

# 3) 严格校验
devkit config validate --strict
```

迁移前确认配置文件已提交或已备份。迁移后 review diff，重点检查：

- 被重命名或删除的字段是否符合预期；
- 新增字段的默认值是否适合当前项目；
- 是否存在只为兼容历史环境而保留的临时配置。

如果 `--strict` 报未知字段，按错误提示删除或替换；不确定的字段先查迁移说明，不要直接忽略。

### 4. 更新 CI

- 将 CI 的 Node.js 版本改为 18.17+，建议 20 LTS。
- 缓存路径改为 `.devkit/cache/v2`，缓存键包含锁文件哈希、配置哈希和 Node.js 大版本。
- 在流水线中加入配置校验和构建检查：

  ```bash
  devkit config validate --strict
  devkit build --check
  ```

- 如果 CI 使用固定版本镜像，更新镜像 tag，避免流水线仍拉取旧版 DevKit。
- 使用 `npm ci`、`pnpm install --frozen-lockfile` 或 `yarn install --immutable`，确保依赖版本与锁文件一致。

GitHub Actions 示例：

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm

- run: npm ci
- run: npx devkit config validate --strict
- run: npx devkit build --check
```

如需复用构建缓存：

```yaml
- uses: actions/cache@v4
  with:
    path: .devkit/cache/v2
    key: devkit-${{ runner.os }}-node20-${{ hashFiles('**/package-lock.json', 'devkit.config.*') }}
```

### 5. 本地验证

```bash
devkit doctor
devkit build
npm test
```

验证清单：

- [ ] `devkit --version` 输出 `1.2.0`
- [ ] `devkit doctor` 无 error
- [ ] `devkit config validate --strict` 通过
- [ ] 构建成功，产物与 v1.1.4 对比无意外差异
- [ ] 关键测试通过
- [ ] 启用 JSON 日志时，日志可被正常解析
- [ ] 启用 OTLP 导出时，采集端能看到对应 trace/span

建议在合并前把升级分支的 CI 结果与 v1.1.4 的基线对比，确认构建成功率、耗时和错误率没有明显异常。

### 6. 分阶段发布与观察

1. 先发布到测试环境或内部 dogfood 环境，完成一轮完整构建与关键链路验证。
2. 再按 5% → 25% → 50% → 100% 逐步放量；比例和节奏按实际发布系统调整。
3. 每个阶段观察构建成功率、错误率、P95 耗时和关键业务指标，至少覆盖一个发布窗口。
4. 指标正常后再进入下一阶段；确认全量稳定后，再结束本次发布观察。

### 7. 常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `ERR_DEVKIT_NODE_VERSION` | Node.js 低于 18.17 | 升级 Node.js，或使用项目的版本管理器切换到 18.17+ |
| `ERR_DEVKIT_CONFIG_UNKNOWN_KEY` | `--strict` 下存在旧字段 | 运行 `devkit config migrate`，或按提示删除/替换字段 |
| 缓存命中异常 | 缓存目录或缓存键变更 | 清理 `.devkit/cache/v2` 后重新构建 |
| CI 仍使用旧版 | 镜像 tag 或锁文件未更新 | 更新镜像 tag，确认锁文件已提交并使用冻结安装 |

升级过程中如遇到未覆盖的问题，请附上 `devkit --version`、`devkit doctor` 输出和最小复现步骤，提交到项目 issue 跟踪器。
