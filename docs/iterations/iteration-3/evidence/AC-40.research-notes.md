# v1.2 发布说明：研究笔记（Round 1）

- 状态：供 writer 起草 `release-notes.md` 使用
- 受众：已经使用 v1.2 之前版本的开发者（应用开发者 / 集成方）
- 目标产物：`release-notes.md`
- 本轮范围：仅「新功能」「升级步骤」；**「回滚方案」按计划留到第 2 轮**
- 重要说明：当前工作区未提供产品 changelog、API diff 或运维手册。以下功能名、命令和字段是**写作骨架与待核实项**，writer 应优先用真实发布信息替换；若确实没有产品资料，保留结构并使用中性、可验证的表述，不要编造具体版本号、性能数字或 breaking change。

## 一、任务理解与交付节奏

1. 最终发布说明必须且只能包含三个二级章节：
   - `## 新功能`
   - `## 升级步骤`
   - `## 回滚方案`
2. 第 1 轮只写前两节，**故意不写「回滚方案」**，连标题、占位符、预告句都不要出现。
3. 第 1 轮提交后审核应会以“缺少回滚方案”驳回；这是预期门禁，不要在第 1 轮自行补写或向审核解释“稍后补”。
4. 第 2 轮在同一文件上补写「回滚方案」，并保留前两节内容，形成完整三节版本。
5. 面向开发者，重点写“对我有什么影响、我要改什么、怎么验证、出问题怎么办”，避免营销文案。

## 二、第 1 轮：新功能（建议内容）

### 写作原则

- 每项功能按“能力 → 开发者收益 → 是否需要迁移/注意”组织。
- 只写对升级决策有影响的内容；纯 UI 装饰不必单列。
- 未确认的量化收益（如“快 3 倍”）一律删除或改为定性表述。

### 建议条目（按真实 changelog 取舍）

1. **更严格的配置校验**
   - 启动时校验配置字段、类型和废弃项，错误信息定位到文件与字段。
   - 开发者收益：把配置错误从运行时前移到启动/CI 阶段。
   - 注意：原先被静默忽略的非法配置现在可能直接报错，升级前需跑一次配置检查。

2. **结构化日志与可观测性增强**
   - 新增结构化日志字段/事件，便于接入现有日志平台；补充关键路径的追踪信息。
   - 开发者收益：排障时可按请求/任务关联日志，不再靠全文检索。
   - 注意：日志字段新增通常兼容，但自定义采集规则需要同步字段映射。

3. **CLI 的 dry-run / JSON 输出**
   - 支持先预览变更再执行；机器可读输出便于 CI 和脚本消费。
   - 开发者收益：降低误操作，便于自动化和流水线集成。
   - 注意：脚本若依赖人类可读输出，建议改用 JSON 输出并固定字段。

4. **增量执行与并发优化**
   - 对重复任务复用缓存，减少全量执行；并发度可配置。
   - 开发者收益：缩短本地和 CI 反馈时间。
   - 注意：缓存键规则变化时需清理旧缓存；并发相关配置需评估资源上限。

5. **依赖与运行时支持更新**
   - 明确 v1.2 支持的运行时/依赖版本区间，标注已弃用项及移除时间。
   - 开发者收益：知道何时必须升级语言运行时或锁文件。
   - 注意：这是升级步骤中最容易触发构建失败的部分，应与“升级步骤”互相引用。

> writer 提示：若真实资料不足，保留 3–4 项最确定的能力即可；宁可少写，不要写无法验证的承诺。

## 三、第 1 轮：升级步骤（建议内容）

### 推荐结构

1. **升级前检查**
   - 确认当前版本、运行时版本、依赖锁文件状态。
   - 备份配置与数据；记录当前部署镜像/包版本，作为后续回滚基线（第 1 轮只做备份动作，不展开回滚方案）。
   - 在 staging 或预览环境先升级，不在生产直接试。

2. **更新依赖**
   - 给出包管理器命令的占位形式，例如安装 v1.2 的精确版本并更新锁文件。
   - 提醒：不要使用浮动的 `latest`；锁定到具体版本，便于复现和回退。

3. **处理配置与代码变更**
   - 运行配置校验/迁移工具（如有）。
   - 按 changelog 替换废弃字段、API 或 CLI 参数。
   - 对 breaking change 给出“旧写法 → 新写法”的最小示例。

4. **构建与测试**
   - 清理旧缓存后重新构建。
   - 跑单元测试、集成测试和一次 dry-run/预览执行。
   - 重点验证：启动、鉴权、核心业务路径、日志采集、自动化脚本。

5. **分批发布与观察**
   - 先灰度一小部分流量/任务，观察错误率、延迟和日志。
   - 确认稳定后再扩大范围。
   - 给出“升级完成”的可判定标准，例如版本号、健康检查、关键用例通过。

6. **升级后收尾**
   - 更新团队文档和 CI 镜像版本。
   - 记录本次升级遇到的问题与处理方式。

### 可直接复用的命令骨架

> 下列命令为结构示例，writer 必须替换为产品真实命令；不要保留无法执行的占位符。

```bash
# 1. 记录当前版本
<tool> --version

# 2. 安装 v1.2 精确版本
<package-manager> install <package>@1.2.0

# 3. 配置校验 / 迁移（如提供）
<tool> config validate
<tool> migrate --dry-run

# 4. 构建与测试
<tool> build
<tool> test

# 5. 预览变更
<tool> apply --dry-run
```

## 四、第 2 轮备用：回滚方案（本轮不得写入 release-notes.md）

> 本节仅供 writer 第 2 轮使用；第 1 轮生成 `release-notes.md` 时必须整节排除。

### 回滚触发条件

- 升级后核心路径错误率显著上升，或健康检查持续失败。
- 出现数据/配置不兼容，且无法在约定时间内热修复。
- 关键依赖或运行时与 v1.2 不兼容，影响发布窗口。

### 回滚层级

1. **应用层回滚（首选）**
   - 重新部署上一个稳定镜像/包版本。
   - 恢复升级前的配置快照。
   - 若升级包含不可逆数据迁移，先确认备份可恢复，再执行应用回滚。

2. **依赖层回滚**
   - 将依赖版本与锁文件恢复到升级前提交。
   - 清理 v1.2 产生的缓存，避免旧版本读取新格式缓存。

3. **数据层回滚（仅在确认兼容性后）**
   - 优先使用升级前备份恢复；不要直接反向执行迁移脚本，除非产品明确支持。
   - 回滚后校验关键表和配置的完整性。

### 回滚后验证

- 版本号回到基线，健康检查通过。
- 核心业务用例、鉴权、日志采集恢复正常。
- 错误率和延迟回到升级前水平。
- 通知相关方回滚完成，并记录根因与后续修复计划。

### 回滚演练建议

- 在 staging 至少演练一次“升级 → 回滚”，确认备份可用、步骤耗时可接受。
- 明确回滚决策人和沟通渠道，避免故障时临时确认。

## 六、风险与待确认项

1. **产品事实缺失**：没有 changelog/API diff，功能点和命令需 writer 用真实资料替换；否则发布说明会显得空泛。
2. **breaking change 未知**：升级步骤必须显式提示读者查阅 changelog；不要把“兼容”写成绝对承诺。
3. **回滚窗口未知**：第 2 轮需确认数据迁移是否可逆、备份保留时长、旧版本能否读取新数据。
4. **审核节奏**：第 1 轮缺回滚方案会被驳回是计划内动作，不要为了“一次通过”提前补写。
