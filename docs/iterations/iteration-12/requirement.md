## 一、背景与问题

### 1.1 现状与问题

I1.9 把运行过程沉淀成三层记录，I1.10a / I1.10b 把「看不见」变成「看得见、点得进」：用户能列出实例、画流程图、下钻看卡片与证据、处理升级、一键唤起宿主会话。但阶段一的最后一块——治理与审计——仍是缺口，用户今天的处境是：

- **链建了却验不了**：事件日志已是只追加、首尾相接的链，每条都带前序指纹，但没有任何办法当着用户的面证出「这条没被人改过」。用户想知道「这份审计还能不能信」，只能手工逐条核对指纹，且改动一条记录后没有任何可见的失败提示。I1.9 明确把「篡改检测报告 / 校验命令」留给了本迭代。
- **谁能唤醒谁没人管**：路由层按工作流边直接投递唤醒，角色声明的唤醒白名单没有在决策点被强制校验。一个未被授权的角色可能被唤醒并拿到上下文，事后既没有拦截提示也没有可追溯的拒绝留痕。用户无法回答「这个角色凭什么被叫起来」。
- **证据过期照单全收**：交接前只校验证据引用「存在 / 缺失」，不校验它与声明产物是否还是同一份内容。产物在生成后被改动，旧引用仍然指向一个存在的文件，交接照常发生，用户拿到的是对不上号的证据。
- **高风险节点能悄悄过**：发布、数据变更、合规意见、副作用高的节点，其下游没有被强制要求人工终审或升级路径。一次自动化流转就可能把高风险产物直接推到下游，用户事后才发现「没人签过字」。
- **审计记了太多也漏了该记的**：连接线聚合、角色状态、会话状态这些派生或执行细节与主审计混在一起，真正该留痕的节点状态变更、交接包状态变更反而不突出，用户翻审计日志像翻流水账。
- **并行与预算没有刹车**：实例能同时铺开多少节点没有上限，预算耗尽时节点直接失败。用户既看不到「为什么一下铺这么多」，也在预算见底时得到一个失败态而不是可恢复的暂停态。
- **包带不走也进不来**：角色与工作流能导出，但依赖的技能、派生父、子工作流不跟着走，离线导入后缺这少那；导入也不校验签名与版本，第三方包可以直接落进本地资产库，用户无从判断「这包是谁给的、能不能用」。
- **升级引用改不动**：角色与工作流换了新版，派生角色和工作流里的旧引用不会自动升级，用户只能手工逐个改，改漏一处运行时就取到旧定义。
- **日志与追踪出不去**：事件日志和追踪跨度只在本机文件里，用户想交给外部系统统一看，没有开放的导出格式。
- **反复出现的反模式看不见**：文档类节点长期卡在校验、本可并行的节点被串成一条线跑、审核节点次次附和上游且拿不出独立证据——这些信号今天没有任何提示，用户只能凭直觉觉得「这次跑得不对劲」。
- **性能没有说法**：阶段一退出要求桌面应用可独立完成日常操作，但「20 个实例并发、50 个活跃会话、交接 2 秒内」没有任何一次可复述的取证，用户不知道系统扛不扛得住。

不解决会怎样：`docs/index.md` 把治理审计（链式哈希 + 权限拦截 + 证据过期 + 签名校验 + 版本迁移）列为阶段一退出条件（913 行），把「桌面应用能否独立完成日常操作」列为关键判断点（1044 行）。I1.12 是这条判断点的最后承载迭代：不做，阶段一无法收口，前面六个能力域攒下的信任链在「交接那一刻」断掉。

### 1.2 目标与成功衡量

做完之后，用户可观测的变化：

1. **审计当场可验**：在夹具实例上改动事件日志任意一条记录，用户执行一次校验即得到「链已断、第 N 条失配」的明确失败提示；未改动的原件校验通过并给出完整条数。衡量：篡改命中 100%，正常链误报 0。
2. **越权与过期在交接前被拦**：白名单外的唤醒、与声明产物指纹不一致的证据，都在交接前被拒绝，用户看到具体拒绝原因，并能查到一条拒绝留痕。衡量：越权漏拦 0、过期证据漏放 0、拒绝留痕率 100%。
3. **高风险有人签字**：缺少人工终审或升级路径的高风险工作流在校验阶段就被挡下，补上后才能跑；有终审路径的必须等人裁决才继续。衡量：高风险缺终审拦截 100%。
4. **包带得走、进得来、升得动**：导出包含全部依赖闭包；签名无效与版本不兼容的包被拒绝且不污染本地资产；`orch migrate` 能把派生角色与工作流引用升到新版并列出变更项。衡量：闭包漏项 0、坏包放行 0、升级后可校验通过。
5. **扛得住且说得清**：mock 压测下 20 并发实例、50 活跃会话时 handoff 延迟 <2s，并给出逐档数据；真实宿主面按本机证据分级单列，不把 mock 结果写成真实宿主达标。衡量：mock 实测延迟 <2s，证据分级标注 100%。
6. **零回归**：I1.10b 的 51 条 AC、I1.9 的 27 条 AC 判据与逐字文案原样成立，状态迁移唯一入口、事件先落盘再广播、纯净扫描、中文唯一来源等不变量照旧。衡量：上游 78 条 AC 判据改动 0。

| §2.3 路由层权限拦截：角色唤醒白名单校验 | 实例负责人、安全关注者 | 谁能唤醒谁没人管 | 白名单外唤醒被拒、不投递、留痕；白名单内正常交接 |

| §2.5 高风险节点人工终审 | 合规关注者、发布负责人 | 高风险节点悄悄过 | 缺终审路径的工作流被挡下；有路径必须等人裁决；治理规则不重做 UI |
| §2.6 审计粒度规则落地 | 翻审计日志的人 | 审计记太多又漏该记的 | 节点/交接包状态变更进主审计；连接线/角色/会话状态不单独审计 |
| §2.7 预算与配额：并行度上限与预算耗尽暂停 | 资源负责人、值班人 | 并行无刹车、耗尽即失败 | 超限节点排队；预算耗尽暂停可恢复，不失败 |
| §2.8 角色包 / 工作流包导出（含依赖闭包） | 资产作者、迁移者 | 包带走后缺依赖 | 导出含技能/派生父/子工作流闭包，离线可导入 |
| §2.9 签名校验 + 版本兼容检查 | 导入者、安全关注者 | 第三方包无从判断 | 签名有效且版本兼容才导入；坏包拒绝且不污染资产 |
| §2.10 版本迁移工具 `orch migrate` | 升级资产的人 | 派生引用改不动 | 列出变更项、升级派生角色与工作流引用、升级后可校验 |
| §2.11 可观测性导出（OpenTelemetry 格式） | 运维、外部系统消费者 | 日志与追踪出不去 | 事件日志与追踪导出为开放格式，导出只读不改实例 |
| §2.12 反模式监控 | 流程改进者、值班人 | 反模式看不见 | 文档瓶颈/串行化退化/确认偏误三类信号可查，只读提示 |
| §2.13 性能基线（20 实例 / 50 会话 / handoff <2s） | 实例负责人、验收人 | 扛不扛得住没说法 | mock 压测达标并分级；真实宿主面留本机取证 |
| §2.14 功能之间的衔接 | 所有使用上述能力的人 | 治理能力如何串成闭环 | 从建链→拦截→判定→留痕→迁移→导出→压测的完整路径 |
| §2.15 用户可见的业务规则 | 全部读者 | 规则需可引用核对 | BR-01~BR-19 逐条可对照 AC |

### 2.2 链式哈希审计：`prev_event_hash` 加固与篡改检测

- **使用角色**：审计人、值班人、需要确认「这份日志能不能信」的人。
- **使用场景**：一次实例跑完后复盘，或怀疑日志被人改过时，用户要能当场验一验。
- **用户操作**：用户对某个实例执行一条校验命令；系统逐条核对审计链的首尾衔接，给出「完整 / 断了」的结论。用户还可以在一份被改动的日志副本上执行同一命令，看它是否报出断点。
- **预期效果**：正常链显示「链完整，共 N 条」；每条事件仍带有指向前一条的指纹（规划原文称 `prev_event_hash`，首条为固定起点），从首到尾无断点。被改动的副本显示失败，并指出第一条对不上的记录序号，用户能据此定位是第几条被改。
- **异常情况**：日志有不可读行、序号不连续、历史遗留的无标记旧记录，分别给出可理解的提示，不崩溃；升级前的旧记录按「历史」对待，不校验、不回填、不算断点（沿用 I1.9 口径）。（反向映射：上述不可读行 / 序号不连续 / 旧记录情形由 AC-01 的机检与 AC-02 的 I1.9 衔接承担，处置口径见 D-2。）
- **边界说明**：本能力是 I1.9 既有 append-only 链的「加固」，不重写历史、不改链格式、不重置起点；只覆盖事件日志，不覆盖宿主内完整执行日志；校验是只读操作，不改变实例状态、不追加新事件。篡改检测不自动修复或回滚被改记录。

### 2.3 路由层权限拦截：角色唤醒白名单校验

- **使用角色**：实例负责人、关注越权风险的人。
- **使用场景**：一个角色完成任务后，核心要决定叫醒下一个角色时。
- **用户操作**：用户不需要每次手动放行；只需在配置里为角色声明唤醒白名单，运行到交接时系统自动按白名单判断。事发后用户可查看被拒绝的唤醒记录。
- **预期效果**：白名单内的唤醒照常发生，目标角色开始工作；白名单外的唤醒被拒绝，目标角色根本不被叫起、不拿到上下文，用户看到明确的拒绝原因，并能在审计记录里查到一条「谁在何时想叫醒谁、因为不在白名单被拒」的留痕。
- **异常情况**：角色没有声明白名单、白名单配置不可读、目标角色不存在时，给出明确提示并按既有升级 / 挂起口径处理，不静默跳过、不放行。
- **边界说明**：拦截发生在核心的唤醒决策点，不依赖宿主；核心不能在宿主内核层拦截会话内的单次文件写入，那部分由宿主原生机制负责（基线 §4 能力域 6 边界）。

### 2.4 证据过期检测：指纹不一致拒绝交接

- **使用角色**：交接双方角色、值班人。
- **使用场景**：上游角色声称产出了某个文件并附了证据，下游即将接收前。
- **用户操作**：用户像往常一样让流程跑到交接；系统在投递前自动比对证据与声明产物是否还是同一份内容。用户不需要手工比对文件指纹。
- **预期效果**：证据与声明产物指纹一致、引用存在时，交接照常投递；不一致（产物被改动）、引用缺失时，交接被拒绝，用户看到诸如「证据与声明产物不一致，已拒绝交接」的可见原因，并按既有路径生成升级请求。
- **异常情况**：声明的产物路径不存在、产物为空、指纹无法计算时，按「不一致 / 缺失」处理并拒绝交接，不误放行；拒绝时给出可定位到节点与产物的原因。
- **边界说明**：本能力是治理侧「拒绝交接的判定」，只产出判定结果（是否过期、原因、关联节点），供 I1.11 证据浏览视图消费；本迭代不定义该视图的任何界面、按钮或文案位置。本能力不等于交接包 TTL 的 `pending → expired` 自动过期（见 §1.3 范围外）。证据「是否真的做过」的真实性由宿主侧或独立审核角色负责，核心只判引用存在、未过期、与声明产物一致。

### 2.5 高风险节点人工终审

- **使用角色**：合规关注者、发布负责人、实例负责人。
- **使用场景**：定义含发布、数据变更、合规意见或副作用高的工作流时，以及该节点跑到交接时。
- **用户操作**：用户在定义工作流时带上人工终审节点或升级路径；运行到高风险节点后，流程必须等人裁决才继续。用户校验一个缺终审路径的高风险工作流时，会收到明确提示。
- **预期效果**：高风险节点下游有人工节点或升级路径的，工作流校验通过；跑到该节点时，未经人工裁决不自动推进下游，裁决结果被记录。缺少终审路径的工作流在校验阶段就被挡下，提示用户补上 human 节点或升级路径。
- **异常情况**：高风险标记识别不出、终审节点配置不可读时，按「缺终审路径」从严处理并给出提示；不因识别失败而放行。
- **边界说明**：本能力是治理侧审计规则，判定「高风险下游必须有人工把关」并产出审计结果；不重做 I1.11 的人工干预队列界面——具体的「允许 / 拒绝 / 重派 / 终止」按钮与队列交互由 I1.11 提供，本迭代只把「需要终审 / 缺终审被挡」的判定结果交给它消费。

### 2.6 审计粒度规则落地

- **使用角色**：翻审计日志复盘的人、对日志可读性有要求的人。
- **使用场景**：用户打开一个实例的审计记录，想知道「到底哪些事被正式记了一笔」。
- **用户操作**：用户执行实例日志查看命令，按事件类型浏览。
- **预期效果**：主审计里清楚地记着两类变更——节点状态变更、交接包状态变更；健康度档位变化仍按 I1.9 口径进事件日志。用户看不到连接线聚合状态、角色状态、会话状态各自单独占一条主审计记录：连接线聚合是可从交接包状态随时重建的派生视图，角色状态是运行时派生投影，会话状态只进执行日志摘要。
- **异常情况**：某类事件写入失败时按既有事件总线纪律处理（落盘失败不广播），不出现「记了半条」；派生视图与主审计不一致时以主审计的交接包状态为准。
- **边界说明**：本规则只约束「主审计记什么」，不改变这三类状态本身的存在与展示——它们在流程图、下钻卡片上照常可见（I1.10a / I1.10b 既有能力），只是不作为独立审计事件落盘。

### 2.7 预算与配额：并行度上限与预算耗尽暂停

- **使用角色**：资源负责人、值班人。
- **使用场景**：一个实例里同时就绪的节点太多、或可用预算快用完时。
- **用户操作**：用户为实例配置并行度上限与预算；运行中不需要手工干预排队，预算耗尽时也不需要手工把失败改成重试。
- **预期效果**：同时进入执行的节点不超过上限，其余就绪节点排队等待，前面节点完成后按序补位，没有节点因此失败或被丢弃。预算不足以派发下一节点时，实例转为「已挂起」并给出「预算耗尽」的可见原因，而不是「失败」；补充预算后用户可让实例从挂起继续。
- **异常情况**：并行度上限配置为 0 或非法值、预算字段缺失时，给明确提示并按最保守口径（不新增并行派发）处理，不无限铺开。（反向映射：上限排队由 AC-11 承担、预算耗尽挂起由 AC-12 承担，非法值 / 缺失字段的保守口径见 D-6。）
- **边界说明**：并行度上限沿用角色实例的既有 `max_concurrent_sessions` 语义（基线 §3.3）与实例级预算；预算耗尽触发的暂停走既有挂起 / 恢复路径，不新造第三种实例状态；已开始执行的节点如何处理见附录 D-6。

### 2.8 角色包 / 工作流包导出（含依赖闭包）

- **使用角色**：资产作者、需要在另一台机器或团队间迁移资产的人。
- **使用场景**：用户要把一个自定义角色或工作流交给别人，或搬到离线环境。
- **用户操作**：用户对自己创建的角色或工作流执行导出，选一个导出位置。
- **预期效果**：导出包里不仅有这个角色 / 工作流本身，还自动带上它依赖的全部东西——它引用的技能、它派生自的父角色、它包含的子工作流——用户不需要逐个手动挑。接收方在离线环境导入后，依赖项齐全、资产可用。
- **异常情况**：某个依赖缺失、派生链存在循环时，导出失败并明确指出缺哪个依赖 / 哪处循环，不产出一个缺胳膊少腿的包。
- **边界说明**：闭包只包含该资产「真正依赖」的部分，不把无关资产一并打包；导出是只读操作，不改本地资产。

### 2.9 签名校验 + 版本兼容检查

- **使用角色**：导入第三方包的人、关注来源与兼容性的人。
- **使用场景**：用户拿到一个别人给的角色包 / 工作流包，要先判断能不能安全导入。
- **用户操作**：用户执行导入；系统在落库前自动校验包的签名与版本兼容性，并把结论告诉用户。
- **预期效果**：签名有效且版本与当前系统兼容的包，导入成功、资产可用，用户看到「签名有效、版本兼容」的确认；用户据此确认来源可信。
- **异常情况**：签名被改动 / 无效、版本高于当前且不兼容时，导入被拒绝，用户看到具体原因（签名无效 / 版本不兼容）；本地已有资产不被覆盖、不留半安装状态，资产库保持原样。
- **边界说明**：签名与版本校验是导入的前置门禁，先校验后写入；本迭代不负责替用户判断「这个签名者可不可信」——信任决策仍由用户基于来源自己做。签名方案与版本兼容判定口径见附录 D-7。

### 2.10 版本迁移工具 `orch migrate`

- **使用角色**：升级资产的人、维护派生角色与工作流的人。
- **使用场景**：角色或工作流出了新版，用户手里的派生角色和工作流还引用着旧版本。
- **用户操作**：用户执行 `orch migrate`；先看一份「将要改哪些引用」的清单，确认后再升级。
- **预期效果**：派生角色与工作流里指向旧版父角色 / 技能 / 子工作流的引用被升级到新版；升级前清楚列出每一处将变更项；升级后用户可重新校验，校验通过；命令给出变更摘要，让用户知道改了什么。
- **异常情况**：已经是最新版本、没有可迁移项时，给出明确提示且不改动任何文件；引用目标不存在或迁移会破坏派生链时，不静默改写，给出可见错误并保留原资产。
- **边界说明**：迁移只改写引用，不改用户的业务定义正文；迁移前先备份，失败可回到原状（附录 D-8）；迁移是可重复执行的安全操作，重复执行不产生二次改写。

### 2.11 可观测性导出（OpenTelemetry 格式）

- **使用角色**：运维、需要把数据交给外部统一观测系统的人。
- **使用场景**：用户想把某个实例的审计事件与追踪跨度交给外部系统看。
- **用户操作**：用户对该实例执行导出，指定输出位置。
- **预期效果**：事件日志与追踪跨度都以开放的 OpenTelemetry 格式导出，外部系统能读；用户看到导出结果（导出条数 / 位置）。
- **异常情况**：实例没有追踪数据、事件日志有不可读行时，跳过不可读部分并给出提示，不中断整个导出、不崩溃；导出失败不修改原实例。（反向映射：无追踪数据 / 不可读行跳过与导出前后哈希不变由 AC-18 承担，映射口径见 D-9。）
- **边界说明**：导出是只读操作，不改变实例状态、不追加审计事件、不重写日志文件；本迭代只做导出，不做外部系统的接入或推送（那是阶段二 / 三的事）。具体的事件与跨度到开放格式的映射见附录 D-9。

### 2.12 反模式监控

- **使用角色**：流程改进者、值班人。
- **使用场景**：用户怀疑「这次跑得不对劲」，想知道有没有常见的反模式信号。
- **用户操作**：用户查看某实例的反模式信号列表。
- **预期效果**：系统给出可定位到实例 / 节点的信号，至少覆盖三类——文档瓶颈（文档类节点长期卡在校验）、串行化退化（本可并行的节点被串成一条线）、确认偏误（审核节点次次附和上游且拿不出独立证据）；每条信号带一句人能看懂的简述，用户据此判断要不要介入。
- **异常情况**：实例数据不足以判定某类信号时，不误报、不崩溃，给出「数据不足」的提示；信号规则配置不可读时给出明确提示。
- **边界说明**：信号是只读提示，不自动改调度、不改节点状态、不生成升级；具体判定阈值与信号规则见附录 D-10。反模式监控不替代 I1.11 的异常通知 UI，只把信号结果供其消费。

### 2.13 性能基线（20 实例 / 50 会话 / handoff <2s）

- **使用角色**：实例负责人、验收人、评估系统能否投入日常使用的人。
- **使用场景**：阶段一收口前，用户要确认系统在目标负载下交接是否够快、能否支撑多实例多会话。
- **用户操作**：用户在压测环境构造 20 个并发实例、50 个活跃会话，触发交接并查看延迟统计；验收人在本机对真实宿主面单独取证。
- **预期效果**：mock 压测下，20 实例并发时 handoff 延迟 <2s，50 活跃会话成立，并给出逐档延迟数据（如中位 / 较高分位 / 最大），用户能据此复述「在什么负载下有多快」。
- **异常情况**：延迟超目标、会话数达不到目标时，压测报告明确给出未达标档位与可定位的瓶颈点，不伪造达标、不静默略过。
- **边界说明**：mock 压测任何环境可做；**真实宿主（本机 DSH 0.2.2-rc.1）性能取证留本机**，其证据级别单列为「已实测（真实宿主面）」，不得用 mock 压测结果写成真实宿主达标（§3.3 第 3 条、AC-20 / AC-21）。指标口径见附录 D-11。

### 2.14 功能之间的衔接

用户走一遍完整体验，看到的是这样一条链：

1. 实例跑起来，每一步动作进审计链，每条带前序指纹（§2.2）。跑完后用户校验整链，确认「没被改过」。
2. 某角色完成任务要唤醒下一个：核心先看白名单（§2.3）——白名单外的叫醒被拦下并留痕，白名单内的继续。
3. 继续前先查证据（§2.4）——产物指纹对不上就拒收并生成升级，对上了才投递。
4. 若下游是高风险节点（§2.5），必须等人裁决才往下走；缺终审路径的工作流在定义阶段就被挡下。
5. 这一路的节点状态与交接包状态被如实记进主审计（§2.6）；连接线颜色、角色圆点这些派生视图照常显示，但不单独占审计记录。
6. 若同时就绪的节点太多（§2.7），超出的排队；预算见底就挂起而非失败，补预算再继续——用户看到的始终是「可恢复」而不是「崩了」。
7. 用户把这套角色 / 工作流连同依赖一起打包带走（§2.8），在别处先验签名与版本（§2.9）再导入；日后版本升级，用 `orch migrate`（§2.10）把派生引用升到新版并校验。
8. 需要交给外部系统时，导出事件与追踪（§2.11）；想看流程有没有走歪，查反模式信号（§2.12）。
9. 最后，用户在目标负载下跑一遍压测（§2.13），确认交接够快——mock 面与真实宿主面分级取证，谁达标谁不达标一目了然。

失败路径同样串得起来：越权被拦留痕 → 过期证据被拒生成升级 → 高风险缺终审被挡 → 预算耗尽挂起可恢复 → 坏包被拒不污染资产 → 迁移失败可回退 → 篡改被校验定位。每一步都有可见结果，没有静默吞掉的环节。

### 2.15 用户可见的业务规则

- **BR-01**：每条审计事件都带有指向前一条的指纹，首条使用固定起点；校验时从首到尾逐条核对，任意一条被改动即校验失败并指出第一条失配的序号。
- **BR-02**：链只追加、不改写、序号不复用；篡改检测是只增不改的加固，不重写历史记录、不重置起点，与 I1.9 既有链兼容。
- **BR-03**：核心在唤醒决策点按角色唤醒白名单校验；白名单外的唤醒被拒绝，不投递、不创建或驱动目标会话，并留一条可追溯的拒绝审计。
- **BR-04**：权限拦截发生在核心路由层，不依赖宿主；核心不拦截宿主内核层会话内的单次文件写入。
- **BR-05**：交接前校验证据与声明产物指纹一致且引用存在；不一致、缺失或指纹不可算时拒绝交接，不投递，并给出可定位到节点与产物的可见原因。
- **BR-06**：证据过期检测的判定由治理侧产出（是否过期、原因、关联节点），供 I1.11 证据浏览视图消费；本迭代不定义 UI。
- **BR-07**：发布、数据变更、合规意见、副作用高的节点，其下游必须有人工节点或升级路径；缺少的工作流在校验阶段不通过、不允许交接，补齐后通过。
- **BR-08**：高风险人工终审是治理侧审计规则，产出「需要终审 / 缺终审被挡」的判定结果；不重做 I1.11 的干预队列界面。
- **BR-09**：节点状态变更、交接包状态变更写入主审计；连接线聚合状态（派生视图）、角色状态（派生投影）、会话状态（进执行日志摘要）不单独写入主审计。
- **BR-10**：健康度档位变化进事件日志的口径沿用 I1.9 既有规则，本迭代不重复记、不改口径。
- **BR-11**：单实例并行度有上限，同时进入执行的节点不超过上限，超出者排队等待、完成一个补一个，不失败、不丢弃。
- **BR-12**：预算不足以派发下一节点时，实例转为「已挂起」并给出可见原因，不标记为失败；补充预算后可继续，不新造实例状态。
- **BR-13**：角色包 / 工作流包导出包含依赖闭包（引用的技能、派生父角色、子工作流）；依赖缺失或派生链循环时导出失败并指出问题，不产出残缺包。
- **BR-14**：导入包先校验签名有效且版本兼容才写入；签名无效或版本不兼容时拒绝导入、给出原因，不覆盖已有资产、不留半安装状态（签名校验命令名冻结为 `orch verify <包>`，见 D-13）。
- **BR-15**：`orch migrate` 升级派生角色与工作流的引用到新版，升级前列出变更项，升级后可校验；已是最新时提示且不改动，目标不存在或破坏派生链时不改写、保留原资产（命令名冻结见 D-13）。
- **BR-16**：事件日志与追踪可导出为 OpenTelemetry 格式；导出只读，不改变实例状态、不追加审计、不重写日志；不可读行跳过并提示（导出命令名冻结为 `orch export <类型>`，见 D-13）。
- **BR-17**：反模式监控给出文档瓶颈、串行化退化、确认偏误等信号，带可定位信息；信号只读，不自动改调度、不改状态、不生成升级；数据不足不误报。
- **BR-18**：性能基线为 ≥20 并发实例、≥50 活跃会话、handoff 延迟 <2s；mock 压测与真实宿主取证分级标注，mock 实测不得写成真实宿主达标；未达标给出瓶颈点，不伪造。
- **BR-19**：I1.10b 的 51 条 AC 与 I1.9 的 27 条 AC 判据及逐字文案只增不改，`orchestrator.transit()` 唯一入口、事件先落盘再广播、purity 扫描、中文唯一来源 `src/cli/labels.js`、三主链逐字输出、`USAGE_LINES` 既有 25 行用法块逐字不变（新增命令以独立用法块追加，不改写既有行，见 D-13）、零依赖、测试条数只增不减等不变量照旧。

**AC-01 · 规划验收①：篡改一条记录，链式哈希校验失败**
- 场景类型：功能 / 审计
- 风险：高（规划验收句核心）
