# Maestro 多会话编排控制台应用 · 完整需求基线 + 迭代规划

---

# 第一部分：需求基线

## 一、定位与形态

### 1.1 一句话定位

> **Maestro 是一个桌面形态的“多客户端会话控制平面应用”**：常驻系统托盘，后台运行编排守护进程，通过**统一的 ACP 适配器**在 DeepSeek Harness、Cursor、GPT/Codex、WorkBuddy 等宿主中创建并驱动多个原生会话，每个会话承载一个角色；工具只负责**角色定义、通用任务工作流编排、会话间唤醒与交接、实例状态管理、治理与审计**，Agent 的推理、工具调用和鉴权完全由客户端自己处理。

### 1.2 它不是什么

- 不是 Agent 运行时，不调用模型，不实现推理
- 不是新的 IDE，不替代 DSH / Cursor
- 不是浏览器里的一个页面，而是**有独立窗口和托盘的桌面应用**
- 不是插件或纯 CLI；CLI 和 Web 是它的辅助入口
- **不是编码专用工具**——编码只是它支持的任务类型之一

### 1.3 App 形态

**桌面应用 + 后台 daemon + 系统托盘 + 可选 Web 入口。**

```
┌─────────────────────────────────────────────────────────────┐
│  桌面应用主窗口（控制台）                                      │
│  ├─ 实例列表（健康度）                                        │
│  ├─ 实例层：角色流程图（主视图）                                │
│  ├─ 角色下钻：局部 DAG + 任务卡片                              │
│  ├─ 资产库：角色 / 技能 / 工作流                               │
│  └─ 升级队列 / 交接详情 / 证据浏览                             │
├─────────────────────────────────────────────────────────────┤
│  系统托盘：常驻，显示实例数 / 待处理升级数，通知，暂停/退出       │
├─────────────────────────────────────────────────────────────┤
│  后台 daemon：编排核心 + ACP 适配器 + 事件总线 + 持久化          │
│  监听本地 socket / WebSocket，服务主窗口、CLI、可选 Web         │
├─────────────────────────────────────────────────────────────┤
│  辅助入口：CLI（orch ...） / 可选 Web（localhost:<port>）      │
└─────────────────────────────────────────────────────────────┘
```

**桌面壳技术选型**：优先 **Tauri**，产物体积小、内存占用低、系统托盘和 WebSocket 客户端支持成熟；如果 Tauri 的 WebView 在目标平台存在兼容性问题，回退 **Electron**。**阶段一必须交付可双击启动的桌面应用**，不接受“只有 CLI + 浏览器面板”作为阶段一退出条件。

**可选 Web 入口的阶段归属**：Web 入口（`localhost:<port>`）**不在阶段一交付**。阶段一以桌面应用为唯一图形入口，Web 入口在阶段二 I2.4 作为“多宿主远程查看”的补充交付。daemon 从第一天起通过本地 socket + WebSocket 服务桌面应用，Web 入口复用同一套接口，不额外设计。

**使用体验**：双击应用图标打开主窗口；关闭窗口缩到托盘，daemon 继续监听和投递唤醒；从托盘“退出”才真正停止（有运行中实例时提示确认）。深入某个角色会话时，一键跳转到 DSH / Cursor / GPT / WorkBuddy 对应窗口。

### 1.4 与宿主的关系：并列，不嵌套

```
DSH / Cursor / GPT / WorkBuddy（执行层）
Agent 推理 / 工具 / 鉴权
        │  统一 ACP 适配器
        ▼
Maestro（控制层）
角色 / 工作流 / 唤醒 / 实例 / 治理
```

### 1.5 支持的任务类型

工具不预设“编码”为默认范式。角色和产物类型覆盖**研究分析、内容创作、编码工程、业务运营、通用协调**五组。

| 任务类型 | 典型角色 | 产物形态 |
|---|---|---|
| 研究分析 | 研究员、事实核查员、数据分析师 | 研究报告、引用清单、数据结论 |
| 内容创作 | 撰写者、编辑、翻译、审核者 | 文稿、修订稿、多语言版本 |
| 编码工程 | 架构师、开发、代码审查、测试、发布 | 代码变更、测试证据、发布包 |
| 业务运营 | 需求澄清者、流程设计者、合规审查者 | PRD、流程定义、合规意见 |
| 通用协调 | 编排者、规划者、汇总者、裁决者 | 计划、摘要、裁决记录 |

产物隔离由角色声明的 `artifact_type` 决定：`code` 走 git worktree，`document` 走版本化文件区，`dataset` 走数据快照，`report` 走只追加产物区。**不对非编码任务强制 git 隔离。**

## 二、核心架构决策：ACP 作为通用会话管理协议

### 2.1 决策

daemon 的适配器层收敛为**一个通用 ACP 客户端**，不再为每个宿主编写独立适配器。所有宿主通过 ACP 暴露会话创建、驱动和唤醒能力；daemon 只实现一份 ACP 接口。

### 2.2 理由

ACP 是当前多宿主生态的事实收敛点：

- **DSH** 官方 ACP 服务器支持 `session/new`、`session/resume`、`session/list`、`session/close`，单连接多会话多路复用已实现，每个会话独立 `cwd`，committed answers、prompt completion、cancellation、permission requests 严格隔离。
- **WorkBuddy** 通过 ACP HTTP+SSE 暴露 `session/new`、`session/prompt`、`session/cancel`，`session/load` 用于追加消息。
- **GPT/Codex** 通过 `codex-acp` 提供 stdio ACP 服务，将 ACP 会话映射到 Codex 线程。
- **Cursor CLI** 原生支持 `agent acp`。
- **统一抽象已有实践**：`@yitom/acp-client` 提供“8 大运行时开箱即用”的 ACP 客户端抽象，含 `resume → load → new` 的会话恢复状态机。

### 2.3 daemon 与 ACP 的边界

daemon 的编排逻辑对 ACP 完全无感知，边界收敛为五个 ACP 原语：`initialize`、`session/new`、`session/prompt`、`session/update`、`session/cancel`。

宿主方言（恢复语义 `session/resume` 不回放 vs `session/load` 追加、transport stdio vs HTTP/SSE、证据钩子有无）**收敛在适配器层**，不进入核心。daemon 中不得出现 `if host == 'xxx'` 的分支。

### 2.4 已验证的技术前提

| 前提 | 结论 |
|---|---|
| DSH ACP 多路复用 | ACP v1 明确允许单连接多会话，DSH 已实现 `Map<SessionId, SessionRecord>` 隔离 |
| DSH ACP 持久化与恢复 | 官方服务器广告 `session/resume`、`session/list`、`session/close`；`dsh-acp-server` 支持 `--session <id>` |
| WorkBuddy ACP | 通过 sidecar 控制管道发现动态 ACP 端口和临时密码 |
| GPT/Codex ACP | `codex-acp` 是 stdio ACP agent server |
| Cursor ACP | Cursor CLI 原生支持 `agent acp` |
| 统一 ACP 客户端抽象 | `@yitom/acp-client` 提供 8 运行时开箱即用适配 |
| 桌面壳可行性 | Tauri 优先，Electron 回退；阶段零验证系统托盘和 WebSocket 客户端支持 |

### 2.5 剩余待验证项（阶段零回答）

| 项 | 需回答的问题 |
|---|---|
| ACP 适配器跨 transport | 同一适配器能否用 stdio 和 HTTP/SSE 两种 transport 驱动，核心无需修改 |
| ACP 会话恢复方言统一 | 各宿主 `session/resume` / `session/load` 差异能否在适配器层统一为 `resumeOrCreate` |
| ACP 并发会话隔离强度 | 3–5 个 ACP 会话的 cwd、工具调用、权限请求是否严格隔离 |
| 非编码任务证据提取 | `session/update` 事件流是否包含足够的“产物就绪 + 审核确认”语义 |
| 会话状态映射 | `session/request_permission` 能否可靠映射为 `waiting_input` |
| 交接包状态推导 | 能否从 ACP 事件可靠推导 `accepted` / `consumed` |
| Cursor ACP 并发稳定性 | 3–5 个并发 Cursor ACP 会话的失败率和延迟 |
| Tauri 桌面壳可行性 | 系统托盘、WebSocket 客户端、多窗口支持是否满足需求 |

## 三、状态模型（四层）

Maestro 的状态设计分为**四个独立层次**，各有自己的枚举和归属，不能混用。

### 3.1 节点状态（9 个，看板 7 列）

节点是**编排单位**，状态由核心裁决。适配器上报的“会话完成”只是输入。

```
blocked → ready → assigned → running → review → done
                    │           │        │
                    │           │        ├→ failed → running（回流）
                    │           │        │         └→ escalated
                    │           │        └→ escalated
                    └→ cancelled（终态，折叠显示）
```

| 状态 | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| `blocked` | 依赖未满足 | 节点创建时依赖未全部 done | 所有依赖 done |
| `ready` | 可调度 | 依赖满足 | 核心分配会话 |
| `assigned` | 已绑定会话 | 核心选定/创建会话 | 会话开始执行 |
| `running` | 执行中 | 会话开始执行 | 产出提交 / 超时 / 失败 |
| `review` | 待校验 | 会话产出提交 | 证据通过 → done；失败 → failed；等待下游 → 保持 |
| `done` | 验收通过 | 证据校验通过 + 下游接受 | 终态 |
| `failed` | 执行失败 | 会话崩溃 / 证据缺失 / 契约不满足 | 回流到 running 或升级 |
| `escalated` | 升级人工 | 轮次超限 / 依赖死锁 / 连续失败 | 人工裁决后 → done / failed / 重新分配 |
| `cancelled` | 被取消 | 人工终止 / 上游取消 | 终态 |

**`review` 的两个子原因**（不新增看板列，卡片标签区分）：
- `review_reason: evidence` —— 等待核心校验证据
- `review_reason: downstream` —— 证据已通过，等待下游交接包 `accepted`

**超时归入 `failed` 的子类型**（`failed_reason: timeout`），不新增独立状态。理由：超时和失败在编排语义上都是“本次执行未成功”，区别只在重试策略。

**看板列是 7 列**：`blocked / ready / running / review / done / failed / escalated`。`assigned` 归入 `running` 列的“已分配未开始”子状态；`cancelled` 归入 `done` 列的折叠区。

**回流不新建卡片**：同一节点卡片保留，轮次计数 +1，历史轮次折叠在详情中。

### 3.2 会话状态（6 个，卡片指示器）

会话是**执行单位**，状态由适配器从 ACP 事件归一化后上报核心。会话状态只更新节点卡片上的指示器，**不改变节点在看板中的列**。

| 会话状态 | 含义 | 卡片表现 |
|---|---|---|
| `idle` | 会话已创建未接到任务 | 灰色圆点 |
| `thinking` | 推理/执行中 | 蓝色脉冲，显示“执行中 · 已运行 3m” |
| `tool_running` | 调用工具中 | 蓝色脉冲 + 工具图标 |
| `waiting_input` | 等待外部输入（审批/澄清） | 黄色圆点，显示“等待审批：git_push” |
| `waiting_dependency` | 已产出，等待下游或证据校验 | 黄色圆点，显示“等待校验” |
| `escalated` | 已升级，等待人工 | 红色圆点 |

**会话状态与 ACP 事件映射**（适配器层职责）：

| ACP 事件 | 归一化会话状态 |
|---|---|
| 会话创建后、未收到 prompt | `idle` |
| `session/update` 推理/文本增量 | `thinking` |
| `session/update` 工具调用开始 | `tool_running` |
| `session/request_permission` | `waiting_input` |
| 会话产出提交 | `waiting_dependency` |
| 核心生成 escalation | `escalated` |
| `session/cancel` 或会话关闭 | `idle` 或从视图移除 |

### 3.3 角色状态（6 个，角色流程图节点）

角色是**配置单位**，运行时以**角色实例**（Role Instance）存在。角色注册表是静态配置，角色实例是运行时状态，二者在面板层合并展示。

| 角色状态 | 含义 | 流程图表现 |
|---|---|---|
| `inactive` | 工作流定义了该角色，但本实例中尚未绑定任何节点 | 灰色显示，不参与路由 |
| `available` | 可用，无占用 | 绿色圆点 |
| `busy` | 正在服务某个/某些节点 | 蓝色圆点，显示“服务 T-003, T-004” |
| `cooldown` | 刚完成一个节点，会话可复用 | 灰色圆点 |
| `unavailable` | 会话崩溃或宿主不可达 | 红色圆点 |
| `retired` | 角色实例已关闭 | 不显示 |

**角色实例数据模型**：

```yaml
role_instance:
  instance_id: INST-001
  role_id: developer
  status: inactive | available | busy | cooldown | unavailable
  active_sessions: [sess-003, sess-004]
  serving_nodes: [T-003, T-004]
  host_icons: [dsh, cursor]        # 多宿主时并列
  last_action_summary: "T-003 · 轮次 1/2 · 已运行 8m"
  max_concurrent_sessions: 2
```

**同一角色可并行服务多个节点**：`max_concurrent_sessions` 字段默认 1，可配置到 3–5；超过 1 个会话时角色节点显示堆叠指示器。

### 3.4 交接包状态（7 个，连接线数据源）

交接包是**角色间传递的结构化有界上下文**，状态变化驱动连接线聚合状态。

```
created → delivered → accepted → consumed
              │           │
              │           └→ rejected
              └→ pending → expired
```

| 状态 | 含义 | 触发 |
|---|---|---|
| `created` | 交接包已构造，未投递 | 写入持久化信箱 |
| `delivered` | 已投递到目标会话 | 等待目标接受 |
| `pending` | 宿主不在线，投递未确认 | 重试投递，超时后 `expired` |
| `accepted` | 目标会话已接受 | 目标节点从 `assigned` 进入 `running` |
| `consumed` | 目标节点产出提交 | 交接包被消费完毕 |
| `rejected` | 目标会话拒绝 | 触发回流或升级 |
| `expired` | 超过 TTL 未接受 | 触发升级人工 |

**关键**：`accepted` 只表示目标接受了交接包，`consumed` 才表示目标节点已完成。连接线“已完成”条件是所有交接包均为 `consumed`。

### 3.5 状态变更的完整时序（一次回流）

```
t0  测试节点 T-005 会话产出提交
    → 会话 tester: thinking → waiting_dependency
    → 节点 T-005: running → review (review_reason: evidence)
    → 核心校验证据：缺陷证据完整
    → 节点 T-005: review (evidence) → review (downstream)

t1  核心构造交接包 HO-006（缺陷引用 + 复测命令）
    → HO-006: created → delivered
    → 目标会话 dev_1: cooldown → thinking

t2  dev_1 接受交接包
    → HO-006: delivered → accepted
    → 节点 T-003: done → running（轮次 1/2）
    → 节点 T-005: review → failed（等待复测）

t3  dev_1 修复完成
    → 会话 dev_1: thinking → waiting_dependency
    → 节点 T-003: running → review (evidence)
    → 核心校验通过 → review (downstream)
    → 构造 HO-007（复测指令）
    → HO-007: created → delivered → accepted
    → 节点 T-005: failed → running（复测）

t4  测试复测通过
    → 节点 T-005: running → review → done
    → 节点 T-003: review → done
    → HO-006 / HO-007: accepted → consumed
    → 实例健康度更新
```

### 3.6 崩溃恢复时的状态规则

| 恢复时状态 | 恢复后状态 | 条件 |
|---|---|---|
| `running` + 会话可恢复（`session/resume` 成功） | 保持 `running` | 会话继续执行 |
| `running` + 会话不可恢复 | `assigned` | 重新分配会话，从当前轮次重试 |
| `assigned` | `assigned` | 重新调度 |
| `review` | `review` | 等待核心重新校验 |
| `blocked` / `ready` | 原状态 | 依赖关系不变 |
| 角色实例 `busy` + 会话不可恢复 | `available` | 重新调度其服务节点 |
| 交接包 `delivered` 未 `accepted` | `pending` | 重投 |

**恢复后不重放已完成节点**，轮次计数从检查点恢复，不重置。

## 四、核心能力域

### 能力域 1：角色与技能资产

角色是**宿主无关的可复用资产**，覆盖编码与非编码场景。

- **内置角色库**：约 15 个角色，分通用协调、研究分析、内容创作、编码工程、业务运营五组
- **自定义角色**：从零创建、从内置派生、从导入包安装
- **技能组合**：角色引用可复用的“技能包”（提示词 + 工作方法 + 可选验证命令）
- **角色契约**：声明输入输出 schema、工具集、`artifact_type`、副作用等级、唤醒白名单、`max_concurrent_sessions`
- **产物类型驱动隔离**：`code` → worktree；`document` → 版本化文件区；`dataset` → 快照；`report` → 只追加区
- **角色校验**：schema 完整性、技能引用有效、契约连通、权限闭环、派生链无循环

**关键分离**：
- **角色注册表**（静态）：`roles/*.yaml`，只存角色定义
- **角色实例**（运行时）：由会话注册表/实例管理器持有，记录状态、活跃会话、服务节点
- 二者在面板层合并展示；角色流程图数据源是角色实例，不是角色注册表

**CLI 命令集**：`orch role list / show / create / edit / validate / export / import / diff`；`orch skill list / show / create / validate / export / import`

**边界**：角色声明的工具集和路径约束是**声明式**的，由适配器翻译给宿主；实际执行边界由宿主原生机制负责。

---

### 能力域 2：通用任务工作流编排

工作流是**宿主无关的声明式资产**，引擎不假设产物是代码。

- **声明式工作流**：YAML 定义角色节点、依赖边、条件路由、回流循环、人工节点、升级路径
- **节点模型 `node_type`**：`role` / `human` / `escalate` / `subworkflow`
- **通用原语**：顺序、并行 fan-out/fan-in、条件分支、回流循环、轮次上限、超时、重试、人工节点、子工作流、升级、终止
- **双内置模板**：编码闭环（开发→测试→缺陷回流→升级）与通用任务闭环（研究→撰写→审核→修订回流→交付），共享同一引擎
- **交接包**：只携带结构化有界上下文（任务、产物引用、证据引用、约束、指令），不携带完整对话历史；必须通过目标角色输入 schema 校验
- **字段映射**：支持上下游字段名差异的显式映射
- **产物合并/汇总顺序**：并行节点按声明顺序合并；代码走 git 合并，文档走版本合并，数据走人工裁决
- **工作流校验**：可达性、回流边必须有轮次上限、并行 scope 不重叠、权限匹配、变量引用有效、节点状态转换合法性、角色对唤醒权限
- **版本锁定**：实例启动时锁定资产版本，运行中资产更新不影响运行实例
- **子工作流折叠**：子工作流在流程图中显示为折叠组节点，点击下钻

**CLI 命令集**：`orch workflow list / show / create / validate / diff / run / dry-run / pause / resume / abort`

---

### 能力域 3：多会话驱动（统一 ACP 适配器）

**一份 ACP 适配器 + 每个宿主一份薄 transport 配置**，驱动所有支持 ACP 的宿主。

- **通用 ACP 适配器**：实现 `initialize`、`session/new`、`session/prompt`、`subscribeEvents`、`session/cancel`、`closeSession`
- **transport 方言**：stdio（DSH、Codex）、HTTP/SSE（WorkBuddy）、按宿主配置选择；transport 差异不进入 daemon
- **会话恢复方言**：适配器统一处理 `session/resume`（不回放）、`session/load`（回放/追加）、`resumeOrCreate` 回退链
- **会话状态归一化**：适配器把 ACP 原生事件映射为 6 个会话状态，供角色实例摘要和卡片指示器使用
- **会话复用策略**：角色可配置“任务内复用会话”或“每任务新会话”
- **跨宿主混跑**：同一实例中不同角色可运行在不同宿主上
- **配置翻译**：创建会话时把角色配置翻译成 ACP 会话参数
- **产物隔离**：按 `artifact_type` 分配隔离空间

**边界**：适配器只做**ACP 语义翻译和生命周期管理**，不实现推理，不拦截宿主内部工具调用。daemon 不出现任何 `if host == 'xxx'` 的分支。

---

### 能力域 4：会话间唤醒与交接

角色完成后主动唤醒下一个角色，审核驳回能唤醒上游修订，形成跨任务类型的闭环。

- **事件订阅**：适配器订阅 ACP `session/update` 完成事件并上报核心
- **集中路由决策**：核心根据工作流路由表判断“唤醒谁、带什么上下文、是否升级”
- **主动唤醒投递**：适配器调用 `session/prompt` 向空闲会话发起新 turn
- **回流闭环**：支持 A→B→A 往复；核心维护轮次计数，超限时升级人工
- **交接可靠性**：唤醒消息先落盘再投递；失败重试；宿主不在线时消息保持 `pending`
- **证据门禁**：交接包必须附带**未过期的、与声明产物一致的证据引用**；缺失或过期时核心拒绝投递并触发升级
- **交接包状态机**：7 个状态，见 3.4 节

**连接线数据模型**：

```yaml
connection:
  instance_id: INST-001
  from_role: tester
  to_role: developer
  direction: forward | backflow
  aggregate_status: rejected | expired | pending | delivered | accepted | consumed | not_started
  handoff_ids: [HO-006]
  parallel_count: 1
  latest_round: 1
  latest_activity: "2026-11-04T10:30:00Z"
```

**聚合规则**：
- 正向与回流**分开聚合**（正向一条线，回流一条弧线）
- 同向多并行**合并为一条线**，线加粗 + 标签“N 并行交接”
- 优先级：`rejected > expired > pending > delivered > accepted > consumed > not_started`
- 多轮回流：弧线显示**最近一轮**，历史轮次在点击详情中展开

**聚合状态与视觉编码**：

| 聚合状态 | 条件 | 视觉 |
|---|---|---|
| `rejected` | 任一交接包 `rejected` | 红色实线 + 回流箭头 |
| `expired` | 任一交接包 `expired` | 橙色虚线 + 感叹号 |
| `pending` | 任一交接包 `pending` | 黄色虚线 |
| `delivered` | 任一交接包 `delivered` 未 `accepted` | 蓝色实线 + 流动动画 |
| `accepted` | 任一交接包 `accepted` 未 `consumed` | 蓝色实线 + “处理中”标签 |
| `consumed` | 全部交接包 `consumed` | 绿色实线 |
| `not_started` | 角色对已定义但无交接包 | 灰色虚线（默认隐藏，开关显示） |

**标签策略**：默认只显示**异常标签**（`rejected` / `expired` / `pending`）；正常状态悬停时显示。

**边界**：唤醒是**核心集中决策**；适配器只负责 ACP 投递。证据的真实性执行下沉到宿主侧验证机制或独立审核角色，核心校验引用的存在性和有效期。

### 能力域 5：实例管理（视图层次 + 状态 + 日志 + 公共资料）

实例是**运行时管理的基本单位**，状态变更的裁决权在核心。

#### 5.1 视图层次（四层）

```
全局层（实例列表）
  └─ 实例健康度、进度、待处理数；不展示角色和节点

实例层（角色流程图，主视图）
  ├─ 角色实例节点：状态色 + 活跃会话数 + 服务节点 + 宿主图标 + 异常角标
  ├─ 特殊节点：human（灰色盾牌）、escalate（红色感叹号）、subworkflow（折叠组节点）
  ├─ 连接线：正向线 + 回流弧线，聚合状态编码
  └─ 可选切换：全实例节点看板（7 列）

角色下钻层（点击角色节点或特殊节点进入）
  ├─ 顶部：角色状态栏
  ├─ 左侧：局部 DAG（该角色参与的节点 + 1 跳上下游，节点颜色 = 节点状态）
  └─ 右侧：任务卡片列表（按节点状态排序，三层信息 + 会话状态指示器）

节点详情层（点击任务卡片进入）
  └─ 会话状态时间线、ACP 事件摘要、证据引用、交接包历史、跳转宿主会话
```

#### 5.2 角色流程图

**角色节点视觉编码**：

| 元素 | 规则 |
|---|---|
| 状态色 | 🟢 available / 🔵 busy / ⚪ cooldown / 🔴 unavailable / 灰色 inactive |
| 宿主图标 | 右下角小图标标注 DSH / Cursor / GPT / WorkBuddy；多宿主并列 |
| 活跃会话数 | `busy` 时显示“N 个活跃会话”；N > 1 时角标堆叠 |
| 服务节点 | 当前绑定节点 ID 列表；超过 2 个折叠 |
| 异常角标 | `escalated` 节点挂在该角色上时，右上角红色感叹号 |
| 尺寸 | 默认中等卡片；异常角色用**角标 + 红色脉冲**，不改变尺寸（避免布局重算） |

**特殊节点**：

| 节点类型 | 视觉 | 状态 | 交互 |
|---|---|---|---|
| `human` | 灰色盾牌 | 复用节点状态 | 点击跳转人工任务详情 |
| `escalate` | 红色感叹号 | 复用节点状态 | 点击跳转升级队列 |
| `subworkflow` | 折叠组节点，标注“子工作流：xxx · N 角色” | 派生状态（内部有 escalated 则红色） | 点击下钻子工作流角色流程图 |

**布局算法**：
- 按工作流 DAG 的拓扑层次排列角色，从左到右或从上到下
- 回流边不改变层次，只画反向弧线
- 同层并行角色垂直排列
- 异常角色和连接线优先占据视觉焦点，但不破坏拓扑层次
- 支持手动拖拽调整位置，偏好按实例保存
- 角色数 > 12 时按角色分组折叠为组节点
- 子工作流显示为折叠组节点

**交互**：
- 点击角色节点 → 进入角色下钻视图
- 点击连接线 → 展开该角色对的交接包列表，每个可展开详情
- 悬停角色节点 → 高亮其所有上下游连接线，其他元素降透明度
- 悬停连接线 → 高亮两端角色
- 双击角色节点 → 聚焦模式，只显示 2 跳以内链路
- 点击红色/橙色连接线或 escalated 角标 → 跳转升级处理面板

#### 5.3 角色下钻视图

**左侧局部 DAG**：
- 只显示该角色参与的节点及其**直接上下游（1 跳）**
- 节点颜色 = 节点状态
- 该角色节点加粗边框
- 依赖类型：实线 = 正向依赖，虚线 = 回流
- 点击节点 → 右侧卡片列表滚动到对应卡片

**右侧任务卡片列表**：
- 按节点状态排序：`escalated` > `failed` > `running` > `review` > `assigned` > `ready` > `blocked` > `done`
- 卡片三层信息：标题行（节点 ID、标题、轮次）+ 执行行（角色、会话状态、耗时、当前工具调用）+ 依赖/产出/证据行
- 会话状态指示器
- 点击卡片 → 展开详情（会话状态时间线、ACP 事件摘要、证据引用、交接包历史）

**“查看全部节点”切换**：切换到全实例节点看板（7 列，原设计）。

**`subworkflow` 下钻**：点击折叠组节点进入子工作流的角色流程图，复用同一套布局算法。

#### 5.4 共享工作区与产物存储

- **共享工作区**：实例级隔离，三层可见域——`shared/`（全局可读，核心/人工可写）、`stage/`（阶段参与者可读，上游可写）、角色私有上下文（不进入共享区）；`status.md` 作为人类可读交接棒
- **产物存储**：按 `artifact_type` 分区——`artifacts/code/`、`artifacts/docs/`、`artifacts/data/`、`artifacts/reports/`

#### 5.5 三层日志

- **事件日志**：审计，append-only、链式哈希
- **执行日志摘要**：适配器在会话完成时，将执行日志的摘要（命令、退出码、关键输出行数、日志 artifact 引用）附加到事件日志中；完整日志留在宿主，核心只存摘要和引用
- **追踪 span**：每个实例生成 `trace_id`；每个节点的 span 记录 `start_time / end_time / status / handoff_ids`；回流链在时间线上可展开。追踪数据写入 `instances/<id>/state/traces.jsonl`，可导出为 OpenTelemetry 格式（阶段一 I1.12 实现导出）

#### 5.6 人工干预队列与通知

- **人工干预队列**：升级和审批统一为可查询队列，面板和 CLI 均可处理
- **通知机制**：至少一种触达方式（托盘通知 / 面板轮询 / IM）

#### 5.7 数据接口与实时推送

**数据接口**：
```
GET /instances/:id/graph          # 全量快照
WS  /instances/:id/graph/stream   # 增量推送
```

**推送事件**：`role_instance.updated` / `connection.updated` / `special_node.updated` / `graph.snapshot`（重连时全量）。

**节流规则**：角色实例状态变化实时推送；连接线聚合状态变化合并 1 秒内多次变更；会话状态变化只推送卡片指示器，不触发流程图重绘。

**CLI 输出**：
```
orch instance graph INST-001 --format json   # 结构化，供回归测试对比
orch instance graph INST-001 --format text   # ASCII 摘要
```

#### 5.8 健康度规则

| 健康度 | 条件 |
|---|---|
| 🔴 需关注 | 有待处理升级 / 节点超时 / 会话崩溃 / 有角色 `unavailable` / 有连接线 `rejected` 或 `expired` |
| 🟡 慢 | 有节点运行时长超过 P90 / 有连接线 `pending` 超过 TTL 50% |
| 🟢 正常 | 无异常 |
| ⚪ 已结束 | 实例完成或终止 |

健康度由**核心计算**并写入实例元数据，影响路由决策，变化进事件日志。

#### 5.9 边界

- Agent 的完成声明只是输入，节点状态由核心依据契约和证据链裁决
- 执行日志完整内容留在宿主，核心只索引摘要和引用
- 角色流程图**只展示角色级和交接级信息**，不展示节点级和会话级细节（防止主视图信息过载）

### 能力域 6：治理与审计

防“假交付”、防“越权唤醒”、防“无法追溯”。

- **三层权限模型**：角色声明层（唤醒白名单、审批要求）+ 工作流约束层（节点间产物 scope 隔离）+ 宿主执行层（宿主原生权限）
- **路由层拦截**：核心在唤醒决策时检查角色权限白名单，不合规唤醒直接拒绝并留痕
- **证据引用校验**：核心校验证据引用存在、未过期、与声明产物一致；真实性由宿主侧验证插件或独立审核角色执行
- **审计事件**：所有编排动作写入事件日志，链式哈希防篡改
- **审计粒度**：
  - 节点状态变更：审计
  - 交接包状态变更：审计（连接线聚合状态是派生视图，不单独审计）
  - 角色状态变更：派生不单独审计
  - 健康度变化：进事件日志
  - 会话状态变更：进执行日志摘要，不进主审计
- **人工终审**：高风险节点（发布、数据变更、合规意见、副作用 high）下游必须有 human 节点或升级路径
- **升级机制**：轮次超限、依赖死锁、契约校验连续失败、证据缺失/过期时自动生成升级请求
- **预算与配额**：单实例并行度上限、预算耗尽时暂停而非失败
- **会话失败区分**：区分会话进程崩溃（重建/升级）与会话运行慢（节点超时）
- **生态能力**：角色包/工作流包导出（含依赖闭包）、导入包签名校验、版本兼容检查、`orch migrate` 版本迁移、可观测性导出、反模式监控

**边界**：核心能在路由层拒绝不合规唤醒，但**不能在宿主内核层拦截会话内的单次文件写入**——后者由宿主原生机制负责。

## 五、运行时模型与数据布局

### 5.1 运行时闭环

```
工作流实例启动
  → 解析节点，计算就绪节点
  → 对每个就绪节点：查角色配置 → 通过 ACP 适配器创建/附着会话
    → 按 artifact_type 分配隔离空间 → 构造交接包 → session/prompt
  → 订阅 ACP session/update 事件
  → 收到完成事件：
      1. 校验输出是否符合角色契约
      2. 校验证据引用存在/未过期/与声明产物一致
      3. 更新节点状态
      4. 更新交接包状态（accepted / consumed）
      5. 评估路由边条件
      6. 命中回流 → 轮次+1 → 检查上限
      7. 命中升级 → 生成 escalation → 人工节点
      8. 命中正常边 → 构造交接包 → session/prompt 唤醒目标节点
      9. 命中 end → 实例结束
  → 所有事件写入事件日志
  → 更新角色实例状态、连接线聚合状态、健康度
  → 通过 WebSocket/SSE 推送到面板
```

### 5.2 数据布局

```
.orch/
├── roles/  skills/  workflows/        # 宿主无关的定义资产
├── hosts/                             # 宿主 transport 配置（stdio / HTTP+SSE）
├── instances/<id>/
│   ├── workspace/
│   │   ├── shared/  stage/  status.md
│   │   └── artifacts/{code,docs,data,reports}/
│   ├── state/                         # 节点状态、轮次、检查点、角色实例、连接线聚合、traces.jsonl
│   └── graph.json                     # 角色流程图数据快照
├── inbox/                             # 持久化信箱
└── events.jsonl                       # 事件日志（链式哈希）
```

## 六、边界声明

1. **ACP 是通用会话管理协议，不是唯一协议**：如果某个候选宿主不支持 ACP，接入它需要额外的适配器或 transport 包装；但 ACP 覆盖了当前已知宿主（DSH、Cursor、GPT/Codex、WorkBuddy）。
2. **daemon 编排逻辑对 ACP 无感知**：只依赖五个 ACP 原语；宿主方言收敛在适配器。
3. **非编码场景的证据真实性依赖独立审核角色**：核心不替代事实核查/编辑审核/合规审查，只确保审核确认被记录为可追溯证据。
4. **不对非编码任务强制 git 隔离**：产物隔离由 `artifact_type` 决定。
5. **核心只做组织、路由和治理**：Agent 推理、工具调用、鉴权、会话内单次操作的实际约束，全部由宿主原生机制负责。
6. **宿主扩展是验证手段，不是功能堆叠**：每次扩展运行同一套回归工作流，差异归属到适配器或核心抽象并修正。
7. **角色流程图只回答“团队在怎么协作”** ：节点级和会话级细节下钻到角色视图；这是防止信息混乱的核心规则。
8. **角色注册表与角色实例分离**：注册表是静态配置，实例是运行时状态；面板层合并展示。
9. **连接线聚合状态是派生视图**：不单独审计，可随时从交接包状态重建。
10. **阶段一以桌面应用为唯一图形入口**：Web 入口在阶段二 I2.4 交付；阶段一退出条件要求“桌面应用可独立完成日常操作，不依赖 CLI 或浏览器”。

### 阶段零：技术验证（1 个迭代）

**阶段三退出条件**：三个宿主上同一套 ACP 适配器行为一致；核心抽象经过三次扩展压测后稳定；角色流程图在三宿主上数据一致；宿主接入标准流程可复用。

## 关键判断点

| 判断点 | 位置 | 意义 |
|---|---|---|
| 统一 ACP 适配器能否跨 transport 驱动 | I0.1 | 核心抽象是否真正宿主无关 |
| 会话状态映射和交接包状态推导是否可靠 | I0.1 | 状态模型的数据基础是否成立 |
| Tauri 桌面壳可行性 | I0.1 | 桌面应用技术选型是否成立 |
| DSH 单宿主完整流程是否可用 | 阶段一退出 | 产品链路是否成立，不依赖多宿主 |
| 角色流程图能否完整表达含人工/子工作流的拓扑 | I1.10a 验收 | 主视图的拓扑完整性 |
| 角色下钻与联动是否可用 | I1.10b 验收 | 核心交互体验是否成立 |
| 桌面应用能否独立完成日常操作 | I1.11 / I1.12 验收 | 阶段一退出条件的核心判据 |
| 同一适配器在第二宿主是否行为一致 | I2.2 验收 | ACP 方言处理是否收敛在适配器 |
| 跨宿主混跑是否可用 | I2.3 验收 | 多宿主协同是否成立 |
| 第三宿主是否暴露新的隐藏假设 | I3.2 验收 | 抽象是否经过足够压测 |
| 三宿主角色图数据是否一致 | I3.2 验收 | 状态模型是否真正宿主无关 |
| 三宿主治理是否一致 | I3.3 验收 | 治理机制是否可移植 |

---

**一句话总结**：Maestro 以 **ACP 作为通用会话管理协议**，daemon 只实现一份适配器，每个宿主只添加极薄的 transport 配置和方言声明；状态模型分**节点（9 个）/ 会话（6 个）/ 角色（6 个）/ 交接包（7 个）** 四层；实例层主视图是**角色流程图**（含 human/escalate/subworkflow 特殊节点，连接线聚合交接状态），角色下钻是**局部 DAG + 任务卡片**，节点看板降为可选切换；桌面应用从 **I1.10a 开始正式构建**，I1.10b 完成下钻联动，I1.11 补齐通知/人工干预队列/资产库/证据浏览，I1.12 完成治理加固与生态能力；先在 DSH 上把完整产品链路做透，再用 Cursor 验证宿主无关性，最后用 WorkBuddy 或 GPT/Codex 压测 transport 抽象。阶段一退出条件是“桌面应用可独立完成日常操作，不依赖 CLI 或浏览器”。
