# Maestro 多 Agent 研发组织 · 需求基线 + 迭代规划（v2 形态校正版）

> **文档性质**：这是对 `docs/index.md` v1 基线的**全面重写**，不是补丁。
> **生效日期**：2026-11-23。**v1 原文备份**：`docs/index.v1-baseline-20261123.md`（1062 行，逐字保留，供追溯与差集对照）。
> **校正依据**：① 用户对 `v0.0.1-beta.3` 的实测反馈——"目前的交互形式其实是用不起来的"；② 用户提供的《多 Agent 产品研发团队完整工作流程设计》——**它只是"能配出来的一种使用场景"，不是产品的唯一形态定义**；③ 已交付代码的真实能力盘点。
> **一句话结论**：v1 把 Maestro 写成了"**多客户端会话控制平面**"，把引擎做齐了，却把用户真正要用的那一步——"打开应用 → 扫描本机 Agent CLI → 基于 CLI 建角色 → 搭 Agent Team → 建工作流"——拆散在 I0.1 / I1.5 / I1.6 / I1.10a / I2.1，且排在最后。**v2 把这条链路扶正为产品第一入口与唯一核心，引擎降级为底座。**
> **形态口径（用户 2026-11-23 明确）**：12 阶段研发组织是**产品要能配出来的一个目标场景 / 内置模板**，用于验证能力闭环；产品本身是通用的"CLI 扫描 → 建角色员工 → 搭 Team → 建任意工作流"平台，不限于研发，也不限于这一套 12 阶段。

# 第一部分：需求基线（v2）

## 一、定位与形态

### 1.1 一句话定位

> **Maestro 是一个桌面形态的"多 Agent 团队搭建与运行平台"**：应用启动后**主动扫描本机已安装的所有 Agent 客户端 CLI 并罗列**，用户基于这些 CLI **创建角色与员工 Agent**、把多个员工编排成 **Agent Team**、创建或套用**任意工作流（12 阶段研发组织是官方内置模板之一，不是唯一形态）**；Maestro 的控制平面负责组织/角色/任务/交接/评审/门禁/产物/治理，Agent 的推理、工具调用和鉴权完全由底层 CLI 自己处理。

**与 v1 的差别**：v1 的宾语是"会话"，v2 的宾语是"组织 + 团队 + 工作流"。CLI 从"被配置的宿主"变成"被发现的员工载体"。

### 1.2 它不是什么

- 不是 Agent 运行时：不调用模型、不实现推理、不替代 CLI 的智能
- 不是新的 IDE，也不是 ChatGPT 网页版的自动化工具（交互只发生在 CLI 客户端与控制平面之间）
- **不是"一个角色 = 一个 Agent"的编排器**：一个角色可有多名 Agent，一个阶段不应只由一个 Agent 独立完成
- 不是纯 CLI / 纯 Web 页面：阶段一必须交付可双击启动、能独立完成日常操作的桌面应用
- 不是编码专用工具：产品、架构、前端、后端、测试、DevOps、安全都是组织内的正式角色

### 1.3 核心用户旅程（v2 第一入口，必须逐字落地）

```
启动应用
 → 【自动扫描】探测本机所有 Agent CLI（PATH / 应用目录 / 包管理器 / 注册表）
 → 【罗列】展示 CLI 清单：名称、路径、版本、可用能力、连接状态、并发上限
 → 【建角色】用户选一个 CLI，创建角色（职责/输入输出/权限/微信技能）；
              一个角色下可挂多名员工 Agent，各自绑定同一或不同 CLI
 → 【搭团队】把角色拖进部门（产品部/研发管理部/前端部/后端部/测试部/平台安全部），
              设定负责人、并发数、协作规则
 → 【建工作流】选官方内置模板（含 12 阶段研发组织）或自定义 DAG；设门禁、运行模式（全自动/半自动/手动）、
              阶段内并行策略
 → 【启动实例】控制平面按依赖调度任务 → CLI 会话执行 → 交接/评审/门禁
 → 【监控与干预】组织视图 → 团队视图 → 角色视图 → 任务/会话详情；
              处理升级、审批、缺陷回流
 → 【交付与复盘】产物归档、质量复盘、技术债进入下一迭代
```

**验收红线**：任何无法从"启动应用"走到"一个 Agent Team 跑完一次迭代"的构建，都不算产品形态成立。beta.1~3 停在"选工作流 → 填任务 → 看实例"，**不算走通**。

### 1.4 App 形态

**桌面应用 + 后台 daemon + 系统托盘**；Web 入口阶段二再交付，不进阶段 A。

主视图相对 v1 的变化（新增项标 ★）：

### 1.5 与宿主 CLI 的关系：并列，不嵌套

```
Codex / Claude Code / Cursor / Gemini CLI / OpenCode / DSH / WorkBuddy（执行层）
  Agent 推理 / 工具 / 鉴权 / 会话内部权限
        │  ACP 适配器 + CLI 能力探测
        ▼
Maestro（控制层，Control Plane）
  组织 / 部门 / 角色 / 员工 / 任务 / 交接 / 评审 / 门禁 / 产物 / 治理
```
CLI 是员工的**载体**，不是 Maestro 的子模块；Maestro 不控制网页版客户端。

### 1.6 任务类型与产物

组织覆盖研发全生命周期：产品（需求/竞品/验收）、架构、前端、后端、测试、DevOps、安全、数据库。产物类型沿用 v1 的 `artifact_type` 分区（`code` → worktree，`document` → 版本化文件区，`dataset` → 快照，`report` → 只追加区），并对**需求/架构/接口/测试**四类文档强制纳入统一项目知识库（见 §六.4）。

## 二、核心概念模型（v2 重写）：组织 → 部门 → 角色 → 员工 → 会话

### 2.1 五层模型

| 层 | 定义 | 关键字段 | v1 对应 |
|---|---|---|---|
| 组织 Organization | 多项目/多团队的顶层容器 | `org_id`、成员部门、权限域 | 无（新增） |
| 部门 Department | 职能分组 | `dept_id`、负责人、角色列表 | 无（新增） |
| 角色 Role | 职责与契约（宿主无关） | `role_id`、职责、输入输出 schema、技能、权限、所需 CLI 能力 | v1 静态角色 YAML |
| 员工 Agent | 角色的一个可调度执行体（**绑定具体 CLI**） | `agent_id`、`role_id`、`cli_id`、能力标签、并发上限、工作区 | v1 角色实例的一部分 |
| 会话 Session | 员工的一次执行 | `session_id`、`agent_id`、ACP 会话、状态 | v1 会话 |

**关键规则**：
1. **角色 ≠ Agent**：一个角色可挂 N 个员工；一个阶段可派多个员工并行。
2. **员工绑定 CLI，角色不绑定**：角色声明"所需能力"（如 `acp.acp_support`、`workspace.isolation`），调度时从满足能力的已发现 CLI 中挑选员工。
3. **员工实例 ≠ 会话**：同一员工配置可在不同任务中开多个会话；真实并发由 CLI 与工作区隔离能力决定。

### 2.2 Agent CLI 发现与注册（v2 核心新增）

**发现来源**（首次启动与手动"重新扫描"均执行）：

| 来源 | 方法 | 产出 |
|---|---|---|
| PATH | 扫描可执行文件，匹配已知 CLI 名与 `--version` | 路径、版本 |
| 应用目录 | macOS `/Applications`、Windows 开始菜单/Program Files、Linux `.desktop` | 安装位置、图标 |
| 包管理器 | npm 全局、Homebrew、pipx、cargo install 列表 | 版本、可升级性 |
| 用户配置 | 手动添加可执行文件路径（覆盖/补充自动发现） | 自定义 CLI |

**能力探测**：对发现的 CLI 执行轻量握手——是否支持 ACP / stdio / 会话恢复方言 / 并发上限 / 证据钩子。结果写入 CLI 能力矩阵，供调度器使用。

**数据模型**：
```yaml
agent_cli:
  cli_id: codex-main
  name: Codex CLI
  executable: /usr/local/bin/codex
  version: 0.78.0
  detected_at: 2026-11-23T...
  capabilities: [acp, stdio, session_resume, workspace_isolation]
  max_concurrent_sessions: 3
  connection_status: idle | connected | unreachable | probing
  verified_at: ...
```

**边界**：扫描只读，不修改用户 CLI 配置、不代替用户安装；不可达的 CLI 标 `unreachable` 并给出修复建议，不静默丢弃。

### 2.3 Agent Team

```yaml
agent_team:
  team_id: team-productLaunch
  name: 产品发布团队
  departments: [产品部, 研发管理部, 前端部, 后端部, 测试部, 平台安全部]
  lead_role: 研发负责人
  members:                       # 角色 → 员工列表
    - role: 产品经理
      agents: [pm-analyst-1, pm-analyst-2, pm-reviewer-1]   # 一角色多员工
    - role: 前端开发
      agents: [fe-01, fe-02, fe-03]
  run_mode: semi_auto            # auto | semi_auto | manual
  approval_gates: [prd_freeze, architecture_confirm, release]
  iteration_capacity: 5
```

**调度原则**：任务按"能力标签 + 当前负载 + 依赖满足 + 工作区无冲突"分配到具体员工；员工可跨项目复用，但同一时刻并发受 CLI 与工作区约束。

### 2.4 工作流与阶段

工作流 = 阶段 DAG + 阶段内并行规则 + 门禁 + 运行模式 + 变更策略。v1 的"节点/交接包/轮次/升级"引擎保留，阶段是新的编排单位（一个阶段可包含多个节点/任务）。

### 2.5 统一项目知识库

所有员工共享同一份经确认的项目资料，不各自持有互相不一致的上下文。目录见 §六.4。

## 三、核心架构决策（引擎底座，v1 保留 + 适配）

### 3.1 Control Plane

v1 的 daemon 升级为 Control Plane，职责扩展为：组织/部门/角色/员工注册、任务调度、评审与审批、项目知识库、产物与版本管理、事件与状态管理。原 ACP 适配器、事件总线、持久化直接复用。

### 3.2 ACP 作为通用会话管理协议

复用 v1 §二：`initialize` / `session/new` / `session/prompt` / `session/update` / `session/cancel` 五个原语；宿主方言收敛在适配器；daemon 不出现 `if host == 'xxx'`。新增一条：**CLI 能力探测结果也收敛在适配器层**，不进核心。

### 3.3 待验证项（阶段 A 必须回答）

| 项 | 问题 |
|---|---|
| CLI 发现覆盖率 | 常见 CLI 的安装路径/版本命令是否可跨平台稳定识别 |
| 能力探测可靠性 | 不启动完整会话能否可靠判断 ACP/恢复方言/并发上限 |
| 一角色多员工 | 同一角色的多员工并行是否产生工作区串台 |
| 阶段内并行 | 前后端并行 + QA 同步编写测试的依赖驱动是否可裁决 |
| 门禁实效 | 全自动/半自动/手动三模式在真实研发流程中是否可收敛 |

## 四、状态模型（v1 引擎底座，保留并扩一层）

四层状态机完整保留（**完整表格与时序见 v1 备份 `index.v1-baseline-20261123.md` §三**）：

1. **节点状态 9 态**：`blocked → ready → assigned → running → review → done`，含 `failed` / `escalated` / `cancelled` 与回流边。
2. **会话状态 6 态**：`idle` / `thinking` / `tool_running` / `waiting_input` / `waiting_dependency` / `escalated`。
3. **角色状态 6 态**：`inactive` / `available` / `busy` / `cooldown` / `unavailable` / `retired` —— v2 中此状态计算到**员工 Agent**上，角色层显示其下员工的聚合状态。
4. **交接包状态 7 态**：`created → delivered → accepted → consumed`，含 `pending` / `rejected` / `expired`。

**v2 新增第 5 层：任务状态**（研发流程语义）：
```
待处理 → 可领取 → 已领取 → 开发中 → 待评审 → 修改中 → 已完成
异常分支：退回负责人 / 需求澄清 / 接口变更请求 / 架构评审 / 冲突裁决 / 超时告警重试 / 意外退出恢复
```
**新增团队/阶段状态**：`规划中 / 就绪 / 执行中 / 门禁等待 / 回流中 / 交付 / 复盘完成`。

**核心不变量（继承 v1，不得破坏）**：状态迁移唯一入口 `orchestrator.transit()` + CAS；`halted` 独立一次落盘；事件先落盘再广播；`verdict` 严格判定；中文唯一来源 `src/cli/labels.js`。

## 五、核心能力域（v2 重排，★为新增/核心）

### 能力域 0 ★：Agent CLI 发现与接入（**第一入口**）

- 自动扫描 PATH / 应用目录 / 包管理器 / 用户配置，罗列本机所有 Agent CLI
- 能力探测（ACP / transport / 恢复方言 / 并发 / 证据钩子）与连接测试
- CLI 能力矩阵、可替换的员工载体、不可达诊断
- **CLI 清单是配置项，不硬编码**：本机实测当前只有 WorkBuddy.app，目标场景模板列出 Codex/Claude Code/Cursor/Gemini CLI/OpenCode；最终支持集见附录裁决清单 D-2

**实现方式（D-2 技术调研结论，2026-11-23 实测）**：

| 环节 | 三方可否直接支持 | 结论 |
|---|---|---|
| 静态"装了什么"的清单发现 | **可**。开源 `geiger-scan`（`Atomburstofficial/geiger`，MIT，npm 0.4.0，**零依赖**，Node≥18）：`data/known-agents.json` 内置 Claude Code / Codex CLI / Gemini CLI / Qwen / OpenCode / DSH / Cursor / VS Code 扩展 / npm 全局包等识别表；11 个 detector 覆盖配置目录、全局包、IDE 扩展、浏览器扩展；输出 `schemaVersion:1` 的只读 JSON | **复用其识别表 + detector 设计**，不整体依赖其 CLI（见下） |
| "能不能被 ACP 驱动"的能力握手 | **否**。已逐文件核对 geiger 源码（`src/detectors/**`、`src/engine.js`）：无 `acp` / `initialize` / `session/new` / `stdio` 相关代码，它只读配置、不做运行时握手；Trove（`Intevity/trove`，MIT）只做检测 + 转发 OTEL 遥测，也不做 ACP 会话 | **必须自研**，落在 v1 已有的 `src/adapter/host-config.js` + adapter factory 上扩展"能力探测"步骤 |
| 绑定员工 / 调度 / 工作流执行 | 否，属于产品核心壁垒 | 自研（阶段 A2~A5） |

**集成策略**：不把 `npx geiger-scan` 作为运行时硬依赖（桌面应用不能假设用户有 Node / 能联网拉包 / 接受第三方扫描进程读全部配置）。做法为 ① 移植其 MIT 识别表与 detector 思路到 `src/adapter/cli-discovery/`，本地零依赖实现；② 如需对齐生态变化，保留"导入 geiger JSON 快照"的可选入口（`--json` 输出 schema 公开、版本化）；③ 自研的能力握手结果写进 `agent_cli.capabilities`，供调度器按能力选员工。

### 能力域 1 ★：组织 / 部门 / 角色 / 员工管理

- 组织、部门、角色、员工四级 CRUD；角色声明所需 CLI 能力
- 一角色多员工；员工绑定具体 CLI；动态创建与释放会话
- 任务分配策略：能力 / 负载 / 依赖 / 冲突 / 插件·Skill·MCP 需求
- 沿用 v1 角色注册表与校验器，扩展"角色-员工"关系校验

### 能力域 2 ★：Agent Team 搭建器

- 拖拽式团队编排：部门 → 角色 → 员工，设负责人与并发
- 协作规则：汇报关系、裁决路径、冲突升级
- 团队模板（新建 / 从内置派生 / 导入导出）

### 能力域 3 ★：研发工作流创建器（12 阶段）

- 12 阶段模板 + 自定义 DAG；阶段内并行与依赖驱动
- 评审门禁（问题四级：阻断/严重/一般/建议）、三种运行模式
- 变更管理：需求变更 → 架构/任务/用例影响分析
- 沿用 v1 工作流引擎原语（并行/分支/回流/轮次/子工作流），阶段为新上层单位

### 能力域 4 ★：横向协作机制

任务管理、文档管理、评审管理、Agent 调度、质量管理、变更管理——贯穿全部阶段，不是独立页面功能。

### 能力域 5：多会话驱动（v1 复用）

统一 ACP 适配器、会话复用策略、跨宿主混跑、配置翻译、产物隔离。

### 能力域 6：会话间唤醒与交接（v1 复用）

### 能力域 7：实例管理与视图（v1 复用 + 挂载新视图）

### 能力域 8：治理与审计（v1 复用）

权限拦截、证据过期、链式哈希、人工终审、预算配额、生态导出与迁移。

## 六、内置场景模板：12 阶段研发工作流（用户目标场景之一，非唯一形态）

### 6.1 十二阶段

1. **产品构思与需求分析**：用户想法 → 多名产品经理独立分析 → 交叉评审 → 补调研 → PRD
2. **PRD 评审与确认**：研发负责人/前端/后端/QA/安全多角色评审 → 问题汇总 → 修正 → **PRD 冻结（门禁）**
3. **技术架构与研发规划**：架构/选型/数据模型/接口/迭代规划/任务拆分
4. **技术方案评审**：前后端+QA 评审 → 风险 → 修正 → **方案确认（门禁）**
5. **迭代启动与任务分配**：负责人分派 → 员工领取 → 确认依赖 → 开发计划
6. **并行研发**：多前端/后端并行 → 代码评审 → 单测 → CI
7. **集成与联调**：合并 → 接口联调 → 集成测试 → 缺陷修复
8. **QA 测试**：计划 → 功能/接口/自动化/性能/安全/回归测试
9. **缺陷处理闭环**：缺陷单 → 归属分析 → 分派 → 修复 → 复测 → 回归
10. **迭代验收**：QA 验收 + 产品验收 + 研发负责人确认（三方门禁）
11. **发布与交付**：发布检查 → 部署 → 冒烟 → 交付记录
12. **复盘与下一迭代**：质量复盘 → 需求反馈 → 技术债 → 下轮规划

> 阶段 6–9 非严格串行：QA 在开发期即参与测试设计，部分测试随任务完成提前开展。

### 6.2 三种运行模式

| 模式 | 行为 |
|---|---|
| 全自动 | Agent 自动协作、分配、评审、推进 |
| 半自动 | 日常任务自动，关键节点（PRD 冻结/架构确认/需求变更/正式发布）人工审批 |
| 手动 | 每阶段由用户决定是否继续 |

### 6.3 评审与问题分级

| 等级 | 处理 |
|---|---|
| 阻断 | 必须修复才能通过 |
| 严重 | 必须明确解决方案 |
| 一般 | 负责人决定是否修改 |
| 建议 | 记录，可进后续迭代 |

**独立评审机制**：各 Agent 独立阅读、独立出方案、交叉审核，再由负责人汇总决策——避免多 Agent 互相附和产生相同错误。

### 6.4 项目知识库目录

```
project/
├── requirements/    original-idea.md / prd.md / review/ / changes/
├── architecture/    system-design.md / frontend-design.md / backend-design.md
│                    / database-design.md / api-contracts/
├── iterations/      <iter>/plan.md / tasks/ / acceptance.md
├── testing/         test-plans/ / test-cases/ / bug-reports/ / test-reports/
├── reviews/  releases/  retrospectives/
```

### 6.5 任务流转异常规则

Agent 无法完成 → 退回重派；需求不明 → 发起澄清；接口不全 → 变更请求；架构不合理 → 发起评审；QA 发现需求缺失 → 退回产品评审；两 Agent 冲突 → 负责人裁决；超时 → 告警/重试/重派；意外退出 → 恢复任务与产物；需求变更 → 计算受影响架构/任务/用例。配套 ACK 确认、幂等交付、重试、执行记录、产物快照。

## 七、运行时模型与数据布局

```
启动 → 扫描 CLI → 注册员工载体 → 建组织/角色/员工 → 搭 Team
  → 建工作流（阶段 DAG + 门禁 + 模式）→ 启动实例
  → 按依赖调度任务：选员工 → 翻译 ACP 参数 → 建会话 → prompt
  → 订阅 update → 校验产出/证据 → 更新任务/阶段/交接状态
  → 命中评审门禁 → 人工/自动裁决 → 回流或推进
  → 全事件写日志 → 更新健康度 → 推送视图
  → 阶段 12 完成 → 产物归档 + 复盘
```

**实际落盘布局（beta.4 已实现，以此为准）**：

| 路径 | 内容 | 归属 |

| `.orch/cli-registry.json` | CLI 发现结果（识别表命中 + 能力探测） | A1 |
| `.orch/studio.json` | **单一状态文件**：部门/角色/员工/会话/团队/工作流/运行/任务/缺陷/变更 | A2~A6 |

| `.orch/kb/<runId>/run.md` | 运行摘要（阶段×状态×角色×门禁） | A5 |

## 八、边界声明

1. Maestro 是 Control Plane，不实现大模型能力；CLI 是执行层，并列不嵌套。
2. 只控制 CLI 客户端，不控制任何网页版客户端。
3. CLI 扫描只读，不改用户系统配置、不代装软件。
4. 角色不绑定 CLI，员工绑定 CLI；调度按能力而非名称。
5. 一个角色可多员工，一个阶段可多员工并行；并发受 CLI 与工作区约束。
6. 三运行模式的门禁语义由用户配置决定，产品不预设"必须全自动"。
7. 所有员工共享统一项目知识库；不允许各自持有不一致上下文。
8. 引擎能力（v1）是被调用的底座，不是产品卖点；用户价值的度量是"能否配出并跑通一个 Agent Team 工作流"。

## 阶段 A：核心形态闭环（最高优先级）

### A1 — Agent CLI 发现与罗列
- 扫描 PATH / 应用目录 / 包管理器 / 用户配置；罗列名称、路径、版本、连接状态
- 能力探测与连接测试；CLI 能力矩阵；重新扫描与不可达诊断
- **验收**：在一台装了至少一种 Agent CLI 的机器上，启动应用能自动列出该 CLI 且信息准确；手动添加自定义 CLI 可执行。
- **证据前提**：需在装有目标 CLI 的机器上取证（当前 macOS 机器仅检出 WorkBuddy.app，见裁决 D-2）。

### A2 — 基于 CLI 创建角色与员工
- 角色 CRUD（职责/契约/技能/所需 CLI 能力）；员工 CRUD 并绑定具体 CLI
- 一角色多员工；部门归属；角色能力校验
- **验收**：用户选一个已发现的 CLI 建角色并挂 2 名员工，两人可各自建会话；角色不绑定死某个 CLI。

### A3 — Agent Team 搭建器
- 部门 → 角色 → 员工拖拽编排；设负责人、并发、协作规则
- 团队模板的创建/派生/导入导出
- **验收**：能搭出"产品部+研发管理部+前端部+后端部+测试部+平台安全部"的完整团队并保存为模板。

### A4 — 研发工作流创建器（12 阶段）
- 12 阶段模板 + 自定义 DAG；阶段内并行与依赖驱动
- 评审门禁、问题四级、三种运行模式、变更影响分析
- **验收**：能配出用户给出场景模板的完整 12 阶段工作流，含 PRD 冻结/架构确认/发布三道门禁；半自动模式下门禁确实拦截；**同时验证可配出一个非研发场景的自定义 DAG**（证明产品不限于这一套阶段）。

### A5 — 端到端闭环（形态成立的判据）
- 从 A1 扫描到 A4 工作流一次跑通：团队执行一个迭代，产出需求→架构→代码→测试→验收→复盘全套产物
- 统一项目知识库读写；产物归档
- **验收**：**目标形态可复现**——用户无需写任何配置和 CLI，纯界面完成一次完整研发迭代；这是 v2 阶段一的退出判据。

### A6 — 横向协作机制基座
- 任务/文档/评审/Agent 调度/质量/变更六机制的持久化与界面入口
- 任务异常流转（澄清/变更/冲突/超时/退出恢复）
- **验收**：制造一次"QA 发现需求缺失"，能走通退回产品评审的完整链路。

**阶段 A 退出条件**：A1~A5 全绿且 A6 可用；**"能配出并跑通一个 Agent Team + 工作流（12 阶段为验收样例，非唯一形态）"是唯一硬判据**。
