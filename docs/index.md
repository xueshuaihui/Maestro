# 多会话编排控制台应用 · 最终需求基线 + 迭代规划

---
Maestro 是一个多会话编排控制台——像指挥家组织乐团一样，在 DSH、Cursor、GPT/Codex、WorkBuddy 中组织多个角色会话，按工作流协同完成编码与非编码任务。

# 第一部分：需求基线

## 一、定位与形态

**一个桌面形态的“多客户端会话控制平面应用”**：常驻系统托盘，后台运行编排守护进程，通过**统一的 ACP 适配器**在 DeepSeek Harness、Cursor、GPT/Codex、WorkBuddy 等宿主中创建并驱动多个原生会话，每个会话承载一个角色。工具只负责**角色定义、通用任务工作流编排、会话间唤醒与交接、实例状态管理、治理与审计**，Agent 的推理、工具调用和鉴权完全由客户端自己处理。

**它不是什么**：不是 Agent 运行时，不替代任何宿主，不是编码专用工具，不是插件或纯 CLI。它有独立窗口和托盘，CLI 和 Web 是辅助入口。

### App 形态

**桌面应用 + 后台 daemon + 系统托盘 + 可选 Web 入口。** 关闭主窗口缩到托盘，daemon 继续监听和投递唤醒；从托盘“退出”才真正停止。

### 与宿主的关系：并列，不嵌套

```
DSH / Cursor / GPT / WorkBuddy（执行层）
Agent 推理/工具/鉴权
        │  统一 ACP 适配器
        ▼
编排控制台（控制层）
角色/工作流/唤醒/实例/治理
```

### 支持的任务类型

工具不预设编码为默认范式。角色和产物类型覆盖**研究分析、内容创作、编码工程、业务运营、通用协调**五组。产物隔离由角色声明的 `artifact_type` 决定：`code` 走 git worktree，`document` 走版本化文件区，`dataset` 走数据快照，`report` 走只追加产物区。**不对非编码任务强制 git 隔离。**

---

## 二、核心架构决策：ACP 作为通用会话管理协议

**决策**：daemon 的适配器层收敛为**一个通用 ACP 客户端**，不再为每个宿主编写独立适配器。所有宿主通过 ACP 暴露会话创建、驱动和唤醒能力；daemon 只实现一份 ACP 接口。

**理由**：ACP 是当前多宿主生态的事实收敛点。DSH 官方 ACP 服务器支持 `session/new`、`session/resume`、`session/list`、`session/close`，且**单连接多会话多路复用已实现**；每个会话拥有独立的 `cwd`，committed answers、prompt completion、cancellation、permission requests 严格隔离。WorkBuddy 通过 ACP HTTP+SSE 暴露 `session/new`、`session/prompt`、`session/cancel`，`session/load` 用于追加消息而非另建会话。GPT/Codex 通过 `codex-acp` 提供 stdio ACP 服务，将 ACP 会话映射到 Codex 线程，支持 `session/new`、`session/resume`、`session/list`、`session/close` 等完整生命周期。Cursor CLI 原生支持 `agent acp`。`@yitom/acp-client` 已经提供“8 大运行时开箱即用”的 ACP 客户端抽象，包含 `resume → load → new` 的会话恢复状态机。

**daemon 的编排逻辑对 ACP 完全无感知**，边界收敛为五个 ACP 原语：`initialize`、`session/new`、`session/prompt`、`session/update`、`session/cancel`。不同宿主对 `session/resume` / `session/load` 的支持差异（DSH 的 `session/resume` 不回放历史，`session/load` 回放；WorkBuddy 的 `session/load` 追加消息；codex-acp-v2 的 `session/resume` 带 `replayFrom`）属于**适配器层的方言处理**，不进入核心。

### 已验证的技术前提

| 前提 | 结论 |
|---|---|
| **DSH ACP 多路复用** | ACP v1 明确允许单连接多会话，DSH 已实现 `Map<SessionId, SessionRecord>` 的隔离 |
| **DSH ACP 持久化与恢复** | 官方服务器广告 `session/resume`（不回放）、`session/list`、`session/close`；`dsh-acp-server` 支持 `--session <id>` 跨调用保持同一会话 |
| **WorkBuddy ACP** | 通过 sidecar 控制管道发现动态 ACP 端口和临时密码，使用 ACP HTTP/SSE 创建会话、发送任务、收集结果 |
| **GPT/Codex ACP** | `codex-acp` 是 stdio ACP agent server，支持 `session/new`、`session/resume`、`session/list`、`session/close` |
| **Cursor ACP** | Cursor CLI 原生支持 `agent acp`（stdio JSON-RPC） |
| **统一 ACP 客户端抽象** | `@yitom/acp-client` 提供 8 运行时开箱即用适配，含会话状态机与恢复流程 |

### 剩余待验证项（阶段零回答）

| 项 | 需回答的问题 |
|---|---|
| **ACP 适配器跨宿主兼容性** | 同一个 ACP 适配器能否用 stdio（DSH/Codex）和 HTTP/SSE（WorkBuddy）两种 transport 驱动，而无需修改核心 |
| **ACP 会话恢复的方言差异** | 各宿主的 `session/resume` / `session/load` 语义差异是否能在适配器层统一，而不泄露到 daemon |
| **ACP 并发会话的隔离强度** | 同时 3–5 个 ACP 会话在 daemon 驱动下，cwd、工具调用、权限请求是否严格隔离 |
| **非编码任务的证据提取** | ACP 的 `session/update` 事件流是否包含足够的“产物就绪 + 审核确认”语义，还是需要适配器补充 |
| **Cursor ACP 的并发稳定性** | 3–5 个并发 Cursor ACP 会话的失败率和延迟 |

## 三、核心能力域

### 能力域 1：角色与技能资产

角色是**宿主无关的可复用资产**，覆盖编码与非编码场景。

- **内置角色库**：约 15 个角色，分通用协调、研究分析、内容创作、编码工程、业务运营五组
- **自定义角色**：从零创建、从内置派生、从导入包安装
- **技能组合**：角色引用可复用的“技能包”（提示词 + 工作方法 + 可选验证命令）
- **角色契约**：声明输入输出 schema、工具集、`artifact_type`、副作用等级、唤醒白名单
- **产物类型驱动隔离**：`code` → worktree；`document` → 版本化文件区；`dataset` → 快照；`report` → 只追加区
- **角色校验**：schema 完整性、技能引用有效、契约连通、权限闭环、派生链无循环

**边界**：角色声明的工具集和路径约束是**声明式**的，由适配器翻译给宿主；实际执行边界由宿主原生机制负责。

---

### 能力域 2：通用任务工作流编排

工作流是**宿主无关的声明式资产**，引擎不假设产物是代码。

- **声明式工作流**：YAML 定义角色节点、依赖边、条件路由、回流循环、人工节点、升级路径
- **通用原语**：顺序、并行 fan-out/fan-in、条件分支、回流循环、轮次上限、超时、重试、人工节点、子工作流、升级、终止
- **双内置模板**：编码闭环（开发→测试→缺陷回流→升级）与通用任务闭环（研究→撰写→审核→修订回流→交付），共享同一引擎
- **交接包**：只携带结构化有界上下文（任务、产物引用、证据引用、约束、指令），不携带完整对话历史；必须通过目标角色输入 schema 校验
- **字段映射**：支持上下游字段名差异的显式映射
- **产物合并/汇总顺序**：并行节点按声明顺序合并；代码走 git 合并，文档走版本合并，数据走人工裁决
- **工作流校验**：可达性、回流边必须有轮次上限、并行 scope 不重叠、权限匹配、变量引用有效
- **版本锁定**：实例启动时锁定资产版本，运行中资产更新不影响运行实例

---

### 能力域 3：多会话驱动（统一 ACP 适配器）

**一份 ACP 适配器 + 每个宿主一份薄 transport 配置**，驱动所有支持 ACP 的宿主。

- **通用 ACP 适配器**：实现 `initialize`、`session/new`、`session/prompt`、`subscribeEvents`、`session/cancel`、`closeSession`
- **transport 方言**：stdio（DSH、Codex）、HTTP/SSE（WorkBuddy）、按宿主配置选择；transport 差异不进入 daemon
- **会话恢复方言**：适配器统一处理 `session/resume`（不回放）、`session/load`（回放/追加）、`resume → load → new` 回退链
- **会话复用策略**：角色可配置“任务内复用会话”或“每任务新会话”
- **跨宿主混跑**：同一实例中不同角色可运行在不同宿主上，daemon 统一调度
- **配置翻译**：创建会话时把角色配置（提示词、技能、工具集、路径约束）翻译成 ACP 会话参数
- **产物隔离**：按 `artifact_type` 分配隔离空间

**边界**：适配器只做**ACP 语义翻译和生命周期管理**，不实现推理，不拦截宿主内部工具调用。daemon 不出现任何 `if host == 'xxx'` 的分支。

---

### 能力域 4：会话间唤醒与交接

角色完成后主动唤醒下一个角色，审核驳回能唤醒上游修订，修订后再唤醒审核，形成跨任务类型的闭环。

- **事件订阅**：适配器订阅 ACP `session/update` 完成事件并上报核心
- **集中路由决策**：核心根据工作流路由表判断“唤醒谁、带什么上下文、是否升级”
- **主动唤醒投递**：适配器调用 `session/prompt` 向空闲会话发起新 turn；ACP 对空闲会话的 prompt 语义由宿主保证
- **回流闭环**：支持 A→B→A 往复；核心维护轮次计数，超限时升级人工
- **交接可靠性**：唤醒消息先落盘再投递；失败重试；宿主不在线时消息保持 pending
- **证据门禁**：交接包必须附带**未过期的、与声明产物一致的证据引用**；缺失或过期时核心拒绝投递并触发升级

**边界**：唤醒是**核心集中决策**；适配器只负责 ACP 投递。证据的真实性执行下沉到宿主侧验证机制或独立审核角色，核心校验引用的存在性和有效期。

---

### 能力域 5：实例管理（状态 / 日志 / 公共资料）

实例是**运行时管理的基本单位**，状态变更的裁决权在核心。

- **实例作为管理单元**：每次工作流运行创建一个实例，持有版本快照、节点状态、证据引用、事件日志、人工干预记录、运行时计数器
- **状态视图**：实例概览 + 角色泳道（idle / thinking / waiting / blocked / escalated）+ 节点看板（blocked / ready / running / review / done / failed / escalated）+ 交接流时间线
- **共享工作区**：实例级隔离，三层可见域——`shared/`（全局可读，核心/人工可写）、`stage/`（阶段参与者可读，上游可写）、角色私有上下文（不进入共享区）；`status.md` 作为人类可读交接棒
- **产物存储**：按 `artifact_type` 分区——`artifacts/code/`、`artifacts/docs/`、`artifacts/data/`、`artifacts/reports/`
- **三层日志**：事件日志（审计，append-only、链式哈希）+ 执行日志摘要（调试）+ 追踪 span（跨角色因果链）
- **人工干预队列**：升级和审批统一为可查询队列
- **通知机制**：至少一种触达方式（托盘通知 / 面板轮询 / IM）

**边界**：Agent 的完成声明只是输入，节点状态由核心依据契约和证据链裁决；执行日志完整内容留在宿主，核心只索引摘要和引用。

---

### 能力域 6：治理与审计

防“假交付”、防“越权唤醒”、防“无法追溯”。

- **三层权限模型**：角色声明层（唤醒白名单、审批要求）+ 工作流约束层（节点间产物 scope 隔离）+ 宿主执行层（宿主原生权限）
- **路由层拦截**：核心在唤醒决策时检查角色权限白名单，不合规唤醒直接拒绝并留痕
- **证据引用校验**：核心校验证据引用存在、未过期、与声明产物一致；真实性由宿主侧验证插件或独立审核角色执行
- **审计事件**：所有编排动作写入事件日志，链式哈希防篡改
- **人工终审**：高风险节点（发布、数据变更、合规意见、副作用 high）下游必须有 human 节点或升级路径
- **升级机制**：轮次超限、依赖死锁、契约校验连续失败、证据缺失/过期时自动生成升级请求
- **预算与配额**：单实例并行度上限、预算耗尽时暂停而非失败
- **会话失败区分**：区分会话进程崩溃（重建/升级）与会话运行慢（节点超时）

**边界**：核心能在路由层拒绝不合规唤醒，但**不能在宿主内核层拦截会话内的单次文件写入**——后者由宿主原生机制负责。

## 四、运行时模型与数据布局

### 运行时闭环

```
工作流实例启动
  → 解析节点，计算就绪节点
  → 对每个就绪节点：查角色配置 → 通过 ACP 适配器创建/附着会话
    → 按 artifact_type 分配隔离空间 → 构造交接包 → session/prompt
  → 订阅 ACP session/update 事件
  → 收到完成事件：
      1. 校验输出是否符合角色契约
      2. 校验证据引用存在/未过期/与声明产物一致
      3. 更新节点状态
      4. 评估路由边条件
      5. 命中回流 → 轮次+1 → 检查上限
      6. 命中升级 → 生成 escalation → 人工节点
      7. 命中正常边 → 构造交接包 → session/prompt 唤醒目标节点
      8. 命中 end → 实例结束
  → 所有事件写入事件日志
```

### 数据布局

```
.orch/
├── roles/  skills/  workflows/        # 宿主无关的定义资产
├── hosts/                             # 宿主 transport 配置（stdio / HTTP+SSE）
├── instances/<id>/
│   ├── workspace/
│   │   ├── shared/  stage/  status.md
│   │   └── artifacts/{code,docs,data,reports}/
│   └── state/                         # 节点状态、轮次、检查点
├── inbox/                             # 持久化信箱
└── events.jsonl                       # 事件日志（链式哈希）
```

## 五、边界声明

1. **ACP 是通用会话管理协议，不是唯一协议**：如果某个候选宿主不支持 ACP，接入它需要额外的适配器或 transport 包装；但 ACP 覆盖了当前已知宿主（DSH、Cursor、GPT/Codex、WorkBuddy）。
2. **daemon 编排逻辑对 ACP 无感知**：只依赖五个 ACP 原语；宿主方言（恢复语义、transport）收敛在适配器。
3. **非编码场景的证据真实性依赖独立审核角色**：核心不替代事实核查/编辑审核/合规审查，只确保审核确认被记录为可追溯证据。
4. **不对非编码任务强制 git 隔离**：产物隔离由 `artifact_type` 决定。
5. **核心只做组织、路由和治理**：Agent 推理、工具调用、鉴权、会话内单次操作的实际约束，全部由宿主原生机制负责。
6. **宿主扩展是验证手段，不是功能堆叠**：每次扩展运行同一套回归工作流，差异归属到适配器或核心抽象并修正。

# 第二部分：迭代规划

## 总体节奏

| 阶段 | 迭代数 | 核心目标 | 结束标志 |
|---|---|---|---|
| **阶段零** | 1 | 验证 ACP 适配器跨宿主兼容性，锁定实现路径 | 验证报告完成，ACP 适配器路径锁定 |
| **阶段一** | 10 | DSH 单宿主完整产品链路 | 从角色定义到治理审计全部可用 |
| **阶段二** | 4 | 第二宿主（Cursor）扩展，验证宿主无关性 | 同一套定义行为一致，缺陷清单闭环 |
| **阶段三** | 3 | 第三宿主（WorkBuddy 或 GPT/Codex）扩展，压测抽象边界 | 三宿主行为一致，抽象稳定 |

每迭代 1–2 周，含 1 天迭代评审和 0.5 天复盘。

---

### 阶段零：ACP 适配器兼容性验证（1 个迭代）

**核心任务**：回答剩余待验证项，锁定阶段一的实现路径。

| 验证项 | 产出 |
|---|---|
| **ACP 适配器跨 transport** | 同一适配器分别用 stdio（DSH）和 HTTP/SSE（WorkBuddy 或 mock）驱动，确认核心无需修改 |
| **会话恢复方言统一** | DSH `session/resume`（不回放）与 WorkBuddy `session/load`（追加）能否在适配器层统一为 `resumeOrCreate` |
| **ACP 并发隔离** | 3–5 个 ACP 会话的 cwd、工具调用、权限请求隔离强度 |
| **非编码证据提取** | `session/update` 事件流中能否可靠提取“文件产物就绪 + 审核确认” |
| **Cursor ACP 并发稳定性** | 3–5 个并发 Cursor ACP 会话的失败率和延迟 |

**验收**：验证报告，每个接缝给出“可用 / 受限 / 不可用”结论，阶段一 ACP 适配器实现路径被锁定。**不做功能开发。**

---

### 阶段一：DSH 单宿主完整流程（10 个迭代）

**阶段目标**：在 DSH 上交付完整可用的产品链路——角色定义、工作流编排、ACP 会话驱动、唤醒交接、实例管理、桌面控制台、治理审计全部可用。**不涉及其他宿主。**

#### I1.1 — 编排核心骨架 + ACP 适配器最小链路

- 编排核心骨架：实例状态机、事件总线、持久化基础
- ACP 适配器：`initialize`、`session/new`、`session/prompt`、`subscribeEvents`（stdio transport）
- 单角色单节点跑通：ACP 创建会话、发任务、收完成事件、标记节点 done

**验收**：硬编码单节点任务在 DSH 中通过 ACP 创建会话、完成、被核心感知。

#### I1.2 — 编码闭环（开发→测试→回流→升级）

- 内置角色：开发、测试、协调者
- 编码闭环模板：开发 → 测试 → 缺陷回流 → 轮次上限 → 升级
- 交接包构造与 ACP 投递；轮次计数与升级生成

**验收**：测试第 2 轮失败 → 核心停止回流、生成升级、实例挂起等待人工。

#### I1.3 — 非编码闭环（研究→撰写→审核→回流→升级）

- 内置角色：研究员、撰写者、审核者
- 通用任务闭环模板：研究 → 撰写 → 审核 → 驳回回流 → 轮次上限 → 升级
- 文档类产物走版本化文件区；证据模型泛化：文件存在 + 引用可解析 + 审核角色确认

**验收**：审核角色第 2 轮驳回 → 核心停止回流、生成升级；与 I1.2 共享同一引擎。

#### I1.4 — 共享工作区 + 交接包校验 + CLI 最小命令集

- 共享工作区：`shared/`、`stage/`、`status.md`
- 交接包 schema 校验：缺少必填字段或证据引用时拒绝投递
- 持久化信箱：唤醒消息先落盘再投递，失败重试
- CLI：`orch run`、`orch instance status`、`orch instance log`、`orch escalate resolve`

**验收**：CLI 能看到实例阶段、活跃角色、待处理升级；交接包缺证据时被拒绝并触发升级。

#### I1.5 — 角色注册表 + 技能注册表 + 内置角色扩展

- 角色注册表：`roles/*.yaml` 加载、schema 校验
- 技能注册表：`skills/*/SKILL.md` 加载、技能引用解析
- 内置角色扩展至约 15 个，覆盖五组；内置技能约 10 个，编码与非编码技能并列

**验收**：`orch role list` 列出全部角色；引用不存在的技能时加载被拒绝。

#### I1.6 — 自定义角色 + 工作流完整原语

- 自定义角色三条路径：从零、从内置派生、导入包
- 角色校验器：schema 完整性、技能引用、契约连通、权限闭环、派生链无循环
- 工作流完整原语：并行 fan-out/fan-in、条件分支、子工作流、超时、重试、字段映射
- 工作流校验器：可达性、回流边轮次上限、并行 scope 不重叠、变量引用有效

**验收**：派生角色修改技能引用后行为变化符合预期；契约不连通的工作流被校验器拒绝。

#### I1.7 — 产物类型隔离 + 代码 worktree 集成

- 产物隔离：`code` → git worktree；`document` → 版本化文件区；`dataset` → 快照；`report` → 只追加区
- 代码类角色：独立 worktree、独立分支，核心管理合并顺序
- 合并冲突检测与升级

**验收**：两个开发角色并行修改同模块不同文件，worktree 隔离后顺序合并无覆盖；改同一文件时冲突被检测并升级。

#### I1.8 — 实例管理器完整 + 崩溃恢复

- 实例管理器完整：状态机、轮次计数、检查点
- 崩溃恢复：daemon 重启后从检查点恢复，未完成节点重新调度或标记待人工确认
- 会话失败区分：ACP 会话进程崩溃（重建/升级）vs 运行慢（节点超时）
- 会话复用策略：`reuse` / `fresh` 按角色配置生效

**验收**：回流中途 kill daemon，重启后从检查点恢复且不重复已完成节点。

#### I1.9 — 桌面控制台应用（主窗口 + 看板 + 升级处理）

- 桌面壳（Tauri/Electron）：主窗口 + 系统托盘
- 实例列表 + 实例详情 + 角色泳道 + 节点看板
- 交接流时间线 + 升级队列（一键继续/重派/终止）+ 证据浏览
- 托盘交互：实例数/待处理升级数、通知、暂停/退出
- 一键跳转：从角色泳道跳转到 DSH 对应会话

**验收**：人在面板上完整走“发现问题→查看证据→处理升级→实例继续”，不需要终端；关闭主窗口后 daemon 继续投递唤醒。

#### I1.10 — 资产库浏览 + 工作流画布 + 治理加固

- 角色库/技能库/工作流库浏览；工作流画布（只读）
- 链式哈希审计：每条事件附加 `prev_event_hash`
- 路由层权限拦截：角色唤醒白名单校验
- 证据过期检测：证据与声明产物指纹不一致时拒绝交接
- 高风险节点人工终审
- 预算与配额：单实例并行度上限、预算耗尽时暂停而非失败
- 性能基线：≥20 并发实例、≥50 活跃会话、handoff 延迟 <2s

**验收**：篡改事件日志一条记录，链式哈希校验失败；证据过期后交接被拒绝；越权唤醒被拦截并留痕；20 实例并发时 handoff 延迟在目标内。

**阶段一退出条件**：DSH 上从角色定义、工作流编排、ACP 会话驱动、唤醒交接、实例管理、桌面控制台到治理审计全部可用；编码与非编码两条闭环均跑通；桌面应用可独立完成日常操作。

### 阶段二：第二宿主扩展（Cursor，4 个迭代）

**阶段目标**：用同一套 ACP 适配器接入 Cursor，跑通回归工作流；扩展用于验证核心抽象是否宿主无关，并发现缺陷。

#### I2.1 — Cursor ACP transport 接入

- Cursor ACP 配置：`agent acp`（stdio）
- 复用阶段一的 ACP 适配器，仅添加 Cursor transport 配置
- 会话唤醒：空闲会话 `session/prompt` 立即开始 turn
- 证据采集：从 ACP `session/update` 提取退出码和工作区指纹

**验收**：I1.2 的编码闭环在 Cursor 上跑通，行为与 DSH 一致。

#### I2.2 — 非编码闭环回归 + 适配器差异修正

- I1.3 的非编码闭环在 Cursor 上跑通
- 对比 DSH 与 Cursor 的 ACP 行为差异（恢复语义、事件流、审批透传）
- 差异修正：适配器问题修适配器；核心抽象假设问题修核心
- 记录“宿主无关性缺陷清单”

**验收**：非编码闭环在两个宿主上行为一致；缺陷清单中每一项有明确归属和修正记录。

#### I2.3 — 跨宿主混跑 + 实例管理器跨宿主适配

- 同一实例中产品角色在 DSH、开发角色在 Cursor，核心统一调度
- 会话注册表区分宿主，状态机不感知宿主差异
- 会话失败区分在两宿主上的统一处理

**验收**：混跑实例中两个宿主的角色能正常交接；任一宿主 ACP 会话失败时核心能正确重建或升级。

#### I2.4 — 桌面控制台多宿主视图 + 回归测试套件

- 桌面控制台：实例详情标注角色所在宿主；一键跳转对应宿主会话
- 回归测试套件：编码闭环 + 非编码闭环 + 跨宿主混跑，作为后续宿主的准入测试
- 宿主能力矩阵：记录每个宿主支持的能力（resume/load 语义、transport、证据钩子）

**验收**：桌面应用能区分 DSH 和 Cursor 会话；回归套件可在新宿主接入时一键运行。

**阶段二退出条件**：同一套 ACP 适配器在 DSH 和 Cursor 上行为一致；跨宿主混跑可用；回归套件和宿主能力矩阵建立；宿主无关性缺陷清单闭环。

### 阶段三：第三宿主扩展与能力验证（3 个迭代）

**阶段目标**：接入第三宿主（候选：WorkBuddy 的 HTTP/SSE ACP，或 GPT/Codex 的 `codex-acp`），进一步压测 ACP 适配器的 transport 抽象和核心抽象边界。

#### I3.1 — 第三宿主选型 + ACP transport 最小链路

- 第三宿主选型：评估 WorkBuddy（HTTP/SSE）或 GPT/Codex（stdio）的 ACP 成熟度
- 适配器最小链路：复用通用 ACP 适配器，添加对应 transport 配置
- 运行回归套件最小集（单节点任务）

**验收**：第三宿主上单节点任务通过 ACP 跑通；记录与 DSH/Cursor 的 transport 差异。

#### I3.2 — 回归套件全量运行 + 核心抽象修正

- 编码闭环 + 非编码闭环 + 跨宿主混跑在第三宿主上运行
- 对比三宿主行为，识别核心抽象中的隐藏假设（如“会话可主动唤醒”“证据可自动采集”）
- 修正核心抽象：宿主特定假设下沉到适配器接口，核心只依赖最小公约数
- 更新宿主能力矩阵和 ACP 适配器方言文档

**验收**：三宿主回归套件全部通过；核心抽象中不再有未声明的宿主假设；适配器方言文档更新。

#### I3.3 — 多宿主治理一致性 + 缺陷复盘与规划收尾

- 多宿主治理一致性：审计事件格式统一、权限拦截逻辑统一、证据过期检测统一
- 多宿主性能基线：三宿主并发实例的 handoff 延迟和失败率
- 缺陷复盘：整理三阶段发现的缺陷类型，归入“适配器方言问题 / 核心抽象问题 / 宿主 ACP 能力限制”
- 规划收尾：明确后续宿主接入的标准流程（选型 → transport 配置 → 回归套件 → 抽象修正）

**验收**：三宿主上治理行为一致；缺陷复盘报告完成；新宿主接入标准流程文档化。

**阶段三退出条件**：三个宿主上同一套 ACP 适配器行为一致；核心抽象经过三次扩展压测后稳定；宿主接入标准流程可复用。

## 关键判断点

| 判断点 | 位置 | 意义 |
|---|---|---|
| 统一 ACP 适配器能否跨 transport 驱动 | I0.1 | 核心抽象是否真正宿主无关 |
| DSH 单宿主完整流程是否可用 | 阶段一退出 | 产品链路是否成立，不依赖多宿主 |
| 同一适配器在第二宿主是否行为一致 | I2.2 验收 | ACP 方言处理是否收敛在适配器 |
| 跨宿主混跑是否可用 | I2.3 验收 | 多宿主协同是否成立 |
| 第三宿主是否暴露新的隐藏假设 | I3.2 验收 | 抽象是否经过足够压测 |
| 三宿主治理是否一致 | I3.3 验收 | 治理机制是否可移植 |

---

**一句话总结**：以 **ACP 作为通用会话管理协议**，daemon 只实现一份适配器，每个宿主只添加极薄的 transport 配置和方言声明；先在 DSH 上把完整产品链路做透，再用 Cursor 验证宿主无关性，最后用 WorkBuddy 或 GPT/Codex 压测 transport 抽象。宿主扩展不再是“功能交付”，而是“验证能力和发现缺陷”的手段；差异必须归属到 ACP 方言适配器或核心抽象并修正。
