### 关键教训：域层验证通过 ≠ 通路验证通过

新增 `scripts/verify-ui-flow.mjs`（`npm run verify:ui-flow`），不手工注册任何路由，完全复用 `server.js`
里产品真实存在的懒挂接，请求序列 = 搭建台页面点击时发出的那几条。它抓到 2 个域层验证漏掉的缺口：

1. `src/studio/run.js`：`startRun` 只返回 `{ok, run, planned}`，把 `advanceRun` 的 `waiting` 丢了 →
   `POST /studio/action{run.start}` 永远回 `waiting: null`，页面只能靠 `run.status` 猜停在哪道门禁。
2. `src/studio/tasks.js`：`raiseRequirementGap` 只给 `runId` 时没解析阶段 → `change.stageId = null` →
   查不到任务 → **任务不会被 block**，"退回产品评审"闭环绕了一半。

两者被 `verify-core.mjs` 掩盖的原因：它显式传 `--stage s08`，等于替用户补齐了参数。
**结论：凡是"验证脚本自己补参数才能跑通"的链路，必须再走一遍真实入口。**

### CI 收敛过程（四轮，值得记）

Windows 门禁前两轮抓到的**都是产品缺陷不是夹具问题**：
1. `discover.js` 忽略注入的 `platform`/`env`，直接读 `process.platform` / `process.env.PATHEXT`。
2. `probe.js` 裸 `spawn` 启动 `.cmd` —— Node 自 CVE-2024-27980 后拒绝（EINVAL），而 Windows 上 npm 装的
   agent CLI 几乎全是 `.cmd` shim → **该平台 A1 能力形同不存在**。修法：仅 win32 且 `.cmd`/`.bat` 时经
   `cmd.exe /d /s /c` 启动并自行加引号，**不用 `shell: true`**。
3. 夹具断言 POSIX exec 位（`mode & 0o111`）在 NTFS 上必然假红 → 改为按宿主平台建模（win32 造 `.CMD` 走 PATHEXT）。
4. `ACC-10` 把 JS 本体放 PATH 目录里，被 `PATHEXT` 里的 `.JS` 再命中一次 → 本体移出 PATH 目录。
- `AC-60` 在 arm64 runner 上 `duration 15.16s` 正好命中 `waitForNode` 15s 上界 → 放宽到 30s（只改上界，不改断言）。
- **CI 冷启动首次 spawn 比本地慢一个量级**，等待上界按最慢硬件留余量。
