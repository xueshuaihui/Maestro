| 类别 | 用例 | 修法 |
|---|---|---|
| CRLF | `shapeSnapshot` 逐字、`BR-26` 中文扫描、`既有 8 条 HTTP 路径` | 读源码后 `replace(/\r\n/g,'\n')` |

**清理前必须 `orch core stop`**。本机 `%TEMP%` 因此堆积了 300+ 个 `maestro-i11-reg-*` 从未删掉。

**gate 的隔离复跑会识破 flake**：Windows job 报
`FAIL 失败集合与判定基线差集为 0 — 意外失败（隔离复跑仍失败）：三主链…`，
不是简单按名字判红，而是复跑确认。所以「重试兜底」不能代替根因修复。

## GitHub 推送的兜底通道（重要）

- 本机 `github.com:443` **直连与代理均不可达**（`Failed to connect` / `Recv failure: Connection was reset`），
  但 **`api.github.com` 直连稳定（200）**。
- 兜底：用 **Git Data API** 推送（脚本 `%TEMP%/gh-push/push-via-api.mjs`）：
  `POST /git/blobs`（base64）→ `POST /git/trees`（`base_tree` + 条目）→ `POST /git/commits` → `PATCH /git/refs/heads/<b>`。
- **重建出的 commit sha 与本地不同**（commit 元数据细节差异），但 **tree sha 完全相同**即内容等价。
  校验口径应为「比对 tree sha」而不是「比对 commit sha」；后续 push 脚本要允许「父 sha 不同但 tree 相同」。
- PAT 从 `git credential fill` 取（不进命令行）；权限 `permissions.push=true` 即可，`actions` 用同一 token。
- 触发 CI：`POST /repos/{o}/{r}/actions/workflows/release.yml/dispatches {ref}` → 204。

## ⚠️ beta.2 踩的最大一个坑：`mountApp` 越界引用（真实壳才炸）

- 现象：macOS 门禁判红 `AC-26 壳面 ... rows 探针缺失`；Windows 门禁却过。
- 关键：**Windows 的 AC-26 是 skip**（bundle 不新鲜），所以「Windows 过」等于没验证真实壳。
  `test/` 里唯一跑 `mountApp` 的路径此前**完全不存在**——createApp 级测试不碰 mountApp，
  界面冒烟脚本是手工构造 ctx 直接调 `renderShell`。真实窗口只在 CI 上跑。
- 定位靠自加探针：`rows-empty{ready:false, labels:0, instances:2, status:"idle"}`
  → 实例读得到、文案表永远为空、连接状态还是 idle ⇒ `index.html` 的 `app.start()` 根本没执行。
- 根因：`mountApp` 里有 10 处引用 `createApp` 作用域内的 `noticeText`，
  首帧 `buildShellContext` 直接 `ReferenceError` → `mountApp` 抛出 → `mounted` 为 undefined
  → `app.start()` 不执行 → 文案永不加载 → 列表永远空。`__MAESTRO_CTL__` 已赋值，所以 ctl 还能触发。
- 修法：`createApp` 暴露 `text(key, params)`，shell 侧用 `labelText` 经它取文案。
- **新增 `test/wp14/mount-smoke.test.js`**（最小 DOM shim + `closest`/点击派发）钉三件事：
  ① 空文案表首帧不抛；② 文案+实例到位后窗口自己发 `rows` 探针；③ 侧栏九项 + 「新建实例」都能跳转。
  这个测试同时能抓「侧栏死链」这类只能靠真机发现的回归。
- 教训：**新写的外壳层如果没有一个测试真正调用 `mountApp`，等于把整个入口交给 CI 去发现**。
  以后任何 mountApp 内的改动，先跑 `test/wp14/mount-smoke.test.js`。
